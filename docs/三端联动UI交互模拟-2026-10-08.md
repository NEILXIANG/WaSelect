## 0. 怎么模拟的（与前三轮的区别）

前几轮主要从**接口**模拟。这一轮从**界面交互**模拟，三端跑在同一个本机服务和同一个库上：

| 端 | 怎么驱动 | 真的部分 | 替身的部分 |
|---|---|---|---|
| 服务端 | `npm run dev` 起在独立模拟库 `japan_shop_sim`（不碰开发库） | 全部：路由、Postgres、调度、事件、审计 | 微信登录走 dev 替身、支付走 mock 通道（回调由脚本按 mock 签名发出，等同机构通知） |
| 管理端 | 内置浏览器里**真实点击 / 输入**（1280×800 视口），截图核对 | 全部：React 页面、请求、提示 | 无 |
| 小程序 | 页面宿主：加载**真 `app.js` 与各页 `index.js`**，模拟点击 / 输入 / 生命周期 | 页面逻辑、vm、utils、请求层、登录、存储语义；请求真打到本机服务端 | `wx` 全局（request 走真 HTTP，导航 / 弹窗 / 剪贴板 / 支付调起被记录）；**不渲染 WXML**（开发者工具 / 真机才能看样式） |

跨端时序（例如"买家停在结算页时运营改价"）用信号文件编排：小程序宿主跑到某一步停住，浏览器里操作完再放行。
宿主脚本放在本地 `.claude/sim-local/`（不进仓库）。

## 2. 发现的问题与修复（全部已修，除注明者）

| # | 级别 | 问题（怎么暴露的） | 修复 |
|---|---|---|---|
| U1 | 中 | 管理端订单搜索框按**回车不搜**，只认点按钮——运营输入单号回车后以为"搜不到" | 回车即搜索（输入法选字的回车除外）；`OrdersPage.dom` 用例 |
| U2 | 低 | 订单列表在 800px 宽下筛选区挤压（"含测试单"竖排） | **未修**：管理端按笔记本宽度设计，记入 §3 |
| U3 | 中 | 详情「支付」行把日元显示成 `mock · ¥2,700`——本项目 `¥` 是人民币（D-36），与同页"合计 2,700 円"并排会被读错币种 | 管理端最小单位金额统一：日元写 `2,700 円`；汇率配置的样例金额同改 |
| U4 | 低 | 「订单修正」面板按钮挤在一起（用了不存在的样式类），填好原因后红字"必填"还挂着 | 改用既有 `form / row2 / link` 样式；输入即清该栏错误 |
| U5 | **高** | 运单号形状"认不出"的提示在**发货之后**才出现——发货邮件已带着错单号发给买家 | 形状规则移到 `shared`（`trackingNoRecognized`，服务端与管理端同一份），「确认发货」与「确认改单号」那一步就提示 |
| U6 | 低 | 事件列表把 `shipment_fixed` 原样显示成英文（另有 `refunded_by_parts`、`test_archived` 同样没中文名） | 补三条中文名；用例钉住伪状态全集 |
| U7 | 中 | 日元单的部分退款金额框提示"如 10.50"，日元没有小数 | 按币种给示例（JPY：整数，如 500） |
| U8 | 中 | 部分退款成功后，页面仍挂着上一个动作的提示「运单号已更新，已给买家重发发货邮件」——运营会以为又发了一封 | 部分退款 / 订单修正开始时清掉旧提示，成功时给自己的提示 |
| U9 | 低 | 结算页提交遇到下架商品只说"商品不存在或已下架"，不说哪一件（回到购物车才标红） | **未修**：购物车已能定位；结算页定位需改页面结构，记入 §3 |
| U10 | **高** | 购物车行价是**加购那一刻的快照**：店家改价后同一屏"行价 1,400 円 / 商品合计 1,600 円"对不上 | 契约 0.6.39 `Quote.lines` 下发逐行当前单价；购物车报价成功后 `cart.syncPrices` 刷新快照并落盘 |
| U11 | 中 | 商品「下架 / 上架」一点即生效，且生效后列表按更新时间**重排**——被操作行跳到第一行、原位置换成另一件，连点两下会误下架另一件 | 两步确认（点一下出「确认下架 / 取消」） |
| U12 | **高** | **本人上一批（AJ-386 P2-8）引入**：库存冲突后点「加载最新值对照」再保存，仍带打开时的旧库存作 `expected_stock` → 永远 40914，只能退出重进 | 加载最新值时同步刷新"打开时库存"；DOM 用例按实测复现（先红后绿） |
| U13 | 低 | 冲突对照表里"分类"显示 `daily` 而不是「生活百货」 | 用分类中文名 |
| U14 | 低 | 运费分档说明把 Markdown 原样显示（反引号、双星号） | 改成普通文案 + `<strong>` |
| U15 | 中 | 停售状态行只显示 `admin:adm-d2b4…`，看不出是谁停的 | 管理端 GET 带 `actor_email`（契约 0.6.39），面板显示邮箱 |
| U16 | 中 | 停售中：购物车底部写"合计未能获取，请稍后重试"；支付页倒计时照走、付款被拦，买家会一直重试到过期 | 购物车提示"暂停接单中，恢复后即可结算"；40916 统一文案说清"到期自动关闭、不扣款、恢复后重下" |
| U17 | 低 | 种子数据：「东京香蕉蛋糕」的推荐语写的是化妆水；承运商叫 `placeholder` | **未修**：开发假数据，真实目录与运费表到手后整体替换（第三轮 P2-30 同口径） |

另记两条**不是缺陷**的观察：
- 开发环境 mock 通道（非审核期、不自动确认）在支付页显示"暂时无法支付"引导，而服务端已建支付行——只在本地出现，审核期 mock 自动确认、生产走 Stripe，不改。
- 5kg 大米运费 14,000 円（商品 2,800 円）：是运费表与商品重量的真实结果，属选品 / 定价问题，不是工程问题。

## 4. 这一轮暴露的方法论问题

- **U12 是我上一批引入的**：P2-8 的服务端与"打开即提交"两条路径都测了，但"冲突 → 加载最新值 → 再保存"这条**恢复路径**没测。
  同类教训：每加一道乐观锁，都要测"撞锁之后怎么走出来"。已补 DOM 用例。
- **U5 / U10 只有界面模拟才暴露**：接口层看，发货返回了 `tracking_recognized`、报价返回了正确合计——都"对"。
  问题出在**时机**（提示晚于邮件）与**同一屏两个数字的来源不同**（快照 vs 报价）。
- **U11 只有真点才暴露**：列表重排在单测里看不出"原位置换成了别的商品"。
