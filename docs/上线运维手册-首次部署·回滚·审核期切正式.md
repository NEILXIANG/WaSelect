# 上线运维手册：首次部署 · 回滚 · 审核期切正式

> 状态：初版（2026-10-06，剩余工作清单 5-3 / O6 / B8）。首次部署实测后逐条补「实测结果」。
> 单一来源：配置项的含义与校验以 `.env.example` + `server/src/config.ts` 为准；平台字段以 `render.yaml`、`deploy/cloudflare-pages.json` 为准。本手册只写**顺序与核对点**，不复制配置表。

---

## 0. 组成与依赖顺序

| 组件 | 平台 | 定义处 | 依赖 |
|---|---|---|---|
| Postgres `waselect-pg` | Render | `render.yaml` databases | — |
| API `waselect-api` | Render web | `render.yaml` | Postgres；部署前自动跑迁移（`preDeployCommand: npm run db:migrate`） |
| 管理端 `waselect-admin` | Render static | `render.yaml` | API 地址（构建期注入） |
| 静态站 `waselect-checkout`（支付落地页 + 法务页） | Cloudflare Pages | `deploy/cloudflare-pages.json` | API 地址（`PUBLIC_API_BASE`，构建期） |
| 每日作业 `waselect-daily` | Render cron（UTC 18:10 = JST 03:10） | `render.yaml` | API 的 `/internal/jobs/daily` + `INTERNAL_JOB_SECRET` |

顺序：**Postgres → API → 管理端 → 静态站 → 每日作业**。后一个都要用到前一个的地址或密钥。

## 1. 首次部署

### 1.1 API 环境变量（Render 控制台逐项填，`sync: false` 的都要手填）

按 `.env.example` 逐项过一遍。生产会被 `config.ts` 跨字段校验**拒绝启动**的组合（漏配时服务起不来，日志里有中文原因）：

- 生产 `PAYMENT_CHANNELS` 含 `mock` 但 `REVIEW_MODE` 不是 `on`；
- 启用 `stripe` 却缺 `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `CHECKOUT_BASE_URL`；
- 生产任何对外地址不是 `https`（`CHECKOUT_BASE_URL` / `IMG_BASE_URL` / `PUBLIC_API_BASE` / `LEGAL_BASE_URL`）；
- 生产没配 `CORS_ORIGINS`；
- 配了 `MAIL_PROVIDER_API_KEY` 没配 `MAIL_FROM`；`SENTRY_DSN` 形状不对；
- `TRUST_PROXY_HOPS ≥ 2` 却没配 `ORIGIN_VERIFY_SECRET`，或者反过来配了 `ORIGIN_VERIFY_SECRET` 层数却小于 2（两者必须成对）；
- 配了 `ALERT_EMAIL` 却没配 `MAIL_PROVIDER_API_KEY`（告警会发不出去）；
- `MOCK_AUTO_CONFIRM=on`（本地模拟付款开关，只允许本地开发与测试）；
- `SENTRY_DSN` 与 `ALERT_EMAIL` **一个都没配**（生产至少要有一个告警通道；`daily_heartbeat_stalled` 只走 Sentry，建议首选 Sentry 免费档，不依赖域名）；
- `PAYMENT_CHANNELS` 含 `wechat`（R1 前没有实现，列出会被静默跳过）；
- 停机各步上限之和超过 `SHUTDOWN_TOTAL_BUDGET_MS`（规则 10）；`PACKAGING_WEIGHT_G` 超过 1000（规则 11）。

可以先留空、之后再补的（留空 = 只记日志 / 不显示，不会坏）：`MAIL_PROVIDER_API_KEY`、`SELLER_*`、`SUPPORT_*`；`ALERT_EMAIL` 与 `SENTRY_DSN` 可以只配其一，不能都空。

⚠️ `MAIL_PROVIDER_API_KEY` + `MAIL_FROM` 在**正式收单前**必须配上：结算页与订单详情已告诉买家「付款、发货、退款会收到邮件」（2026-10-06 复核 AJ-295 / AJ-369）。留空时服务不报错，只是这句承诺不成立。

### 1.2 第一个管理员

1. 首次部署时配 `ADMIN_EMAIL` + `ADMIN_INITIAL_PASSWORD`（≥12 位），启动时自动建出第一个管理员（已存在则不动）。
2. 登录管理端后**立刻**用 `npm run admin:password -- <邮箱> --yes` 换掉初始口令（口令走 stdin，不进命令行历史）。
3. 第二个及以后的管理员：`DATABASE_URL=<生产> npm run admin:create -- <邮箱> --yes`（同样走 stdin；建成写审计 `CLI admin.create`）。
4. **真钱之前**给每个管理员开第二因素（AJ-386 / P1-5）：`DATABASE_URL=<生产> npm run admin:totp -- <邮箱> --yes`，
   把打印出的密钥录进验证器 App（Google Authenticator / 1Password），**然后清屏**。此后登录 = 口令 + 6 位码。
   开通 / 换密钥 / 关闭（`--off`）都会让该管理员现有会话立即失效。手机丢了 = 重新开通一次（换密钥）。
   开了 TOTP 的账号，攻击者从多个来源把登录锁打满时，"口令 + 正确的码"仍能登录。

### 1.3 静态站（Cloudflare Pages）

1. 按 `deploy/cloudflare-pages.json` 填构建命令、输出目录、`NODE_VERSION=22`、`PUBLIC_API_BASE`。
2. 法务页的商家信息在**构建期**从 `SELLER_*` 环境变量填入：Pages 项目里也要配同名变量（与 API 的 `SELLER_*` 保持一致），改了要重新构建。
3. 自定义域绑定后，把同一地址写进 API 的 `CHECKOUT_BASE_URL`（以及需要时的 `LEGAL_BASE_URL`），重启 API。

### 1.4 部署后核对（逐条打勾）

- [ ] `GET /healthz` 200；`GET /readyz` 200（连得上库）。
- [ ] 响应头带 `x-content-type-options: nosniff` 等安全头（`curl -I https://api.<domain>/healthz`）。
- [ ] `curl -I https://checkout.<domain>/o/<真实 token>` → 302，`Location` 指向 API 的 `/api/v1/pay/link/<token>`（`deploy/cloudflare-pages.json` notes 第 4 条）。
- [ ] `GET /api/v1/terms` 返回 `documents` 四类绝对地址，逐个在浏览器打开能看到草案页。
- [ ] Stripe 控制台 webhook 指向 `https://api.<domain>/api/v1/pay/callback/stripe`，发一条测试事件 → 回调登记表有一行。
- [ ] 配了 `SENTRY_DSN` 的：在 **staging** 触发一条 error 级日志（例如把 `STRIPE_SECRET_KEY` 临时改错后发起一次银行卡支付：建会话失败 → 50001，5xx 记 error），Sentry 后台能看到；**这一步同时验证 envelope 省略 `length` 是否被接受**（`server/src/adapters/sentry.ts` NEEDS VERIFICATION）。⚠️ 4xx 记的是 warn，不会上报——别用 404 / 40902 之类去测。
- [ ] 配了邮件的：用一张测试订单走到"已发货"，`contact_email` 收到信；日志 `order_mail_sent`。
- [ ] 手动触发一次每日作业（Render cron 的 "Trigger Run"），然后在管理端「运营日志」看到"最近一次对账"时间更新。

## 2. 审核期（首版提审前后）

审核期的唯一目标：审核员能下单、能看到完整流程，**且不产生任何真实扣款**。

1. API：`REVIEW_MODE=on`、`PAYMENT_CHANNELS=mock`、`REVIEW_SKU_ID=<≥1 円的审核测试商品 id>`、`MOCK_CALLBACK_SECRET`（≥32 位，且不同于 `JWT_SECRET`），**以及 `REVIEW_MODE_UNTIL=<审核期截止日，YYYY-MM-DD>`**。
2. 只有 `REVIEW_SKU_ID` 那件商品能下单；mock 付款单标 `is_test = true`，管理端列表默认不显示（勾选「含测试单」可见）。
3. 审核备注里写明测试商品与 mock 支付路径（界面上不出现"审核 / 测试"字样，AJ-244）。
4. ⚠️ **`REVIEW_MODE_UNTIL` 到期后服务会拒绝启动**（A7 / AJ-378）。这不是惩罚，是最硬的一道提醒——告警通道（Sentry / 告警邮件，生产至少配一个）能报临期，但人未必当天看。届时二选一：
   - 审核还没过 → 把 `REVIEW_MODE_UNTIL` 往后挪（一行配置，重启即恢复）；
   - 审核已过 → 走下面第 3 节切正式。
   临到期 3 天起，每日对账会报一条 `review_mode_closing`；真过期了（进程一直没重启的情况）报 `review_mode_expired`，两者都会进运营告警邮件。

## 3. 审核期 → 正式

按顺序执行，每一步完成再做下一步：

1. **先接通真实通道**：Stripe live 密钥 + webhook secret 配好（`STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET`），`CHECKOUT_BASE_URL` 已是正式静态站地址。
2. **切开关**：`REVIEW_MODE=off`、`PAYMENT_CHANNELS=stripe`（去掉 `mock`——生产留着 mock 会被启动校验拒绝）。保存后 Render 会重启 API。
   - 顺手把 `REVIEW_MODE_UNTIL` 与 `MOCK_CALLBACK_SECRET` 从控制台删掉（留着不报错，但会让下一个人以为审核期还没结束；`MOCK_CALLBACK_SECRET` 在生产未启用 mock 时会被拒绝启动，见 `config.ts` 三审 S1）。
3. **审核期测试单**：不用手动处理。每日作业 `archive_test_orders` 会把付款满 `TEST_ORDER_ARCHIVE_HOURS`（默认 24）小时的测试单迁为已取消并回补库存（事件 note = `test_archived`）。想立刻清掉：手动触发一次每日作业。
4. **核对**：
   - [ ] 首页任意商品可下单（不再限 SKU）；支付页只出现银行卡；
   - [ ] 用一张真卡做一笔小额订单 → 回调落账 → 管理端全额退款 → Stripe 后台看到退款；
   - [ ] 第二天早上「运营日志」的对账无异常（或异常都能解释）。

## 4. 回滚

### 4.1 代码回滚（最常用）

Render 控制台 → 服务 → Deploys → 选上一个绿色部署 → **Rollback**。静态站在 Cloudflare Pages → Deployments 里同样可回滚。

⚠️ **迁移不会随代码回滚**：`preDeployCommand` 只往前跑。回滚前先看这次部署带了哪些迁移（`migrations/` 新增的文件）：

- 只加列 / 加表 / 放宽约束的（如 026、027、028）：旧代码不读新列，**直接回滚代码即可**，不动库。
- 文件头标了 `@breaking` 的（收紧约束、删列等，由 `test/lint/migrations.lint.test.ts` 强制标注）：先读它的 `@breaking` 说明再决定；需要时在**确认无新数据依赖**后执行 `npm run db:migrate:down`（每次退一步）。

### 4.2 配置回滚

环境变量改错导致起不来：日志第一屏就是 `config.ts` 的中文拒绝原因，改回去保存即可（Render 自动重启）。

### 4.3 数据恢复

误删 / 误改业务数据：用 Render Postgres 的备份 / 时间点恢复到**新库**（可用性取决于实例套餐，首次部署时确认，见 §6），核对后再迁回需要的行。⚠️ 审计表（`order_events` / `admin_audit` / `reconciliation_runs`）是 append-only，不能就地改——这是设计，不是故障。

## 5. 日常

| 场景 | 去哪看 / 做什么 |
|---|---|
| 对账有异常 | `ALERT_EMAIL` 收到告警信（按日一封）→ 管理端「运营日志」看取样 id → 订单页按单号搜 |
| 服务报错 | Sentry（配了的话；每分钟最多上报 30 条）→ 用日志里的 `trace_id` 串起整条请求 |
| 缺一件 / 破损 / 完成后售后 | 订单详情「部分退款」：按支付币种填金额（美元填 10.50）+ 原因，两步确认；处理中或结果未知的一笔点「同步」。⚠️ **不要去 Stripe 后台手工退**——库里不会记账，之后整单退款会被机构拒 |
| 买家说"付了款单却关了" | 订单详情事件里有 `late_paid` → 订单列表行"退款"按钮可用 → 全额退款（不回补库存） |
| 价格录错 / 库存错乱，要立刻止血 | 管理端「运营配置」最上面「暂停接单」（填原因、两步确认，立即生效）：报价 / 下单 / 付款全部拦住，回调、退款、发货照常。改正后点「恢复接单」。⚠️ 没有自动到期，记得关 |
| 误拉黑了买家 | 管理端「风控」页底部「已拉黑用户」→ 解除拉黑（填原因）。拉黑时被取消的订单不会恢复，请买家重新下单 |
| 管理员忘记口令 / 被锁 | `npm run admin:password -- <邮箱> --yes`（同时解除登录锁定） |
| 新增运营账号 | `npm run admin:create -- <邮箱> --yes` |
| 导出报关 / 采购清单 | 管理端订单页顶部三个导出按钮（每次导出写审计） |
| 每月对一次钱（AJ-387 / P2-9） | 管理端导出「订单总表」（当月 paid 及以后状态）↔ Stripe 后台 Payments / Payouts 报表：逐笔比单数与金额，差异逐单查。自动回填实收 / 手续费在 Stripe 测试模式联调时做 |
| 运单号录错 | 订单详情「订单修正」→「修改运单号」（填原因、两步确认）；会按新单号给买家重发一封发货邮件 |
| 未付款的单要作废（价格录错等） | 订单详情「订单修正」→「取消订单（未付款）」；已付款的走退款 |
| 改库存时提示"被别人改过"（40914） | 打开编辑页期间有人下单扣了库存：刷新后按最新库存重填 |

### 5.1 发布与迁移纪律（AJ-386，第三轮缺口 P2-17 / P2-19 / P2-20 / P2-28 / P2-29）

- **发布避开 JST 03:00–03:30**：每日作业 03:10 触发、整轮一个事务；部署重启会把它杀掉回滚，cron 却记成功，
  要 26 小时后心跳告警才看得见（P2-19）。撞上了就在控制台手动触发一次 cron。
- **服务起不来先看迁移**：启动时校验"库里执行过的迁移 ⊇ 代码带的迁移"，缺就拒启并点名缺哪条（AJ-385）。
- **上线后再加约束 / 索引**：CHECK 用 `NOT VALID` + 之后单独 `VALIDATE`；索引用 `CREATE INDEX CONCURRENTLY` 且单独成一条迁移
  （node-pg-migrate 默认整条迁移包事务，CONCURRENTLY 进不了事务）。现有 002–033 都是上线前写法（P2-29）。
- **不要在生产跑 `npm run db:seed`**：它会清掉管理员与汇率（只有 `npm run dev` 会补）。
- **审核模式到期只在启动时拦**（P2-20）：过了 `REVIEW_MODE_UNTIL` 进程不重启就继续接 mock 单，每日邮件会报；
  到期前主动改配置并重启。休假前确认 `REVIEW_MODE=off`、停售开关已关。
- **数据库连接池 10**（P2-17）：发起支付在事务内调 Stripe（最长 6 秒）；Stripe 变慢时 10 个并发即占满全池，
  `/readyz` 会跟着变慢。先观察，`readyz` 告警或 p95 明显升高再加池（池大小写在 `server/src/adapters/db.ts`，不是环境变量）或改两阶段发起。
- **邮件 / 告警信发送失败不重试**（P2-28）：单封失败只记 `order_mail_failed` 错误日志；Sentry / 日志告警要盯这个事件。

## 6. 本手册尚未实测的地方（首次部署时逐条补）

- Render 前一层反代是否恰好 1 层（决定 `TRUST_PROXY_HOPS`；改成 2 必须同时配 `ORIGIN_VERIFY_SECRET`）；
- Cloudflare 对查询串是否随 302 保留；
- Sentry envelope 省略 `length` 是否被接受；
- Resend 发件域验证与 SPF / DKIM；
- 回滚一次真实部署的耗时；
- Render Postgres 当前套餐的备份与时间点恢复能力；
- Render cron 控制台手动触发按钮的实际名称（本手册写作 "Trigger Run"）。
- 日志外送：Render Log Streams 指向 Axiom（AJ-139 选型），确认按 `trace_id` 能检索、保留 ≥ 90 天（工程缺口第二轮 §6.3 G2）；
- 密钥轮换步骤（`JWT_SECRET` / `STRIPE_WEBHOOK_SECRET` 目前只能配一把，轮换瞬间全员掉线、在途回调验签失败）：先写清步骤与时机（G9）。
