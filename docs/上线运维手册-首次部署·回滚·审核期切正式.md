# 上线运维手册：首次部署 · 回滚 · 审核期切正式

> 状态：初版（2026-10-06，剩余工作清单 5-3 / O6 / B8）；2026-10-11 按 AJ-441（客服 / 条款拒启）与 AJ-442（强制手机验证、退出作废）订正，并新增第 7–11 节（staging、Stripe 测试模式演练、日志外送、多实例、迁移只前进）。首次部署实测后逐条补「实测结果」。

## 0. 组成与依赖顺序

| 组件 | 平台 | 定义处 | 依赖 |
|---|---|---|---|
| Postgres `waselect-pg` | Render | `render.yaml` databases | — |
| API `waselect-api` | Render web | `render.yaml` | Postgres；部署前自动跑迁移（`preDeployCommand: npm run db:migrate`） |
| 管理端 `waselect-admin` | Render static | `render.yaml` | API 地址（构建期注入） |
| 静态站 `waselect-checkout`（支付落地页 + 法务页） | Cloudflare Pages | `deploy/cloudflare-pages.json` | API 地址（`PUBLIC_API_BASE`，构建期） |
| 每日作业 `waselect-daily` | Render cron（UTC 18:10 = JST 03:10） | `render.yaml` | API 的 `/internal/jobs/daily` + `INTERNAL_JOB_SECRET` |

顺序：**Postgres → API → 管理端 → 静态站 → 每日作业**。后一个都要用到前一个的地址或密钥。

## 1. 首次部署

### 1.1 API 环境变量（Render 控制台逐项填，`sync: false` 的都要手填）

按 `.env.example` 逐项过一遍。生产会被 `config.ts` 跨字段校验**拒绝启动**的组合（漏配时服务起不来，日志里有中文原因）：

- 生产 `PAYMENT_CHANNELS` 含 `mock` 但 `REVIEW_MODE` 不是 `on`；
- 启用 `stripe` 却缺 `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `CHECKOUT_BASE_URL`；
- 生产任何对外地址不是 `https`（`CHECKOUT_BASE_URL` / `IMG_BASE_URL` / `PUBLIC_API_BASE` / `LEGAL_BASE_URL`）；
- 生产没配 `CORS_ORIGINS`；
- 配了 `MAIL_PROVIDER_API_KEY` 没配 `MAIL_FROM`；`SENTRY_DSN` 形状不对；
- `TRUST_PROXY_HOPS ≥ 2` 却没配 `ORIGIN_VERIFY_SECRET`，或者反过来配了 `ORIGIN_VERIFY_SECRET` 层数却小于 2（两者必须成对）；
- 配了 `ALERT_EMAIL` 却没配 `MAIL_PROVIDER_API_KEY`（告警会发不出去）；
- `MOCK_AUTO_CONFIRM=on`（本地模拟付款开关，只允许本地开发与测试）；
- `SENTRY_DSN` 与 `ALERT_EMAIL` **一个都没配**（生产至少要有一个告警通道；`daily_heartbeat_stalled` 只走 Sentry，建议首选 Sentry 免费档，不依赖域名）；
- `PAYMENT_CHANNELS` 含 `wechat`（R1 前没有实现，列出会被静默跳过）；
- 停机各步上限之和超过 `SHUTDOWN_TOTAL_BUDGET_MS`（规则 10）；`PACKAGING_WEIGHT_G` 超过 1000（规则 11）；
- `SUPPORT_EMAIL` 与 `SUPPORT_WECHAT` **一个都没配**（规则 9c / AJ-441：多处提示写"联系客服"，不配则无处可联系；`SUPPORT_HOURS` 不算联系方式）；
- `LEGAL_BASE_URL` 与 `CHECKOUT_BASE_URL` **一个都没有**（规则 9c：结算页没有条款链接）。⚠️ **审核期**只开 mock、没有 `CHECKOUT_BASE_URL`，必须配 `LEGAL_BASE_URL`。

可以先留空、之后再补的（留空 = 只记日志 / 不显示，不会坏）：`MAIL_PROVIDER_API_KEY`、`SELLER_*`、`SUPPORT_HOURS`；`ALERT_EMAIL` 与 `SENTRY_DSN` 可以只配其一，不能都空。

⚠️ `MAIL_PROVIDER_API_KEY` + `MAIL_FROM` 在**正式收单前**必须配上：结算页与订单详情已告诉买家「付款、发货、退款会收到邮件」（2026-10-06 复核 AJ-295 / AJ-369）。留空时服务不报错，只是这句承诺不成立。

### 1.2 第一个管理员

1. 首次部署时配 `ADMIN_EMAIL` + `ADMIN_INITIAL_PASSWORD`（≥12 位），启动时自动建出第一个管理员（已存在则不动）。
2. ⚠️ **生产 / staging 不给没开手机验证（TOTP）的管理员签 token**（AJ-442）：口令对也登不进，登录页提示"还没开启手机验证"。
   所以**部署后、第一次登录前**先给这个管理员开通（见第 4 步），再登录。
3. 登录管理端后**立刻**用 `npm run admin:password -- <邮箱> --yes` 换掉初始口令（口令走 stdin，不进命令行历史）。
   第二个及以后的管理员：`DATABASE_URL=<生产> npm run admin:create -- <邮箱> --yes`（同样走 stdin；建成写审计 `CLI admin.create`），建好后同样先做第 4 步。
4. **每个管理员、每个环境各开通一次**手机验证（AJ-386 开通工具 / AJ-442 起强制）：`DATABASE_URL=<生产> npm run admin:totp -- <邮箱> --yes`。
   - 最好**本人在场**，用他自己的手机把打印出的密钥录进验证器 App，**录完清屏**；密钥不要经微信 / 邮件 / 截图传递（它就是第二道锁本身）。
   - 验证器 App 任选：Google Authenticator、Microsoft Authenticator、iPhone 自带「密码」App（iOS 17+：编辑一条记录 →「设置验证码」→ 手动输入密钥）、1Password 等。
     算法是公开标准 TOTP（RFC 6238：HMAC-SHA1、30 秒一换、6 位），手机算码**不需要联网**，只要手机时间准（开"自动设置时间"）。
   - 此后登录 = 邮箱 + 口令 + App 上当前的 6 位码。之后每次登录**不用**再跑命令。
   - 开通 / 换密钥 / 关闭（`--off`）都会让该管理员现有会话立即失效。**换手机 / 手机丢了 = 再跑一次**（生成新密钥，旧的作废）。
   - 开了 TOTP 的账号，攻击者从多个来源把登录锁打满时，"口令 + 正确的码"仍能登录。
   - 有了 staging 后它是**另一个库**：在 staging 上再开通一次，App 里会多一条（建议命名「WaSelect 预发布」与「WaSelect 正式」区分）。
5. 管理端「退出」会在服务端作废该管理员**所有设备**上的登录（AJ-442）；公用电脑用完务必点退出。

### 1.3 静态站（Cloudflare Pages）

1. 按 `deploy/cloudflare-pages.json` 填构建命令、输出目录、`NODE_VERSION=22`、`PUBLIC_API_BASE`。
2. 法务页的商家信息在**构建期**从 `SELLER_*` 环境变量填入：Pages 项目里也要配同名变量（与 API 的 `SELLER_*` 保持一致），改了要重新构建。
3. 自定义域绑定后，把同一地址写进 API 的 `CHECKOUT_BASE_URL`（以及需要时的 `LEGAL_BASE_URL`），重启 API。

### 1.4 部署后核对（逐条打勾）

- [ ] `GET /healthz` 200；`GET /readyz` 200（连得上库）。
- [ ] 启动日志里是 `launch_ready`，**没有** `launch_not_ready`。有的话按它列出的缺项回到 1.5 补齐（空库上线演练 2026-10-12）。
- [ ] 响应头带 `x-content-type-options: nosniff` 等安全头（`curl -I https://api.<domain>/healthz`）。
- [ ] 管理端静态站带 CSP（AJ-445）：`curl -I https://admin.<domain>/` 能看到 `content-security-policy` 里有 `script-src 'self'`；打开后台走一遍工作台 / 订单 / 商品 / 导出，浏览器控制台没有 `Refused to …` 的拒绝记录。
- [ ] `curl -I https://checkout.<domain>/o/<真实 token>` → 302，`Location` 指向 API 的 `/api/v1/pay/link/<token>`（`deploy/cloudflare-pages.json` notes 第 4 条）。
- [ ] `GET /api/v1/terms` 返回 `documents` 四类绝对地址，逐个在浏览器打开能看到草案页。
- [ ] Stripe 控制台 webhook 指向 `https://api.<domain>/api/v1/pay/callback/stripe`，发一条测试事件 → 回调登记表有一行。
- [ ] 配了 `SENTRY_DSN` 的：在 **staging** 触发一条 error 级日志（例如把 `STRIPE_SECRET_KEY` 临时改错后发起一次银行卡支付：建会话失败 → 50001，5xx 记 error），Sentry 后台能看到；**这一步同时验证 envelope 省略 `length` 是否被接受**（`server/src/adapters/sentry.ts` NEEDS VERIFICATION）。⚠️ 4xx 记的是 warn，不会上报——别用 404 / 40902 之类去测。
- [ ] 配了邮件的：用一张测试订单走到"已发货"，`contact_email` 收到信；日志 `order_mail_sent`。
- [ ] 手动触发一次每日作业（Render cron 的 "Trigger Run"），然后在管理端「运营日志」看到"最近一次对账"时间更新。

### 1.5 开张前的业务配置（全新库，空库上线演练 2026-10-12 实测）

迁移跑完后，库里只有 4 个默认分类（美妆护肤 / 生活百货 / 厨房餐具 / 食品）和一个开放国家（美国）。**运费表、汇率、商品、Banner 全是空的**，此时买家报价会得到"运费不可计算"。按下面的顺序做，每步做完再做下一步：

1. **运营配置 → 运费分档**：录入承运商的全部档位并保存。
2. **运营配置 → 汇率**：`DISPLAY_CURRENCIES` 里的每个外币（默认 CNY、USD）各录一条。银行卡按美元收款，没有 USD 汇率就无法发起付款。
3. **商品管理**：新建商品、上传图片、上架、补库存。
4. **审核期专有**：服务启动时就必须给 `REVIEW_SKU_ID`，而全新库里还没有商品。所以：
   1. 首次部署先填一个占位值（如 `review-sku-tbd`），服务能起来，但审核期内谁都下不了单；
   2. 登录后台，建好审核测试商品（≥1 日元、上架、有库存），从商品编辑页的地址栏复制它的编号；
   3. 把编号写进 `REVIEW_SKU_ID`，重启 API。
5. 重启后看启动日志：
   - `launch_ready` = 三项前提齐了；
   - `launch_not_ready` 会逐条列出还缺什么（运费表、哪种汇率、审核商品不存在 / 没上架 / 库存为 0），同一条也会进每天的对账，显示在「运营日志」页。

## 2. 审核期（首版提审前后）

审核期的唯一目标：审核员能下单、能看到完整流程，**且不产生任何真实扣款**。

1. API：`REVIEW_MODE=on`、`PAYMENT_CHANNELS=mock`、`REVIEW_SKU_ID=<≥1 円的审核测试商品 id>`、`MOCK_CALLBACK_SECRET`（≥32 位，且不同于 `JWT_SECRET`），**以及 `REVIEW_MODE_UNTIL=<审核期截止日，YYYY-MM-DD>`**。
2. 只有 `REVIEW_SKU_ID` 那件商品能下单；mock 付款单标 `is_test = true`，管理端列表默认不显示（勾选「含测试单」可见）。
3. 审核备注里写明测试商品与 mock 支付路径（界面上不出现"审核 / 测试"字样，AJ-244）。
4. ⚠️ **`REVIEW_MODE_UNTIL` 到期后服务会拒绝启动**（A7 / AJ-378）。这不是惩罚，是最硬的一道提醒——告警通道（Sentry / 告警邮件，生产至少配一个）能报临期，但人未必当天看。届时二选一：
   - 审核还没过 → 把 `REVIEW_MODE_UNTIL` 往后挪（一行配置，重启即恢复）；
   - 审核已过 → 走下面第 3 节切正式。
   临到期 3 天起，每日对账会报一条 `review_mode_closing`；真过期了（进程一直没重启的情况）报 `review_mode_expired`，两者都会进运营告警邮件。

## 3. 审核期 → 正式

按顺序执行，每一步完成再做下一步：

1. **先接通真实通道**：Stripe live 密钥 + webhook secret 配好（`STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET`），`CHECKOUT_BASE_URL` 已是正式静态站地址。
2. **切开关**：`REVIEW_MODE=off`、`PAYMENT_CHANNELS=stripe`（去掉 `mock`——生产留着 mock 会被启动校验拒绝）。保存后 Render 会重启 API。
   - 顺手把 `REVIEW_MODE_UNTIL` 与 `MOCK_CALLBACK_SECRET` 从控制台删掉（留着不报错，但会让下一个人以为审核期还没结束；`MOCK_CALLBACK_SECRET` 在生产未启用 mock 时会被拒绝启动，见 `config.ts` 三审 S1）。
3. **审核期测试单**：不用手动处理。每日作业 `archive_test_orders` 会把付款满 `TEST_ORDER_ARCHIVE_HOURS`（默认 24）小时的测试单迁为已取消并回补库存（事件 note = `test_archived`）。想立刻清掉：手动触发一次每日作业。
4. **核对**：
   - [ ] 首页任意商品可下单（不再限 SKU）；支付页只出现银行卡；
   - [ ] 用一张真卡做一笔小额订单 → 回调落账 → 管理端全额退款 → Stripe 后台看到退款；
   - [ ] 第二天早上「运营日志」的对账无异常（或异常都能解释）。

## 4. 回滚

### 4.1 代码回滚（最常用）

Render 控制台 → 服务 → Deploys → 选上一个绿色部署 → **Rollback**。静态站在 Cloudflare Pages → Deployments 里同样可回滚。

⚠️ **迁移不会随代码回滚**：`preDeployCommand` 只往前跑。回滚前先看这次部署带了哪些迁移（`migrations/` 新增的文件）：

- 只加列 / 加表 / 放宽约束的（如 026、027、028）：旧代码不读新列，**直接回滚代码即可**，不动库。
- 文件头标了 `@breaking` 的（收紧约束、删列等，由 `test/lint/migrations.lint.test.ts` 强制标注）：先读它的 `@breaking` 说明再决定；需要时在**确认无新数据依赖**后执行 `npm run db:migrate:down`（每次退一步）。

### 4.2 配置回滚

环境变量改错导致起不来：日志第一屏就是 `config.ts` 的中文拒绝原因，改回去保存即可（Render 自动重启）。

### 4.3 数据恢复

误删 / 误改业务数据：用 Render Postgres 的备份 / 时间点恢复到**新库**（可用性取决于实例套餐，首次部署时确认，见 §6），核对后再迁回需要的行。⚠️ 审计表（`order_events` / `admin_audit` / `reconciliation_runs`）是 append-only，不能就地改——这是设计，不是故障。

## 5. 日常

| 场景 | 去哪看 / 做什么 |
|---|---|
| 对账有异常 | `ALERT_EMAIL` 收到告警信（按日一封）→ 管理端「运营日志」看取样 id → 订单页按单号搜 |
| 服务报错 | Sentry（配了的话；每分钟最多上报 30 条）→ 用日志里的 `trace_id` 串起整条请求 |
| 缺一件 / 破损 / 完成后售后 | 订单详情「部分退款」：按支付币种填金额（美元填 10.50）+ 原因，两步确认；处理中或结果未知的一笔点「同步」。⚠️ **不要去 Stripe 后台手工退**——库里不会记账，之后整单退款会被机构拒 |
| 买家说"付了款单却关了" | 订单详情事件里有 `late_paid` → 订单列表行"退款"按钮可用 → 全额退款（不回补库存） |
| 价格录错 / 库存错乱，要立刻止血 | 管理端「运营配置」最上面「暂停接单」（填原因、两步确认，立即生效）：报价 / 下单 / 付款全部拦住，回调、退款、发货照常。改正后点「恢复接单」。⚠️ 没有自动到期，记得关 |
| 误拉黑了买家 | 管理端「风控」页底部「已拉黑用户」→ 解除拉黑（填原因）。拉黑时被取消的订单不会恢复，请买家重新下单 |
| 管理员忘记口令 / 被锁 | `npm run admin:password -- <邮箱> --yes`（同时解除登录锁定） |
| 新增运营账号 | `npm run admin:create -- <邮箱> --yes`，然后 `npm run admin:totp -- <邮箱> --yes` 开通手机验证（生产不开登不进，AJ-442） |
| 管理员换手机 / 手机丢了 / 登录页说"还没开启手机验证" | `npm run admin:totp -- <邮箱> --yes`（本人在场录进新手机；旧密钥随即作废） |
| 管理员离职 | `npm run admin:revoke -- <邮箱> --yes`：撤掉管理员权限、作废他所有会话、清除手机验证密钥，并写审计。**最后一个能登录的管理员撤不了**——先 `admin:create` + `admin:totp` 建好接手的人再撤 |
| 导出报关 / 采购清单 | 管理端订单页顶部三个导出按钮（每次导出写审计） |
| 每月对一次钱（AJ-387 / P2-9） | 管理端导出「订单总表」（当月 paid 及以后状态）↔ Stripe 后台 Payments / Payouts 报表：逐笔比单数与金额，差异逐单查。自动回填实收 / 手续费在 Stripe 测试模式联调时做 |
| 运单号录错 | 订单详情「订单修正」→「修改运单号」（填原因、两步确认）；会按新单号给买家重发一封发货邮件 |
| 未付款的单要作废（价格录错等） | 订单详情「订单修正」→「取消订单（未付款）」；已付款的走退款 |
| 改库存时提示"被别人改过"（40914） | 打开编辑页期间有人下单扣了库存：刷新后按最新库存重填 |

### 5.1 发布与迁移纪律（AJ-386，第三轮缺口 P2-17 / P2-19 / P2-20 / P2-28 / P2-29）

- **发布避开 JST 03:00–03:30**：每日作业 03:10 触发、整轮一个事务；部署重启会把它杀掉回滚，cron 却记成功，
  要 26 小时后心跳告警才看得见（P2-19）。撞上了就在控制台手动触发一次 cron。
- **服务起不来先看迁移**：启动时校验"库里执行过的迁移 ⊇ 代码带的迁移"，缺就拒启并点名缺哪条（AJ-385）。
- **上线后再加约束 / 索引**：CHECK 用 `NOT VALID` + 之后单独 `VALIDATE`；索引用 `CREATE INDEX CONCURRENTLY` 且单独成一条迁移
  （node-pg-migrate 默认整条迁移包事务，CONCURRENTLY 进不了事务）。现有 002–033 都是上线前写法（P2-29）。
- **不要在生产跑 `npm run db:seed`**：它会清掉管理员与汇率（只有 `npm run dev` 会补）。
- **审核模式到期只在启动时拦**（P2-20）：过了 `REVIEW_MODE_UNTIL` 进程不重启就继续接 mock 单，每日邮件会报；
  到期前主动改配置并重启。休假前确认 `REVIEW_MODE=off`、停售开关已关。
- **数据库连接池 10**（P2-17）：发起支付在事务内调 Stripe（最长 6 秒）；Stripe 变慢时 10 个并发即占满全池，
  `/readyz` 会跟着变慢。先观察，`readyz` 告警或 p95 明显升高再加池（池大小写在 `server/src/adapters/db.ts`，不是环境变量）或改两阶段发起。
- **邮件 / 告警信发送失败不重试**（P2-28）：单封失败只记 `order_mail_failed` 错误日志；Sentry / 日志告警要盯这个事件。

## 7. 预发布（staging）临时环境方案（第 27 项，2026-10-11）

**目的**：上线前在**公网**上把本机测不到的东西演练一遍——真实 https 域名、Render 反代层数（`TRUST_PROXY_HOPS`）、Stripe 回调能否从公网打进来、每日作业、告警邮件、管理员手机验证。演练完可以删掉，所以叫"临时"。

**形态**：在 Render 上按 `render.yaml` 再建一套（API + 最小档 Postgres + 管理端静态站），静态站用 Cloudflare Pages 的预览部署。**库必须是独立的一个**，绝不连正式库。

| 配置项 | staging 取值 | 说明 |
|---|---|---|
| `NODE_ENV` | `staging` | 决定下面几条闸门 |
| `PAYMENT_CHANNELS` | `stripe` | 用 Stripe **测试模式**密钥（`sk_test_…`），见第 8 节 |
| `MOCK_AUTO_CONFIRM` / `WECHAT_DEV_LOGIN` | **不配** | staging 配了会拒启（公网上等于无密码登录 / 免费下单） |

| `SUPPORT_*` / `LEGAL_BASE_URL` | 照生产填 | 规则 9c 只对生产强制，但 staging 就是用来提前撞问题的 |

## 8. Stripe 测试模式演练步骤（真通道、假钱）

**A 段：本机（现在就能做）**

1. Stripe 后台切到 **Test mode** → 开发者 → API 密钥，复制 `sk_test_…` 填进本机 `.env` 的 `STRIPE_SECRET_KEY`；`PAYMENT_CHANNELS=mock,stripe`。
2. 按 `docs/dev/stripe-listen-cloudflared.md` 起 `stripe listen --forward-to localhost:3000/api/v1/pay/callback/stripe`，把它打印的 `whsec_…` 填进 `STRIPE_WEBHOOK_SECRET`，重启 `npm run dev`。⚠️ 每次重开 listen，`whsec` 都会变。
3. 小程序开发者工具里下单 → 支付页选银行卡 → 复制链接到浏览器，用 Stripe 公开的测试卡号付款：

   | 场景 | 卡号（任意未来日期、任意 CVC） | 期望 |
   |---|---|---|
   | 成功 | `4242 4242 4242 4242` | 回调落账，订单"已付款"，收到付款邮件（配了邮件时） |
   | 被拒 | `4000 0000 0000 0002` | 支付页失败，订单仍"待付款"，可换卡重付 |
   | 拒付 | `4000 0000 0000 0259` | 先成功落账，随后回调 `charge.dispute.created` → 订单带拒付限制，发货 / 退款按钮被拦 |

4. 管理端：对成功那单做**部分退款**、再**全额退款**→ Stripe 后台 Payments 里看到对应退款；订单最终"已退款"。
5. 让一单**不付款等它过期**：Stripe 会话随后失效（回调 `checkout.session.expired`），订单"已过期"。
6. 每一步都记下订单号与时间，对照管理端订单时间线、「运营日志」与服务日志里的 `trace_id`。

我们处理的 Stripe 事件（`server/src/adapters/payment/stripe-checkout.ts`）：`checkout.session.completed` / `async_payment_succeeded` / `async_payment_failed` / `expired`、`payment_intent.succeeded` / `payment_failed` / `canceled`、`charge.refunded`、`charge.dispute.created` / `closed`。在 Stripe 后台建 webhook 端点时**只勾这些**。

**B 段：staging（有公网域名后）**

1. Stripe 测试模式 → Webhooks → 新建端点 `https://<staging-api 域名>/api/v1/pay/callback/stripe`，勾上面那组事件；端点的 Signing secret 填进 staging 的 `STRIPE_WEBHOOK_SECRET`，重启。
2. 在 Stripe 后台对该端点"发送测试事件"→ 服务日志里有验签通过的记录（验签失败是 40103，先查 secret 是否填对）。
3. 有 AppID 后用体验版小程序重复 A 段第 3–5 步；没有 AppID 时只做第 2 步（证明公网回调链路通）。
4. 切正式时**换成 live 密钥与正式端点**（第 3 节）——测试模式的密钥与 webhook 端点不要带进生产。

## 9. 日志外送（log drain）配置步骤

**现状**：服务日志只写标准输出，留在 Render 面板里（保留期由平台套餐决定，不能按 `trace_id` 长期检索）。审计与用户行为两条流已落库，不受影响。落点选型见 AJ-139：**Axiom 为默认，Better Stack 为唯一备选**。

1. 在 Axiom 建一个 dataset（如 `waselect-api`）与只写权限的 ingest token。
2. Render 控制台 → 工作区设置里的 **Log Streams**，按 Axiom 文档给出的接收地址与 token 填写（具体字段以平台当时的界面为准，首次配置时把实际步骤补回本节）。代码与 `render.yaml` 不用改。
3. 验收（AJ-139 四条，任一不满足就切 Better Stack）：
   - [ ] 在小程序里点一次商品详情，用响应头里的 `x-trace-id` 在 Axiom 搜到这次请求的全部日志；
   - [ ] 保留期 ≥ 90 天；
   - [ ] 免费额度覆盖当前日志量（Render 面板可看每天大概多少行）；
   - [ ] 日志里没有电话、邮箱、地址明文（脱敏是在服务端做的，外送只是转存）。
4. ⚠️ **隐私政策**：日志送到境外服务商，属于 APPI 第 28 条"向境外第三方提供"，隐私政策的境外提供清单要加上 Axiom——这一条要合伙人或法务确认后再上线外送。

## 10. 什么时候需要多台服务器（多实例触发条件）

**现状**：API 固定**单实例**（`render.yaml` `numInstances: 1`，`test/config/render-env.unit.test.ts` 钉住——改成 2 测试会先红）。下面几处状态只存在于**一个进程的内存里**，多开一台不会报错，只会**静默失效**：

| 组件 | 文件 | 多实例后会怎样 | 扩容前要做什么 |
|---|---|---|---|
| ① 限流计数 | `server/src/adapters/rate-limit-memory.ts` | 每台各数各的，"5 次 / 15 分钟"变成"5 × 台数" | 换成库表或 Redis 计数 |
| ② 身份缓存（拉黑 / 改密 / 退出的即时作废） | `server/src/adapters/identity.ts` | 只作废收到请求的那一台，其它台上旧凭证最多再用 60 秒 | 缓存改短或去掉，或换共享缓存 |
| ③ 常驻调度器 | `server/src/adapters/scheduler.ts` | **互斥不会坏**（锁在 Postgres 里），只是每台都空转抢锁 | 可以不改；或只让一台跑调度 |
| ④ 模拟支付会话 | `server/src/adapters/payment/mock.ts` | 只在审核期用；换台后会话找不到 | 审核期保持单实例即可 |

管理员登录锁（同账号连错锁定）存在库表 `login_attempts` 里，多实例下仍然正确。

**触发扩容的信号**（任一持续出现、且已排除慢查询 / 慢的外部调用）：
- 平时流量下 `/readyz` 变慢或 p95 延迟明显升高；
- Render 面板 CPU 长时间 > 70%，或内存接近套餐上限（当前 512 MB）；
- 大促 / 推广前预计流量是平时的数倍。

**扩容顺序**：先**升单实例的套餐**（最省事，不触发上表任何问题）；确需多台时，先改 ① ②，再改 `numInstances`（同时更新那条测试的预期与理由）。

## 11. 数据库迁移为什么"只前进"

- 部署时 `preDeployCommand: npm run db:migrate` **只执行 up**；代码回滚**不会**把库退回去（第 4.1 节）。
- 服务启动时校验"库里执行过的迁移 ⊇ 代码带的迁移"（AJ-385）：**新代码 + 旧库**会拒启并点名缺哪条；**旧代码 + 新库**能正常启动——所以回滚代码是安全的，前提是迁移本身向后兼容。
- 因此写迁移的规矩：**只加不删**（加列、加表、放宽约束）。要删列 / 收紧约束时拆成两次发布：先发"不再读写它"的代码，确认稳定后再发删除它的迁移，并在文件头标 `@breaking`（`test/lint/migrations.lint.test.ts` 强制）。
- `npm run db:migrate:down` 只在**确认没有新数据依赖**时手动执行，一次退一步；**生产不要**为了"配合回滚"去跑 down。
