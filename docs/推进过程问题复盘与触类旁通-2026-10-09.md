## 一、统一结论

1. **核心问题：教训写下来了，但不会自动生效。** 同一个坑被同一个主体反复踩，复发链见第三节，每条都有出处可查。两份报告在这一点上结论一致：WB 的"不能再犯"操作律、我的 §2 教训，都还是散文，不是会失败的检查。
2. **"不核实就下结论"这一类，两份报告的作者当天都在犯。**
   - 09-26 复盘就已自承此类错误。
   - 10-09 我的第一版总结把代理的计数和推断说成结论，用户指出后才逐条核实。
   - WB 报告当天也有 2 条结论回到代码后不成立（#4 脏汇率致 500、ProductsPage 注释仍未修），见 4.2。
   - 这说明"报告是照片不是直播"（WB P-13）对写报告的人自己同样适用。
3. **根因统一为 12 类**（第二节）。单测和门禁拦不住的主要是三类：
   - 界面渲染与"用户看得见"；
   - 跨端数据形状；
   - 业务处理"有人负责却没人看得到"。

   最后这一类在 WB 报告里没有被识别，是本次融合补上的。
4. **现存问题合并去重后见第五节，每条带位置与验证程度。** 最重的几条：
   - 售后申请运营无入口、自动签收不避开售后；
   - 补发邮件可能连带挡掉实时邮件、放弃时不留痕；
   - 迟到付款 48 小时后不再被报出；
   - 拉黑用户的已付单在发货环节没有任何标记；
   - 小程序关键信息文字对比度 2.07–2.18:1。
5. **修复动作本身在制造同类问题**（第六节）。今天就有 4 例：
   - 文案修复造成自指；
   - 标题边距修复漏了一页；
   - 补发机制可能触发限流熔断；
   - 改了小程序 `app.js` 却没在模拟器完整编译后看一眼就提交。
6. **记录系统本身在失真**：§2 编号重号 / 缺号；§3 标题与内容不符；多份规范文档里的"当前 N"已过期（第五节 5.7）。

## 八、统一操作律（融合 WB 第六节与本文，按能否变成检查排序）

**能变成会失败的检查（应优先做成检查，而不是再写一遍）：**
1. gate 自己把退出码写进日志尾行，交付只认那一行与**通过数**。
2. 自定义组件标签上禁止布局 class（按多行解析）。
3. 请求体 / "不带某键"一律 `toEqual`；长度上限边界表强制含非 BMP 字符。
4. 手写 API fixture 过契约 schema；契约补响应形状校验。
5. 并发测试就位信号走 `pg_stat_activity`，禁止 sleep。
6. 文档里的"当前 N"接回真源或加对账断言；§2 编号唯一性 lint。
7. 副本必须配等值测试；提交前脚本直接调用 `gate:fast`，不抄步骤。

**机器化不了、必须作为人工检查项写进 H 表：**
8. "有 / 无 / 几处"的断言带证据命令与截至 commit；grep 空结果用第二种方式复核；按报告行动前复核 HEAD。
9. 建议出口前过约束图：拒启链、部署依赖链、约束七分流、第三方默认不做。
10. 新护栏注回验证，并逐条确认红的是哪一条。
11. 修一处之后按形态全仓搜一遍（问"明天再来一个同类型的，还管用吗"）。
12. 凡"由运营判断 / 人工处理"的状态，写清谁、从哪里、多久内会看到。
13. 豁免 / 绕行逐条写补偿控制并问聚合暴露面；同一业务日的所有产出物口径一致。
14. 小程序 UI 或 `app.js` 改动：完整编译后在模拟器截图验收，再提交。
15. 子代理 / 协作者的结论只当线索，写进文档前亲自抽查；每条标验证程度。
