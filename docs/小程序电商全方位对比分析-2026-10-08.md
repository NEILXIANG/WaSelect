## 一、结论先说

1. **WB 报告选的坐标系是对的**：日本选品代购、DDP 直邮美国、中文界面——对标 Yamibuy / 小红Mall 而不是淘宝京东，
   "物流焦虑""信任"权重高于促销。这一判断我完全同意，也是本文的出发点。
2. 但它的**能力盘点约三分之一已过时或写时就不准**：相关推荐、包税明示、购物车全选、骨架屏、再次购买、选数量、行为埋点
   今天都已有；详情参数表、州下拉、订单详情的退款信息、后台销售工作台、`pages/comp` 已排除打包——写报告时就存在；
   `pages/design` 根本不存在。照它的 P0 清单排工作会重复劳动。
3. 去掉过时项后，**真正的差距集中在四件事**：支付闭环（微信支付真接入）、主动通知（订阅消息）、售后入口、物流可见性。
   前两件被 **AppID** 卡住，后两件不需要 AppID、现在就能做。

## 二、项目特点（决定什么该学、什么不该学）

| 特点 | 含义 |
|---|---|
| 代购（买手在日本下单采购） | 付款到发货有几天空档；缺货是常态 → "采购中"进度、缺货全额退款说明比秒杀重要 |
| DDP 直邮美国、价内含关税 | "会不会被海关再收钱"是下单前最大顾虑 → 包税要说出来（已做） |
| 中文界面、美国地址 | 用户是在美华人 → 中文 OK，地址要符合 USPS 习惯 |
| 单商户、精选（20–200 SKU 量级） | 搜索、多级分类、复杂筛选的收益低；"为什么值得买"的编辑内容是核心竞争力 |
| 审核期 / 无 AppID | 微信支付、订阅消息、原生客服、分享卡片可点性都要等 AppID |
| 一人 + AI 维护 | 每加一个模块都是长期维护成本 → 优先"小而稳" |

## 四、真正的差距（按对本项目的价值排序）

### 不依赖 AppID、现在就能做

1. **售后入口（最小闭环）**：订单详情加"申请售后"（选原因 + 说明 + 可选图片）→ 落库 → 后台订单详情出现工单、运营处理后买家可见。
   代购场景"出了问题找得到人"是信任底座；现在只能去"我的"翻客服微信。
2. **物流关键节点**：不接第三方轨迹 API 也能先做"发货 → 到达美国 → 派送中 → 签收"由运营或承运商回执更新的节点（或日本邮便的官方查件链接已有，先把"复制"改成更显眼的"查看物流"引导）。
3. **邮件不丢**（工程分析 E-1）：在订阅消息上线前，邮件是唯一主动通知，"发信记录 + 补发"比任何新功能都优先。
4. **首页 / 购物车 / 我的 下拉刷新**：三页还没开（`order` / `pay` / `order-detail` 已开）。
5. **后台漏斗视图**：埋点已在采集，后台只缺一页"首页 → 详情 → 加购 → 结算 → 支付"的转化表——没有它，采集的数据没人看。

### 依赖 AppID（AppID 一到就排）

6. **微信支付 in_app**：服务端通道注册表已留好位置（`server/src/adapters/payment/channels.ts:274`），小程序 `requestPayment` 分支已写（`pages/pay/index.js:414`）。
7. **订阅消息**：发货 / 退款 / 签收三个模板；与邮件并行，不替代。
8. **分享**：首页 / 分类可分享 + 朋友圈（`onShareTimeline`）；海报生成放后。
9. **原生客服**（`open-type="contact"`）。

### 看数据再说

10. **收藏 / 心愿单**：代购决策周期长，有价值；但先看埋点里"浏览多次未加购"的比例。
11. **到货通知**：缺货是常态，配合订阅消息做。
12. **邮编带出城市 / 州**：一张 ZIP 前缀表即可；但州下拉已在，收益中等。

### 5.4 不建议照搬的

- **社会证明（销量 / 评价）**：精选代购初期单量小，"已售 3 件"反而是负面信号；评价需要审核与申诉流程，维护成本高。
  先用"为什么值得买"与产地匠人承担信任，单量起来后再上"真实买家评价"。
- **优惠券**：引入后结算、退款分摊、对账都要跟着改（部分退款的金额分摊已经够复杂），且与"克制可信"调性有张力；
  获客期先用邮件 / 分享，券放到复购数据出来后。
- **独立搜索页**：见 5.3。
