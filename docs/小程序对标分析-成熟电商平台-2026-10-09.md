日期：2026-10-09　基线：`main@ad711b0`（`miniprogram/` 最近一次改动在 `6b5a4d1`，工作区无未提交改动）
性质：**只分析、不改代码**。属轻量档文档（CLAUDE.md「风险分级」），不涉及自主决策入档；§8 的问题留给用户拍板。

## 0. 一页结论

我们的小程序**"链路通、守得住钱、说话诚实"**：下单—支付—确认收货全链路在三端模拟里跑通（`docs/三端联动UI交互模拟-2026-10-08.md` S1），
价格只信服务端报价、错误态三段式带报障码、关税口径与发货承诺在详情页明示、缺货整单退款在付款前说清——
这些"出事故的地方"比多数小店小程序严谨。

差距集中在**"信任感"与"付款之后"**两段——恰好是跨境代购最吃重的两段：

| 差距 | 成熟平台（尤其跨境）怎么做 | 我们现在 | 影响 |
|---|---|---|---|
| 详情页的**信任区** | 价格下方一排保障标签（正品 / 直邮 / 时效 / 售后），点开有说明；店铺 / 来源信息；客服入口常驻 | 只有关税口径与"N 个工作日内发出"两行；首页卡片上那句"为什么值得买"与产地/匠人**到了详情页反而不见了** | 转化：买家决定前最需要的那句话缺席 |
| 付款后的**"现在到哪了"** | 订单详情顶部一条进度条 + "下一步会发生什么"；物流轨迹内嵌；订阅消息推送 | 状态是一个词（`paid` 显示"已付款"），时间线是纯列表；物流要复制链接去浏览器查；**没有下拉刷新**；推送未做 | 售后成本：代购从付款到发货要几天，"已付款"挂几天会被读成"卡住了" |
| **通知渠道** | 订阅消息 / 短信 / App 推送至少一条必达 | 只有邮件，且结算页邮箱**选填**——不填即零通知（第三轮评估 §3 已记） | 售后成本 + 信任 |
| 订单列表 | 状态页签（待付款 / 待发货 / 待收货 / 售后）+ 每行商品缩略图与下单时间 | 单号 / 状态 / 合计三项；无页签（服务端其实已支持 `status` 过滤） | 订单多了以后找单难 |
| 通用交互 | 下拉刷新、骨架屏、图片懒加载、底部固定购买栏、购物车角标在 tabBar | 均无（`.ws-skeleton` 样式已写好但没有页面用） | 体感"慢 / 不像正经店" |

**建议**：不追功能齐全。上线前（P0）只做 6 件、合计约 3 天，全部是**仅前端或前端为主**、且不依赖 AppID 的改动：
**邮箱提醒（或必填）→ 详情页补回"为什么值得买" → 详情页保障区 → 订单状态代购化文案 → 订单页下拉刷新 → 订单号复制与客服就近**。
订阅消息、微信支付、真机验证三件事被外部阻塞卡住，代码侧已有接口，§7 单列。

## 2. 跨境代购的特殊性（决定了哪些"标配"该学、哪些不该学）

| 特殊性 | 对体验设计的含义 |
|---|---|
| **付款 → 采购 → 发货之间有几个工作日空档**（"付款后 N 个工作日内发出"，N 来自 `SHIP_WITHIN_BUSINESS_DAYS`） | 国内平台的"已付款 → 次日发货"心智在这里不成立。状态文案与进度表达必须解释这段空档，否则售后咨询集中在这里 |
| **国际运输时间长、跨时区**（EMS 日本 → 美国；时间一律按 JST 显示并标注） | 需要"预计送达"区间与分段说明；所有时刻标时区（已做） |
| **关税 DDP 口径**（D-32：商品价含美国关税，运费按重量分档单列） | 这是跨境平台的一大卖点（"到手无额外税费"），我们说了，但只是一行灰字；可以升格为保障标签 |
| **扣款币种因通道而异**（银行卡 USD、微信支付 JPY，D-69①；副行 USD / CNY 恒为估算） | 买家在结算页还不知道自己会被扣多少美元——直到支付页才看到。跨境平台通行做法是"结算页即显示将以 X 币种扣款约多少" |
| **银行卡在浏览器完成**（D-49：短链 → Stripe Checkout） | 支付是全链路最长的一跳，流失风险最大；回到小程序后的状态确认已做（支付页 onShow 查状态） |
| **收件信息必须英文**（面单） | 中文用户第一次填会撞校验；需要事先说明 + 示例，而不是事后报错 |
| **买家多为在美华人**（中文界面，路线图明确不做多语言） | 熟悉淘宝 / 京东的交互惯例（订单页签、确认收货、申请售后、联系客服），这是可以直接借用的"肌肉记忆"；但对"关税、清关、美国州码"需要中文解释 |
| **单店、单仓、目录小、靠选品与编辑判断** | 卖场式能力（复杂筛选、排序、千人千面推荐、营销会场）收益低；编辑大卡与"为什么值得买"是差异化，应强化不应稀释 |
| **退货寄回不经济**（美国寄回日本的运费常高于货值，管理端对标文档 §8-4） | 售后以"拍照核实 → 部分退款 / 补发"为主，不需要国内式"退货退款 + 上门取件" |

## 3. 按买家旅程对标

每条建议编号 `M-xx`，标注 **影响**（转化 / 信任 / 售后成本）、**改动面**（仅前端 / 需服务端接口 / 需契约变更）、**工作量**（粗估）、**批次**。
批次定义：**P0** 上线前；**P1** 上线后一个月；**P2** 按触发条件立项；**P3** 暂不做。

### 3.1 首页与发现

| 能力 | 成熟平台通行做法 | 我们 | 判断 |
|---|---|---|---|
| 首屏结构 | 搜索框置顶 → 轮播 / 活动位 → 金刚区（分类图标）→ 商品流；国内平台多为**双列瀑布流**，独立站与精品电商多为**单列大图** | 字标 → 搜索 → 快捷按钮 → 轮播 → 分类 tab → 单列编辑大卡 | 结构完整；单列大卡与品牌定位一致（见 §8-Q6） |
| 购物车入口 | tabBar 购物车图标带**数字角标** | tabBar 无角标；首页另有"购物车 · N""我的"两个按钮，与 tabBar **重复** | 小缺口 |
| 分享 | 首页与商品均可分享到聊天 / 朋友圈 | 仅商品详情可分享到聊天 | P2 |

### 3.3 商品详情（本轮最大缺口）

成熟平台（尤其跨境类）的详情页骨架：

```
┌ 图片轮播（主图 / 细节 / 包装 / 实拍） ─────────┐
├ 价格（主币种大字）  ≈ 换算币种小字             │
│ [正品保障] [日本直邮] [含关税] [N 日内发货] ›  │ ← 保障标签条，点开是说明浮层
├ 标题 / 卖点一句话                            │
├ 发货与时效：日本 → 美国  预计 X–Y 天送达 ›     │
├ 规格 / 产地 / 重量                           │
├ 商品故事 / 编辑推荐 / 详情图                  │
├ 售后说明（缺货退款、破损处理、联系客服）        │
└ ─────────── 底部固定栏 ───────────────────── ┘
  [客服] [购物车·3]      [加入购物车] [立即购买]
```

| 能力 | 成熟平台通行做法 | 我们 | 判断 |
|---|---|---|---|
| 卖点 / 编辑推荐 | 标题下一句卖点或"推荐理由" | 首页卡片有"为什么值得买"与产地/匠人，**详情页没有** | **P0**：数据已下发，前端漏取 |
| 价格展示 | 主币种大字 + 换算小字；跨境类常注明"含税"或"税费另计" | 円大字 + ≈USD · ≈CNY；"价格含美国关税"一行灰字 | 口径对，**表达弱** |
| 信任要素 | 保障标签条（正品 / 直邮 / 包税 / 售后），点开说明；跨境类常写明货源与发货地 | 只有关税与发货时限两行；"日本采购、日本直发"无明示；缺货退款说明只在结算页与订单详情出现 | **P0** |
| 时效 | "预计 X 月 X 日前送达"或"X–Y 天送达"；跨境类给区间 | 只有"付款后 N 个工作日内发出"（发出≠送达） | **P0**（数字需实测） |
| 购买栏 | **底部固定**，含客服 / 购物车 / 主次两个按钮 | 流式，长描述把按钮推到屏外 | P1 |
| 客服 | 底部栏常驻 | 详情页无客服入口 | 并入 P0 保障区 |
| 库存表达 | "仅剩 N 件"、"已售罄 / 到货提醒" | 详情只有"已售罄"（首页卡片有"仅剩 N 件"） | 一致性小缺口，P1 顺手 |
| 评价 / 晒单 | 国内平台核心模块 | 无 | 不建议早期做（§6） |

- **M-02** 详情页补回"为什么值得买 / 产地匠人 / 标签"，版式与首页卡片同源。影响：**转化**；仅前端（`detail/index.vm.js` 取 `why` / `maker` / `tags`）；0.5 天；**P0**。
- **M-03** 详情页"购买保障"区：价格下一排保障标签（如"日本采购 · 日本直邮""价格含美国关税""付款后 N 个工作日内发出""缺货整单全额退款"），点开为说明（复用已有 `DUTY_NOTE`、`STOCK_REFUND_NOTE`、条款页入口）；下方"运输时效参考"与"有疑问？联系客服"（复用 `GET /support`）。
  影响：**信任 + 售后成本**；以前端为主；**运输时效数字必须由服务端配置下发**（约束五：不写死；可加到 `Product` 或 `/support` 一个可选字段 → 契约变更，小）；1–1.5 天；**P0**。
  依赖：EMS 实际时效【需实测确认】——没有实测数前**只写分段说明**（"日本采购 1–N 个工作日 → EMS 国际运输 → 美国派送"），不写天数；退货政策摘要只写已定的部分（缺货全额退款），正文待律师定稿（剩余清单 二）。

- **M-13** 底部固定购买栏（客服 / 购物车角标 / 加入购物车 / 立即购买），并统一处理 tabBar 页与非 tabBar 页的底部留白。影响：转化；仅前端；0.5 天；**P1**。
- **M-34** 收藏 / 心愿单 + 售罄到货提醒。影响：转化（复购）；需服务端 + 契约；2–3 天；**P2**，触发：售罄商品常态化或有复购数据。

## 6. 不建议照搬的

| 做法 | 谁在做 | 不照搬的理由 |
|---|---|---|
| **拼团 / 砍价 / 助力** | 拼多多为代表 | 依赖社交裂变与低客单高频；我们是高客单、低频、靠信任的跨境代购，且每单都要人工采购——拼团带来的突发单量反而压垮采购与发货；对账、退款（成团失败退款）复杂度成倍 |
| **直播 / 短视频种草 / 社区笔记** | 淘宝直播、小红书 | 内容生产成本高、需要持续运营人力；小程序内直播还涉及额外资质与审核【需实测确认】。"为什么值得买"的编辑文案已是我们的轻量内容形态 |
| **优惠券中心 / 满减会场 / 秒杀** | 天猫、京东 | 早期增长靠选品与信任；券与满减会让"价格含关税"的定价口径与报价、退款（部分退款按比例摊券）都复杂一倍；D-69⑥ 的凑单策略只需"包邮阈值 + 满件优惠"两条，不需要券体系 |
| **积分 / 会员等级 / 签到** | 京东、天猫 | 复购数据不足以设计权益；还要处理积分负债与过期，属于提前设计 |
| **千人千面推荐 / 猜你喜欢** | 全部大平台 | 目录小（几十件量级），推荐算法没有发挥空间；首页按编辑排序已足够 |
| **评价 / 晒单** | 全部大平台 | 冷启动期没有评价时空模块反而减分；还涉及内容审核与虚假评价合规风险。单量稳定后可考虑"精选买家反馈"由运营录入 |
| **自助退款 / 退货寄回 / 上门取件** | 国内平台 | 跨境寄回不经济、无法上门核实；与管理端 §8-4 一致：只做"申请"，决定权在运营 |
| **独立购物车服务端同步、多端登录** | 大平台 | 单渠道（小程序）单设备，为此建服务端购物车是空投入 |
| **多语言（英文界面）** | 跨境平台 | 路线图已明确不做；目标买家是在美华人 |
| **toast 式反馈全面替换页内提示** | 国内平台惯例 | 我们刻意选择页内文字（可测、不依赖宿主时序，`wx-api.ts` @limitation 九）；体验差距很小，不值得推翻已有口径 |
| **双列瀑布流首页** | 淘宝、拼多多、小红书 | 卖场形态"先看图再看价"；我们的判断是"先看值不值"，`why` 需要横向篇幅（`home/index.wxml` 注释）。SKU 多了再评估（§8-Q6） |

## 8. 需要用户拍板的问题

> ✅ **拍板结果（用户 2026-10-09：「按照你的推进安排」——六项全部采用下列推荐；决策记录见 `docs/自主决策记录.md` AJ-402）**
>
> | # | 结论 |
> |---|---|
> | Q1 | 联系邮箱**改必填**：仅小程序前端校验，契约与服务端保持可选（订阅消息上线后可回调为选填） |
> | Q2 | 详情页**写**预计送达：上线前只写分段说明不写数字；首批 3–5 单实测 EMS 时效后，由服务端配置下发"约 X–Y 天（参考）" |
> | Q3 | **维持円为主**、≈USD / ≈CNY 为辅；结算页加"银行卡将以美元扣款约 $X"（M-16） |
> | Q4 | 买家侧状态**改代购视角文案**（M-06 进 P0），两套词表收进 `shared`（P1） |
> | Q5 | 应用内物流轨迹放 **P2**，触发条件：每周物流咨询 > 5 次或月单量 > 100；不引入第三方聚合服务 |
> | Q6 | 首页**维持单列编辑大卡**；在售 SKU > 100 时再评估 |
>
> **推进顺序**：管理端第二批 B → C → D 完成后，做本文 P0（M-01～M-06）。
> **进度**：P0 六项已完成（`2177c48` / `33a453e` / `41b97e5`，AJ-405；见 §5 末尾）。若上线日期先于第二批完成，P0 提前插队（它是"上线前"项，管理端第二批的触发条件是单量 > 20 / 天）。

**Q1　结算页联系邮箱：选填 + 强提醒，还是改必填？** —— **推荐：改必填（仅前端校验，契约与服务端保持可选）**
- 理由：订阅消息被外部阻塞，邮件是**唯一**能把"已发货 / 已退款"告诉买家的渠道；第三轮评估已指出"不填即零通知"。代购付款后有几天空档，零通知的买家几乎必然来问客服。
- 代价：少数不愿留邮箱的人会犹豫；需在说明里写清用途（APPI：收集时告知的目的与实际一致，现有说明已对齐）。
- 备选：维持选填，但提交前弹一次提醒（M-01 的弱版本）。订阅消息上线后可回调为选填。

**Q2　商品详情写不写"预计送达天数"？** —— **推荐：写，但数字由服务端配置下发，且先实测再填**
- 理由：跨境买家最关心"多久到"；只写"N 个工作日内发出"会被误读为送达时间。
- 做法：上线前先写分段说明不写数字；首批 3–5 单实测 EMS 时效后，在配置里填"约 X–Y 天"（标"参考"）。写错的承诺比不写更糟（与 FTC 发货时限同口径）。

**Q3　价格主显示币种：维持"円为主、≈USD · ≈CNY 为辅"吗？** —— **推荐：维持，另在结算页加"银行卡将以美元扣款约 $X"（M-16）**
- 理由：円是定价锚与记账币（D-32 / D-69 已定），微信支付将以円扣款；改 USD 为主会让同一件商品在不同日子显示不同"标价"。买家真正需要的是**付款前知道扣多少美元**，这一点用结算页预告解决，不必动主显示。
- 备选：对美国收件地址的买家以 USD 为主显示——需要契约与全部价格组件改动，且与 D-69 口径冲突，不推荐。

**Q4　买家看到的订单状态，是否改成代购视角文案（"已付款 · 日本采购中"等），并与管理端统一从 `shared` 取词？** —— **推荐：是（M-06 进 P0，词表收敛进 P1）**
- 理由：代购的付款—发货空档是最大的咨询来源；系统态直译"已付款"挂几天会被读成卡住。管理端可以保留运营视角的词（"待发货"），两套词表都放 `shared`，消除第三轮记的三处漂移。

**Q5　应用内物流轨迹（M-30）要不要做、何时做？** —— **推荐：P2，触发条件同售后申请（每周物流咨询 > 5 次或月单量 > 100）；优先自接承运商公开查询，不引入第三方聚合服务**
- 理由：上线初期"复制运单号 + 查件链接"能用；轨迹内嵌需要服务端定时抓取与解析，3–5 天投入。若要用第三方聚合查询服务，按项目前提默认"不做"，需你明确同意。

**Q6　首页是否维持"单列编辑大卡"，还是改成主流的双列网格？** —— **推荐：维持单列大卡；在售 SKU > 100 时再评估双列或"单列 / 双列切换"**
- 理由：目录小、靠"为什么值得买"建立信任，这是与大平台的差异点；双列网格会把 `why` 挤掉，回到"先看图再看价"的卖场逻辑。代价是首屏可见商品数少（约 1–2 件），用 M-14 去掉重复按钮可多出一些首屏位置。
