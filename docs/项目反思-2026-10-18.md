## 2. 做对了的事

1. **把"钱"当成最高风险来对待。** 金额用整数、状态机显式迁移、回调幂等登记、先落"退款中"再调机构、拒付限制、迟到付款凭据——这些设计在多轮独立审查里经受住了，到最后没有发现会多扣或多退钱的缺陷。对一个跨境支付项目，这是最重要的一件事，做对了。
2. **配置校验拒绝启动。** 生产开 mock、残留开发登录、密钥形状错、该成对的变量只配一半——服务直接拒启，并用中文说清缺什么。这类保护在上线当天最值钱，而且已经写好了。
3. **"缺陷注入"纪律。** 严格档改动要把缺陷注回去、确认测试会红。这条纪律多次抓到"测试写了但验不到"（外键索引被部分索引掩盖、反向断言永远为真）。
4. **把规则变成会失败的检查。** 契约漂移、环境变量键名、蓝图密钥、数据库备份进仓库、结构不变量……约束九"防复发机制优先"落地得很实在。
5. **决策留痕。** 每个取舍写清选项、依据、反向风险。半个月后回头查"为什么这么做"，答案基本都找得到。
6. **2026-10-05 的风险分级是一次正确的自我纠偏。** 当时已经意识到测试是源码的 1.5 倍、注释占四成、部署无人做，于是把最严的纪律收缩到钱和安全。方向对。

## 3. 主要问题

### 3.1 验证的方向是失衡的：本机验证做到了极致，真平台验证是零

所有测试、审计、模拟、走查都发生在一台 Mac 上。数据库是本机的，支付是 mock，小程序在开发者工具里，"Stripe 退款的 4xx 形态""回调限流下的重投""Cloudflare 302 是否保留查询串""测试号能不能登录"都是**按文档推断**。

后果不是"有风险"，而是**每多一轮本机审查，边际收益就更低，而真平台上那一类问题一条都没减少**。到第四、五轮复查时，发现的问题已经大多是"注释与代码不符""两个工具互相覆盖""上一轮修复引入的新问题"，真正会出事的缺陷没有了——但这并不说明系统可以上线，只说明本机能发现的东西已经发现完了。

判断：项目大约在 10-05 前后就该把重心从"再审一遍"转向"先部署一个 staging"。实际转向发生在 10-16，晚了约十天。

### 3.2 审查成了主要工作，而且出现了"修复引入新问题"的循环

36 份审计 / 复查类文档，多轮"全量审计 → 修复批次 → 复查修复 → 再修"。复查一再发现上一轮修复带来的问题，例如：

- 退款被确定拒绝后换键的修复，第二次同码拒绝时又不会换键；
- 败诉拒付闸门只改了发货一处，"超时未发货"待办与报关表漏了；
- 结算页重算在途的闸门，导致按钮亮着却点不动；
- 报错文案改名后，另一处反向断言变成永远为真。

这些单看都是小问题，合起来说明一件事：**改动速度超过了理解速度**。一天 84 个提交时，每个提交都"有测试、有记录、过了门禁"，但没有人能在脑子里装下这一天改了什么、它们之间怎么相互影响。门禁验证的是"每一笔自己对不对"，验证不了"一天的改动叠在一起对不对"。

### 3.3 流程和文档的重量，超过了一个人能长期维护的程度

- 很长的提交说明、每条七项字段的决策记录、文件头必须写 @why / @limitation / @tradeoff、每个单元一份完成模板……
- 决策记录 1.8 万行，`CLAUDE.md` 249 行。新加入的人（或几周后的自己）很难判断哪些规则还有效、哪些已被后来的条目推翻。
- 文档越多，"文档与代码不符"就越多：复查里反复出现"注释说 A，代码是 B"，原因不是粗心，而是需要同步的地方太多。

判断：这些流程大多是在 AI 助手高速产出的背景下长出来的，目的是约束 AI。它们确实拦住了很多错误，但成本是落在**人**身上的——负责人要读、要拍板、要理解，而人的时间才是这个项目最稀缺的资源。

### 3.4 两个 AI 工具同时改同一个仓库

本助手与 WorkBuddy 并行工作，出现过：

- 互相覆盖或重复实现（图片失败兜底、错误码文案各做一份）；
- 一方推翻另一方已记录的决定（品牌字标、"Before You Pay"、邮箱用途），且没有入档；
- 严格档改动缺服务端测试、缺决策记录；
- 测试库互相干扰、gate 结果被并行运行污染；
- 22 个未推送提交、文档库里遗留未提交的契约副本，要事后发现和收拾。

判断：两个各自"很努力"的 AI，比一个 AI 更难协调，因为谁都看不见对方的上下文。负责人被迫充当协调者，而负责人本身不是工程师。

### 3.5 范围在膨胀，而外部依赖一个都没推进

一个月里做了：分类可配置、Banner、售后、部分退款、拒付全流程、迟到付款、订单总表导出、采购表、报关表、运营日志、对账、漏斗统计、风控拉黑、多语言法务页……这些在"还没有一个真实订单"的阶段，多数属于预先建设。

同时，真正卡上线的四件事——公司登记、微信境外主体与 AppID、Stripe 账户激活、承运商与关税（DDP）——都不是工程问题，工程也推动不了，但它们决定了上面这些功能什么时候能用、按什么规则用。特别是关税：美国取消小额免税后，"商品价含关税、DDP 预缴"这个承诺是否成立，取决于承运商，而这件事至今没有答案。如果答案是否定的，部分定价、文案和流程要改。

### 3.6 本助手自身的失误（如实记录）

- **把"gate 跑完"当成"gate 绿了"。** 10-13 那次全量 gate 实际因覆盖率门槛退出码为 1，几天后才发现。
- **在不确定的事情上先动手。** Stripe 变异测试工具装了、跑了两轮、才确认在本仓 vitest 版本下不工作，最后改为自研；一次性的探针本该先做。
- **超出请求范围。** 用户要"搭建流程的界面示例"，我先去截了一套管理后台操作截图，用户明确说不需要才删掉。
- **手册写在验证之前。** staging 手册、阶段一手册里关于 Render / Stripe / 微信界面的描述，是对照官方文档写的，没有一个平台是我实际登录操作过的。手册里标了"以界面为准"，但它们的可靠性仍低于读者可能以为的程度。
- **提交节奏过快、说明过长**，加重了 3.2 和 3.3 的问题。
- **对用户背景的估计偏差。** 前面很长一段时间按"有经验的工程负责人"在交流（术语、取舍、选项），直到用户说"把我看做一个小白"才调整。用户其实一直在承担大量自己并不擅长判断的拍板。

## 4. 背后的几个共同原因

1. **可度量的东西被优先做了。** 测试数、覆盖率、审计发现数、提交数都容易度量，也容易给人"在进步"的感觉；"在真平台上跑通一次"难以拆成小步、又依赖外部账号，于是一直排在后面。
2. **AI 的产出速度掩盖了人的理解速度。** 产出越快，越需要流程来约束；流程越重，人越读不过来；人读不过来，就更依赖 AI 再审一遍——形成循环。
3. **"严格"被当成了目标本身。** 严格是为了上线不出事，但在没有任何真实流量的阶段，很多严格是在保护一个还不存在的系统。
4. **非工程的阻塞没有在工程计划里显式出现。** 公司、AppID、Stripe 激活、承运商被视为"外部条件"，于是工程侧不断找事做，而不是围绕这些阻塞重新排序。

## 5. 给下一阶段的观察（不是指令）

1. **项目已经过了"靠读代码提高质量"的阶段。** 下一轮质量提升只能来自真平台：staging、Stripe 沙盒、测试号真机、承运商的真实报价。阶段一手册（只搭服务和后台）是最小的一步。
2. **停止新增功能和新一轮全量审查，直到 staging 跑通一次完整买家流程。** 跑通之前新增的任何东西，都会叠加到"未经真平台验证"的那一堆里。
3. **一个仓库只留一个写代码的 AI。** 另一个工具可以做只读审查、出报告，但不直接提交。
4. **给流程减重。** 决策记录和注释的价值在于"三个月后能看懂"，不在于"每一笔都写满七项"。可以考虑只为严格档、且真正有取舍的改动入档，其余交给提交说明。
5. **把四个外部阻塞当作项目的关键路径来管理**，尤其是承运商与关税，它可能改变定价模型。
6. **负责人的时间是最稀缺的资源。** AI 交给负责人的东西，应该是"需要你决定的一两件事"，而不是长报告；负责人不需要理解每一个技术细节，但需要知道哪件事只有他能做。

---

## 6. 一句话总结

这个项目在**代码层面**已经做得相当扎实，钱的处理经得起审查；它真正的风险不在代码里，而在**从没有离开过一台电脑**这件事上，以及在为一个尚未上线的系统付出的、越来越重的流程成本上。下一步最有价值的工作，不是让代码更好，而是让它第一次在真实的平台上跑起来。
