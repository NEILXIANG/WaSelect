## 0. 一页结论

我们的后台**"能用、守得住钱"**——退款 / 拒付 / 乐观锁 / 审计这些"出事故的地方"比多数小商家后台严谨；
但在**"每天开工的第一眼"、"一次处理一批"、"找得到、回得去"**三件事上，和成熟平台差距明显：

| 差距 | 成熟平台怎么做 | 我们现在 | 影响 |
|---|---|---|---|
| 没有**工作台首页** | 登录先看"今日待办 + 今日数据 + 异常提醒" | 登录直接进商品列表；待办计数只在订单页顶部 | 运营每天要自己逐页翻才知道该干什么 |
| 导航与地址 | **左侧边栏** + 每个页面都有**网址**（可刷新、可收藏、可发链接） | 顶部按钮切换，页面靠内部状态，**刷新回到商品页、链接发不出去** | 客服说"你看下这张单"时只能报单号再搜 |
| **批量操作** | 列表勾选 → 批量发货 / 导入运单号 / 打印 / 改状态 | 一单一单点 | 单量上来后发货最耗时 |
| 订单详情布局 | **双栏**：左主区（商品、支付、时间线+备注），右侧栏（客户、地址、标签、风险） | 单列长页，所有表单（改址 / 发货 / 退款 / 部分退款 / 修正）全部展开堆叠 | 一张单要滚三屏，误操作面大 |
| 客户 | 有**客户列表 / 客户详情**（历史订单、累计消费、备注、标签） | 没有；只能从订单反查 | 回头客、问题买家都看不出来 |
| 内部备注 | 订单 / 客户上可写**内部备注**，时间线里与系统事件并列 | 只有系统事件 | 交接班、客服沟通靠微信群 |
| 数据 | 销售 / 订单 / 商品 / 转化报表，首页小卡片 | 只有对账结果 | 不知道卖得怎样 |
| 账号与权限 | 后台里邀请员工、分角色（客服 / 发货 / 财务） | 只能命令行建管理员，全部超级权限 | 多人协作时不敢放权 |

**建议（已拍板，§8）**：不追功能齐全，第一批先补**"统一反馈与确认 → 侧栏与网址 → 工作台 → 订单详情双栏 → 内部备注 → 未保存提醒"**——
它们占日常大部分操作时间，改动集中在前端，后端只需一个统计接口和一张备注表。批量发货放第二批（单量 > 20 / 天前做完）；
员工权限与买家售后申请放第三批，按触发条件立项（§8-3、§8-4）。工作台数据**円为主、USD 为辅**（§8-2）。

## 2. 信息架构与整体布局

### 2.1 成熟平台的共同骨架

```
┌──────────────────────────────────────────────────────────────────────┐
│ [店铺名]      [ 🔍 全局搜索：订单号 / 商品 / 客户 / 运单号  ⌘K ]   🔔 3   (头像▾) │  ← 顶栏
├────────────┬─────────────────────────────────────────────────────────┤
│ 🏠 首页     │  页面标题                            [次要操作] [主操作]  │
│ 📦 订单  12 │  ─────────────────────────────────────────────────────  │
│   待发货 3  │  [全部 | 待付款 | 待发货 3 | 已发货 | 售后 2]  ← 状态页签+计数 │
│   售后   2  │  [🔍 搜索] [日期▾] [渠道▾] [更多筛选]  [保存为视图]       │
│ 🏷 商品     │  ┌─────────────────────────────────────────────────┐   │
│   库存      │  │ ☐ │ 订单号 │ 时间 │ 客户 │ 金额 │ 状态 │ 物流 │ … │   │
│ 👤 客户     │  │ ☐ │ …                                               │   │
│ 📣 营销     │  └─────────────────────────────────────────────────┘   │
│ 📊 数据     │  已选 3 单：[批量发货] [打印面单] [导出]  ← 勾选后出现的操作条 │
│ ─────────  │                                                         │
│ ⚙️ 设置     │                                                         │
└────────────┴─────────────────────────────────────────────────────────┘
```

要点：
1. **左侧边栏**承载一级模块，二级（如"待发货""库存"）直接展开在下面，并带**角标计数**——不用进页面就知道有事。
2. **顶栏全局搜索**（Shopify 的 ⌘K、千牛的顶部搜索）：粘一个单号 / 运单号 / 手机号，直接跳到那条记录。
3. **每个页面、每条记录都有网址**：`/orders/261008-61N4D4`。刷新不丢、可收藏、可发给同事。
4. **列表页三件套**：状态页签（带计数）→ 搜索与筛选 → 表格（勾选列 + 批量操作条）。
5. **主操作固定在右上角**（新建商品、创建订单），次要操作收进"更多"。
6. **设置单独放在侧栏底部**，与日常业务分开。

### 2.2 我们的差距

| 项 | 现状 | 建议 |
|---|---|---|
| 一级导航 | 顶部按钮，6 个业务入口 + 退出平铺；"运营配置 / 风控 / 运营日志"与日常业务同级 | 改**左侧边栏**；业务（首页 / 订单 / 商品 / 客户 / 营销）在上，管理类（风控 / 日志 / 设置）在下，退出收进头像菜单 |
| 计数角标 | 只有订单页顶部有 | 侧栏"订单"旁直接显示待发货数；"风控"旁显示进行中拒付数 |
| 网址 | 无（state 切换） | 引入路由（`/orders`、`/orders/:no`、`/products/:id/edit`…）；浏览器前进后退可用 |
| 全局搜索 | 无 | 顶栏搜索框：识别单号 / 运单号格式直接跳详情，否则搜商品 + 订单 |
| 页面宽度 | 内容区上限约 1150px，宽屏右侧大片留白 | 列表页可铺满；详情页保持阅读宽度 + 右侧栏 |

## 3. 首页工作台（我们完全缺失）

### 3.1 成熟平台的工作台

```
┌ 今日待办 ──────────────────────────────────────────────┐
│ 待发货 3（1 单超 48 小时⚠️）  待处理售后 2  退款处理中 1   │
│ 库存紧张 4   拒付待举证 1（剩 3 天）   汇率 2 天未更新⚠️   │
└────────────────────────────────────────────────────────┘
┌ 今日数据 ───────────────┐ ┌ 近 7 天趋势 ───────────────┐
│ 销售额 ¥ / 円  订单数     │ │  ▁▃▅▂▆▇▅  销售额 / 订单数  │
│ 客单价  访客  转化率      │ │                           │
└─────────────────────────┘ └──────────────────────────┘
┌ 最近订单（5 条，点即进详情） ┐ ┌ 系统提醒 ───────────────┐
│ …                          │ │ 对账异常 0 / 回调失败 0   │
└────────────────────────────┘ └────────────────────────┘
```

共同特征：**"待办"放第一屏，每一项都可点击直达筛好的列表**；数据卡片只放 3–5 个最关键指标；异常用醒目色，没有异常就不占位。

### 3.2 建议（贴合我们的业务）

- **待办**：待发货（标出超过发货时限 `SHIP_WITHIN_BUSINESS_DAYS` 的）、退款处理中 / 部分退款在途、进行中拒付、库存紧张、汇率将过期、停售是否开着。
  数据都已有（列表接口 total、对账结果、汇率表），**后端几乎零改动**。
- **今日数据**：今日订单数、已付款金额（円 + 换算 USD）、本周对比。需要一个轻量统计接口（`select count/sum … where paid_at >= today`）。
- **系统提醒**：最近一次每日对账的异常计数（运营日志页已有），回调验签失败（P1-1 已打日志，可汇总）。

### 4.4 售后

成熟平台（尤其国内）把售后做成**工单**：买家在小程序发起"仅退款 / 退货退款"→ 商家同意 / 拒绝 → 买家寄回填单号 → 商家确认收货 → 退款。
我们现在只有**商家主动退款**，买家没有发起入口，所有沟通靠客服微信。
- **P2**：先做"买家发起售后申请（原因 + 照片）→ 后台售后列表 → 同意即走现有部分 / 全额退款"。退货寄回在跨境场景少见（运费高于货值），可不做。
- **P1**：退款原因给**预设选项**（缺货 / 破损 / 错发 / 买家取消 / 其它）+ 补充说明，便于统计。

### 4.5 客户（缺失）

成熟平台的客户页：列表（姓名、单数、累计金额、最近下单、标签）+ 详情（订单历史、地址簿、备注、黑名单状态）。
- **P1**：只读的客户列表与详情即可（数据都在 orders / addresses / users），把"拉黑 / 解除"从风控页挪到客户详情。

### 4.6 营销

| 能力 | 成熟平台 | 我们 | 建议 |
|---|---|---|---|
| 首页装修 | 可视化拖拽模块（轮播、商品组、图文） | Banner 列表 + 首页"精选"由代码决定 | P2：先做"首页推荐商品排序" |
| 优惠 | 优惠券、满减、限时折扣、包邮门槛 | 包邮门槛在配置里（`free_shipping_remaining_jpy`），后台不可配 | P3：跨境代购早期靠选品，不靠券 |

### 4.7 数据报表（缺失）

成熟平台：销售额、订单数、客单价、退款率、商品排行、时段分布、渠道来源；可按日期对比。

## 7. 不建议照搬的

- **多店铺 / 多渠道 / 多仓库**：Shopify、抖店为平台型设计；我们是单店、单渠道（小程序）、单仓（日本代购发 EMS），照搬只会多一层无用选择。
- **复杂营销体系**（券、拼团、分销）：早期跨境代购的增长靠选品与信任，不靠促销；做了反而增加对账与退款复杂度。
- **可视化装修编辑器**：开发成本高；首页模块少，"推荐商品排序 + Banner"已覆盖九成需求。
- **SKU 规格矩阵**：当前目录几乎都是单规格；硬上会让商品表单和库存乐观锁都复杂一倍。

## 8. 拍板结果（AI 代拍板，用户 2026-10-08 授权；记录见 `docs/自主决策记录.md` AJ-390）

### 8-1　第一批做什么、按什么顺序 —— **按 §6 五项做，另加一项，按依赖顺序排**

| 顺序 | 内容 | 为什么排在这里 |
|---|---|---|
| ① | 统一 **Toast**（操作反馈）与**确认弹层**（危险操作） | 后面四项的动作反馈都要用它；先做组件，后面不用每页各写一遍、再改一遍 |
| ② | **左侧边栏 + 网址路由** | 改的是所有页面的外壳；先换壳再往里填新页面，避免工作台、订单详情做完又跟着搬家 |
| ③ | **首页工作台** | 依赖 ② 的路由（待办要点即跳到筛好的列表，例如 `/orders?status=paid`） |
| ④ | **订单详情双栏**，改址 / 发货 / 退款 / 部分退款 / 修正收进按钮 → 弹层 | 依赖 ① 的弹层；是每天停留最久的页面 |
| ⑤ | **订单内部备注**（与系统事件同一条时间线） | 依赖 ④ 的新布局；后端新增 `order_notes` 表（append-only，进审计） |
| ⑥（新增） | 编辑商品 / Banner **未保存离开提醒** | 改动半天以内；运营填了十几个字段、传了图后误点导航，整张表单丢失——这是实测里最痛的一类 |

**不放进第一批**：批量发货。当前单量是个位数 / 天，一单一单处理不是瓶颈；放第二批，单量 > 20 / 天前做完即可。

### 8-2　工作台数据用円还是 USD —— **円为主，USD 为辅；退款与实收按实际扣款币种**

- 主显示**円**：系统的定价锚、记账币都是円（`PRICING_ANCHOR=JPY`，ADR-09）；商品售价、采购成本、运费、毛利全是円——
  运营判断"今天卖得好不好、赚没赚"天然用円。USD 随汇率每天变，拿 USD 比较不同日期的销售额会被汇率噪音污染。
- 辅显示 **USD**（灰色小字，按**当日生效汇率**折算，标注"≈"）：老板与买家沟通、对 Stripe 后台时要用。
- **例外**：涉及**实际收付**的数字——实收、已退、拒付金额——按**扣款币种原样**显示（Stripe 单为 USD，日后微信单为円），
  不做折算。原因：这几个数要和支付机构对账，折算后对不上（与 AJ-383 部分退款"按支付币种最小单位记"同一口径）。
- 不显示人民币（CNY）：它只是给买家看的展示币，经营判断用不到。

### 8-3　是否需要多人协作 / 员工权限 —— **近期按单人运营设计，员工权限推到第三批，设立触发条件**

- 现状：只有你一个管理员；项目约定"完全自研、不外包"，近期没有外部协作者。现在做角色权限，是为一个还不存在的人建模型。
- 风险兜底已经在位：所有管理员都可开二次验证（AJ-386）、全部操作进审计（运营日志可按人筛）、退款与拉黑有两步确认。
- **触发条件**：有第二个人参与**日常**运营（客服、发货、采购任何一种）时立项。届时先做最小两档：
  **"运营"**（订单查看 / 发货 / 改址 / 备注，不能退款、不能改价、不能改设置）与 **"管理员"**（全部），而不是一开始就做细粒度权限矩阵。
- 在此之前，如有临时帮手：用 `npm run admin:create` 建独立账号（不共用账号，审计才能分清是谁）+ 开二次验证。

### 8-4　售后是否开放买家自助 —— **开放"售后申请"，不开放"自助退款"，也不做退货寄回；放第三批，设触发条件**

- **开放申请**：买家在订单详情点「申请售后」，选原因（缺件 / 破损 / 错发 / 未收到 / 其它）+ 文字说明 + 最多 3 张照片 → 后台出现"售后待处理"，
  运营判断后用**已有的**部分退款 / 全额退款处理，结果回写给买家看。
  理由：目标买家是在美华人，习惯淘宝式"申请售后"；现在全部靠客服微信，记录分散、无法统计，也没法和订单关联。
- **不做自助退款**（买家点了就退）：跨境代购单价高、无法上门取件核实，自动退款会被滥用；决定权留在运营手里。
- **不做退货寄回流程**：美国寄回日本的 EMS 运费常常高于货值，行业通行做法是"拍照核实 → 部分退款或补发"，不退货。
- **时机：第三批**，触发条件：月单量 > 100 单，**或**每周经微信处理的售后咨询 > 5 次。在此之前用微信 + 后台内部备注（第一批 ⑤）记录，
  足够应付；过早上线要同时改小程序（拍照上传、隐私授权、图片存储与保留期），投入不划算。
