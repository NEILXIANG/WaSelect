# 全入口点击测试（2026-10-11 ～ 10-12）

> 用户要求：后台管理与微信小程序**每一个可以操作的入口**都在真实界面里点到，识别 Bug、交互不好、文案不合理、新手 / 老手迷茫、界面布局不合理，并修复（沿用授权代决口径）。
> 本文是**结论与覆盖矩阵**；为什么这些问题此前的测试没拦住、补了哪些测试机制，见 `docs/测试缺口复盘-2026-10-12.md`。

## 1. 范围与方法

- **入口清单从代码生成**：小程序 87 个事件绑定（`bindtap` 等）、后台 256 个 `onClick / onChange / onSubmit / href`，按文件 + 行号逐个标状态（正常 / 已修 / 等价验证 / 限制）。
- **真实界面**：小程序用微信开发者工具（自动化接口 + 截图），后台用内置浏览器（1366×860），数据库是模拟库 `japan_shop_sim`，支付走 mock 通道。不碰生产。
- **每修一处**：先写会红的用例再改；严格档（钱、状态、校验、审计、契约）另写决策记录、做注回、跑全量 gate。
- **对标**：交互与版式按主流电商（淘宝 / 京东 / 有赞小程序；Shopify / 淘宝千牛后台）的通行做法判断。

> "等价验证"= 真实界面里点不到或触发不了（如自定义 tabBar 节点、渲染崩溃兜底页），由组件 / 页面用例覆盖。

## 3. 修了什么（按类）

- **看不懂 / 说错话**（最多）：金额单位「円」→「日元」（用户要求，D-82 / AJ-495）；36 位内部 id 不进正文（运营日志对象、Banner 编辑标题、解除拉黑提示、客户详情弹层）；通道代号、英文导出表头、裸 HTTP 状态码、`image_key` / "目标 id" / `YYYY-MM-DDTHH:mm` 这类字段名与格式串；禁售合规标签提示写代号；没留邮箱也说"已发邮件"；已退款的单提示"联系承运商"；超时未付款两端说法不一（已过期 / 已超时关闭）。
- **交互**：提交订单按钮常亮、缺啥带到哪（AJ-492）；库存不足自动改到可买件数（AJ-493）；原因必填的危险操作（停售、拉黑、解除、删除行为记录）提示就近并聚焦；点「新建 / 编辑」带到表单；筛空了给「清除筛选」；商品图可一次选多张；从详情返回列表回到原来的滚动位置。
- **布局**：长商品名两行截断；吸底保存条遮住输入框；禁用按钮看不出禁用；危险按钮与普通按钮一个样；整行黑色主按钮放在"关店"上；商品图缩略图被裁成一条、排序箭头方向不对；表格缺表头；小程序角标挤偏文字、地址卡松散、条款页三屏缩到一屏。
- **业务规则**：服务端校验美国地址邮编与州（AJ-496，原只有前端拦）；审计中间件漏记分类改动的对象（AJ-497）。

## 4. 已知未修（记下来，不假装做了）

- ~~运营日志"对象"列的订单 / 商品是缩短的内部编号~~：已改写订单号 / 商品名（AJ-499）；客户类对象仍是缩短编号（可点进详情）。
- 自动核对的取样仍是 `ord-…`（可点进订单详情），没换成订单号。
- 拒付期间买家端仍显示"已付款 · 日本采购中"——建议告诉买家"你的银行正在处理这笔付款的争议，处理结束前暂不发货"，需要用户拍板（见测试缺口复盘 §6）。
- 工作台转化漏斗的人数与种子订单对不上（模拟数据造成，不是代码问题）。
- 从一张详情跳到另一张详情时保留了滚动位置（少见）。
- 仅 Stripe 托管页可见的支付界面在模拟环境里看不到。
- 布局类问题没有自动化检查（不引入浏览器测试工具）——每次改界面后用模拟库里的边界商品（255 字标题、180,000 日元、无图、售罄）在两端各看一遍。
