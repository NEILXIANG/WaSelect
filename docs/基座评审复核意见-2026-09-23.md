## 3. 部分成立（14 条）— 照原文改会改错方向

### 3.1 P0-7「进度口径虚高」：我认，但要改的是**呈现方式**，不是简单把 ✅ 降级

评审说"12 项标 ✅，其中 8 项未满足清单自身的验收标准"。对照下来：

- **确实偏乐观**：我的 ✅ 含义是"这块能力建好了、gate 绿、做过红灯验证"，而不是"清单这一行的每一句话都做完了"。F5 的 `/beacon`、F6 的 CORS→限流、F6b 的登录/锁定、F7 的 `app_config` 等都在"怎么验证"栏里明写了却没做。**这是我的错。**
- **但不能一律降级**：其中有几项的缺口是**被前置决策阻塞**，现在做不了（`app_config` 要等 ADR-28 四张表拍板；`/beacon` 契约里有没有对应端点也待确认）。

**我的修法**（比简单降级更有用）：进度表改成三态 + 列出缺口原因

```
✅ 已实现并通过红灯验证  |  🟡 部分（缺 X / Y）  |  ⛔ 阻塞于决策 #N
```

### 3.2 D16「staging 与 development 同样宽松」

**部分不成立**：让 staging 必须有真实 Stripe 密钥是错的——staging 用 mock 通道本来就是常见且合理的。
**成立的部分**：URL 格式校验、`INTERNAL_JOB_SECRET` ≥32 位这类"字符串形状"校验，与运行环境无关，本来就该有。

### 3.3 D18「allocate 不校验符号」

**负权重**（`allocate(100, [-1, 3])` → `[-50, 150]`）是真缺陷，应拒。
**负总额**我不认为是缺陷：退款拆分、折扣分摊本来就是负数，禁止它反而会逼业务层绕开。**只禁负权重。**

### 3.4 D26「issuer 未接配置 / 无法按环境区分」

不完全准确：`AuthConfig.issuer` 存在且签发校验都用了，缺的只是**没有对应的环境变量**。降为 P2。

### 3.5 D25 / D14 需要连起来看

- D25（`ver`/`blocked_at` 不校验）：auth.ts 自己的注释写"F7 之后有库了才能做"——**这个前置已经满足**，所以现在该做。
- D14（append-only 触发器挡住 `user_events` 删除）：**这是我上一轮修 P1 时引入的**——我落实了 ADR-29 的 append-only，却没有回头核对 F5 验收项里“按 user_id 清除行为记录的接口有测试且有审计”（APPI）。这与之前几次出错是同一类：**只核对了“这次要满足的那一条”，没有回头扫一遍清单里所有相关验收项。** 值得单独立一条规则：**改动契约 / 表结构时，必须列出所有受影响的验收项逐条确认，而不是只确认自己关心的那一条。**

D28（afterAll 掩盖根因，措辞对但优先级 P3）· A4（async 样板多余，Express 5 确实自动接管）· T3（gate 重复跑测试）· L6/L7/L8/L10（日志字段与噪声）· SEC7（安全响应头）· MP9（成功判定约定）· FX8（JAN/openid 真实形状）

## 4. 不成立 / 我不同意处理（5 条）

| 条 | 评审的说法 | 我的判定与理由 |
|---|---|---|

## 5. 评审漏掉或低估的（这是本次复核的主要增量）

### 5.1 假数据问题的根：我这六个就是 issue 源头

评审列为 FX1/FX2/FX3 的“素材与业务决策冲突”，本质是同一件事：**我写 fixture 时没有拿契约、技术文档、决策日志做交叉校验，而是凭“看起来合理”造数。** 尤其是 FX3，我不但编了错误的中间档，还**把它写成了断言**——这是最坏的一种，错误被固化成了“必须满足的规则”。

建议补一条约束进 CLAUDE.md：**假数据的数值只能来自"契约 / 技术文档 / 决策日志"三处之一，来源写进注释；自己推算出来的中间值必须标 `@fabricated` 并在 TODO 里登记替换条件。**

### 5.2 ⚠️ 本仓库有一批内容建立在**已作废决策**上（评审完全没提）

这是我认为**比任何一条 D 都重要**的发现：

- 决策日志里 **D-31（09-19）** 定的是"H5 收银页用自有域名 + Stripe **Payment Element**"。
- **D-49（09-22）已推翻它**：银行卡唯一入口 = 复制链接 → **Stripe Checkout 托管页**，删 web-view 容器页与 H5 换票（见 `jp/50-产品与技术/需求与设计/GUI/产品GUI交互文档.md` 抬头、`jp/40-支付与资金/支付方案-完整设计.md` v1.4）。
- 结果是三样东西同时过期：
  1. **我刚写的 Stripe 样本**（只有 `payment_intent.*`）——所以 D31 属实，而且不需要外部资料就能判定：**本仓库 vendored 的契约第 234 行自己写着 `checkout.session.completed / checkout.session.expired / …（D-49/D-50）`**；
  2. **`docs/开发前审计报告-2026-09-19.md` 第 15/16 条**（明确要求"事件改为 payment_intent.succeeded"）——现在是**反向错误指引**，建议打上作废标记，否则下一个读它的人会照着改回错误口径；

- 顺带：我此前的长期记忆里"收银页首屏必须是卡号输入"这条也过期了，本次一并更正。
