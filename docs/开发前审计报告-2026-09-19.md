## 19. 第十四轮（2026-09-21，D-46）：运费分档「取档方向」写反 —— 运营事故级

> 本轮为**全库重新评审**（用户要求更严格），未依赖新增修改。发现的问题全部来自"语义 vs 实现"的对撞，不在任何外部清单里。

### 19.1 头号问题：`VLOOKUP(…,TRUE)` 是向下取档，与「上限（含）」口径相反

三处口径本应一致，实际只有两处对：

| 位置 | 口径 | 实际 |
|---|---|---|
| 模型 `参数!A35` 表头 | 计费重**上限**（含） | ✅ 文字对 |
| 后端 `shipping_rates.max_weight_g` 注释 | 该档上限（含） | ✅ 文字对 |
| 模型实际公式 | `VLOOKUP(J, $A$36:$B$45, 2, TRUE)` | ❌ **近似匹配 = 取「最大且 ≤ 查找值」= 向下取档** |

**后果（静默、不报错）**：只要包裹重不在档位边界上，就低收一档。

| SKU（N=4，包材 250g） | 包裹重 | 旧（向下） | 正确（上限含） | 每单少收 |
|---|---|---|---|---|
| 药妆·洗颜粉 120g | 970g | 2,150 | 3,150 | **1,000 円** |
| 象印保温杯 480ml | 1,850g | 4,050 | 4,950 | **900 円** |
| 伊藤园抹茶粉 100g | 850g | 2,150 | 3,150 | **1,000 円** |
| 贝印厨刀 165mm | 1,250g | 3,150 | 4,050 | **900 円** |
| SK-II 面膜 6 片 | 1,850g | 4,050 | 4,950 | **900 円** |

单均净贡献约 3,794 円（948.5 × 4），**等于被抹掉 24–26%**。而 `B67=1`（运费单列向客户收取）时，这个差额直接由我方承担——客户付 4,050，承运商收 4,950。

**已修**：26 处公式 `VLOOKUP(…,2,TRUE())` → `INDEX($B$36:$B$45, COUNTIF($A$36:$A$45,"<"&w)+1)`（向上取档）。

### 19.2 连带发现：契约里没有 SQL，语义没钉死

§2.5 早就写了预警"低一档每单几百円由我方吸收"，但**模型里这个 bug 一直没被发现**——说明**预警文字不能替代自测向量**。技术文档全篇没有一处写明分档查询 SQL，AI 编码时极可能照着模型（错的那份）写成 `<= … DESC LIMIT 1`。

**已补**：§2.5 写死唯一正确 SQL（`WHERE max_weight_g >= $w ORDER BY max_weight_g ASC LIMIT 1`）+ 明令禁止向下取档 + **7 条自测向量**（`w=100→1400 / 101→1650 / 500→2150 / 501→3150 / 1850→4950 / 2000→4950 / 2001→6600`），DDL 注释同步。新增 **R22**。

## 20. 第十五轮（2026-09-21，小程序专项）：D-47 支付入口架构修正 + D-48 官方支付合规三条硬要求

**本轮方法**：不依据"文件是否有改动"，而是**重新独立审读 + 逐条比对官方原文**。加载 `wechat-miniprogram` / `miniprogram-development` 技能后，拉取微信官方 `web-view` 组件文档与《微信小程序平台运营规范》§14 原文做事实核验。

### 20.1 D-47：银行卡支付默认入口由 `webview` 改为 `copylink`（架构级）

**发现过程**：读官方 `web-view` 组件文档「Bug&Tip」第 1 条——

> **网页内 iframe 的域名也需要配置到域名白名单**

**推论链**（每一步都可验证）：

| 步骤 | 事实 |
|---|---|
| ① | Stripe Payment Element 的卡号 / CVC / 邮编输入框，以及 3DS 挑战页，**全部是 `js.stripe.com` / `hooks.stripe.com`（及发卡行域名）的 iframe** —— 主页面 URL 是自有域名不构成豁免 |
| ② | 业务域名配置要求**下载校验文件并放到该域名根目录** |
| ③ | 我们**无法在 Stripe 的域名根目录放校验文件** |
| ④ | ⟹ 这些 iframe **永远进不了白名单** ⟹ web-view 内 Payment Element 大概率白屏 |

**为什么这是架构级、不是细节**：原设计把 web-view 当主路径，一旦按此实现，I1 阶段**全部 H5 收银页工作会在真机联调那天才发现白屏**，此时 UI、票据换票、回跳、轮询全部要重做。返工点在链条最末端，成本最高。

**三道墙**（原判断含一条我自己的过度结论，已在 D-48 订正）：

1. **墙① iframe 白名单（最硬，技术性阻断）** —— 见上表
2. **墙② Apple Pay 被禁** —— `ApplePaySession` 是 Safari 作用域 API；iOS WKWebView 只要宿主 App 使用脚本注入（`WKUserScript` / `evaluateJavaScript`）即禁用，微信 web-view 有 JSSDK 注入
3. **墙③ 审核（D-48 订正：此项被我上一轮高估）** —— 官方 §14.7 / §5.13「不得引导至 h5 完成支付」**主语是虚拟商品**，我们是自营实物，**不适用**

**处置**：

- `H5_ENTRY_MODE` 默认 `copylink`（短链 + 一键复制 + "在 Safari / Chrome 打开"指引，**无二维码**）；`webview` 降为「真机实测确认 iframe 可加载后」才允许启用
- H5 页面本身不变（一套页面两种入口）；Payment Element 硬规则不变（`return_url` 落 `checkout.<domain>`、`redirect:'if_required'`）
- 全库清扫 14 处「web-view 是默认」的残留表述并同步（技术文档 §5a/§8、PRD §3.1/§3.4、GUI §1/§3.4/§4 时序、工程框架 §3/§5/§7、准备指南 §1.7/§5.3/§6/§7、ADR-19、任务看板、开发计划、合伙人迭代计划）
- R20 由 🟡 升 🟠，改写为「web-view 内 Payment Element 整体不可用」
