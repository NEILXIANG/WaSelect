### 3.1 F-03 为什么是真死路，而不只是"要人工重发"

原报告的推理是：KD-4 修好了重试路径，重试沿用同一个机构幂等键，所以停在 refunding 时"人工再点一次就行"。这对**失败**的退款成立，对 **pending** 的退款不成立。

1. **pending 分支什么都没记下**：`admin-order-routes.ts:365-383` 中，只有 `succeeded` 会调用 `markRefunded`（并把 `refundRef` 写进事件备注）。pending 只打一条 info 日志后返回 202，**`refundRef` 没有落库**，连日志里也没有。
2. **24 小时内重发，拿回的还是 pending**：退款请求带的机构幂等键是 `refund:<orderId>`（`stripe-checkout.ts:535`）。按 Stripe 的幂等规则，同一个键在 24 小时内重放，返回的是**第一次的响应**（AJ-175 KD-4 已按官方文档核对：执行过的结果会被缓存）。所以重发仍然是 pending，订单仍然停在 refunding。
3. **24 小时后重发，预期被拒**：键过期后，这会是一次新的退款请求；而这笔扣款已被那笔 pending 退款占满，按规则不能再退，预期被 Stripe 拒绝，走 `provider_failed`，订单还是停在 refunding。这一点**没有用真 Stripe 实测**。
4. **没有别的出口**：`charge.refunded` 已被识别为 `refunded`，但 `mount.ts` 没有为它注册落账器；`refund.updated` 根本没识别；每日对账的五类扫描**不含 refunding 滞留**。

结论：一旦 Stripe 对某笔退款返回 pending，这张单**在系统里永远到不了 refunded**，也没有任何告警，只能由人去 Stripe 后台核对后直接改库。发生频率取决于 Stripe 实际返回 pending 的比例（未实测），但后果是退款状态错、对账错、买家看到的一直是"退款中"。

**建议的修法**（一个单元，首次真实退款前完成）：
1. pending 时把 `refundRef` 落库。
2. 在 `mount.ts` 为 `refunded` 这个 outcome 注册落账器（`charge.refunded` 回调到达时迁到 refunded），并补识别 `refund.updated` / `refund.failed`。
3. 每日对账增加"refunding 超过 N 小时"一类。
4. 可选：管理端对已有 `refundRef` 的单，重试改为**查询**退款状态，而不是再 POST 一次。

### 3.2 F-07 哪一半对、哪一半不对

- **"JWT 无法失效"不对**。代码里每个受保护请求都会回源比对 `users.token_ver` / `blocked_at` / `is_admin`（`auth.ts:8-11`，D25）；拉黑时 token_ver 递增，旧 token 最迟 60 秒（F-06 那个缓存窗口）失效。原报告引用的 `auth.ts:8-10` 在它的基线上还是一条**过期注释**（写着"token_version 待做"），本轮一致性审计 C9 已更正。另外项目里没有"登出"接口，所以"登出后旧 token 仍有效"这个场景本身并不存在。真正没有的是**按单个 token 撤销**，MVP 不需要。
- **"限流在进程内"对**。在 `render.yaml` 的 `numInstances: 1` 前提下成立；一旦扩成多实例，限流会失效且不报错，60 秒身份缓存也会变成每个实例各一份。目前没有任何测试钉住"必须单实例"这个前提。可选小加固：在 `test/config/render-env.unit.test.ts` 加一条"`numInstances` 必须为 1"的断言，并写明原因（进程内限流与身份缓存），这样扩容时会先红，逼人先处理这两处（🟡）。
