## 0. 这批决策的共同判断原则

回头看这些选择，真正反复起作用的是五条。它们比任何一条具体决策更值得复用：

1. **"绿灯"必须能区分"做对了"和"没做"**。凡是"没做也不报错"的要求，都会随忙碌退化成没做。
   所以优先把要求翻译成**会失败的检查**；翻译不动的，至少给它一个名字（人工检查项 H1–H5）。
2. **代价发生在"没人看的时候"的缺陷优先修**。静默不报错的（运费取错档、幂等占位卡死、
   脱敏误伤）优先于会抛错的。会抛错的缺陷有警报，静默的没有。
3. **先问"现在改的代价"和"上线后改的代价"哪个大**。现在改零成本、上线后改要动真实数据的，现在就改
   （典型：D3/D4 加表）。反过来，现在改会与已定架构冲突的，登记为待办而不是硬上（典型：F-A1）。
4. **凡是能实测的，不许凭记忆**。本仓库已有 5 次"实测推翻我第一版"。
   训练知识偏旧（Express 4 才是主流形态），环境差异（本地 vs Render）也无法靠记忆覆盖。
5. **给机制写 `@limitation`，尤其是它管不了什么**。一个不知道边界的护栏会被误当成"已经安全了"——
   这比没有护栏更危险。每个新增的门禁都写了"它管不了什么"。

## 1. 决策台账

### AJ-01　只开三条类型感知 lint 规则，不用整套 `recommendedTypeChecked`

- **场景**：评审 A5 指出 ESLint 未启用类型感知规则。
- **可选**：(a) 整套 `recommendedTypeChecked`；(b) 只开点名的三条；(c) 暂不开。
- **选择**：**(b)** —— `no-floating-promises` / `no-misused-promises` / `switch-exhaustiveness-check`。
- **依据**：整套会带进 `no-unsafe-assignment`、`no-unnecessary-condition` 等需要大面积改写的规则，
  一次性引入几百条噪音的结果是**有人把整个 block 关掉**，那就一条都没了。宁可少开、开得住。
  这三条恰好打在本项目最容易出事的三类代码上：忘了 await 的 Promise（支付回调/调度器）、
  Promise 传进要同步返回值的位置、状态机加状态时 switch 漏改。
- **反向风险**：漏掉了整套里其他有价值的规则；将来可能要再开一轮，又要过一遍噪音。
- **回滚**：删掉 `eslint.config.mjs` 的 A5 block；`test/lint/type-aware.lint.test.ts` 会立刻红（这是有意的）。
- **下游**：`eslint.config.mjs`、`test/lint/*`。

### AJ-02　`checksVoidReturn` 五项全开（第一版写错，被实测推翻）

- **场景**：担心 Express 的 async handler 被 `no-misused-promises` 误报。
- **可选**：(a) `checksVoidReturn: { arguments: false }`；(b) 默认五项全开。
- **选择**：第一版选了 (a)，**实测后改为 (b)**。
- **依据（实测）**：@types/express 5 的 `RequestHandler` 返回 `void | Promise<void>`，
  async handler 在 `arguments: true` 下**本来就不报**（探针第 38 行无错）；
  而关掉 arguments 会放过 `[1,2,3].forEach(async …)`（探针第 45 行）——
  那是"错误静默吞掉 + 根本不串行等待"的形态，比 Express 那条重要得多。两头都对，所以全开。
- **反向风险**：若将来降级到 Express 4，async handler 会开始报红——那时该改的是升级 Express，不是关规则。
- **回滚**：改回 `checksVoidReturn: { arguments: false }`——但会重新放过 `forEach(async …)`；`type-aware.lint.test.ts` 会红。
- **下游**：`eslint.config.mjs` 的 ⚠️ 注释里写了完整实测过程，防止有人"好心"再关一次。

### AJ-03　新增 LM 层（第 5 个 vitest project）做"门禁的门禁"

- **场景**：`npm run lint` 全绿有两种可能——规则生效且代码干净，或规则压根没挂上。两者输出一模一样。
- **可选**：(a) 不额外验证，靠人记得注回缺陷；(b) 写 fixture 用 ESLint Node API 断言规则真的报了。
- **选择**：**(b)**，并独立成一个 vitest project（不进 `test:unit`）。
- **依据**：删掉 lint 规则这类变化不会让任何一层测试变红，是最难发现的一档失效。
  夹具用**内联 `eslint-disable`** 让全仓 lint 保持 0 错，测试改读 `suppressedMessages`
  断言规则确实报了——双保险：block 一旦被删，disable 指令变"未被使用"，数组变空，立刻红。
- **反向风险**：多一次 TS Program 构建（负载高时 ~15s），且只验"规则会报"不验"全仓无违规"。
- **回滚**：删 `test/lint/` 与 vitest 的 lint project。
- **下游**：`vitest.config.mts`、`test/lint/*`、CLAUDE.md 约束九的对照表。

### AJ-09　`dist-boot` 用 `child.on('close')` 而不是 `'exit'`

- **场景**：断言产物子进程退出时的 stdout 含 `traffic_draining` / `server_drained`。
- **可选**：(a) `exit` 事件；(b) `close` 事件。
- **选择**：**(b)**。
- **依据（实测）**：`exit` 触发时 stdout/stderr 管道**可能还没读完**，那一刻去断言日志会读到半截，
  表现为"随机少一行"的假红灯——最难排查的一类。另外进程是走 `process.exit(0)` 优雅退出的，
  `signal` 是 `null` 不是 `'SIGTERM'`，判据要写成"退出码 0"（我第一版就断言错了 signal）。
- **反向风险**：`close` 只在 stdio 全部关闭后才触发；若将来改 `stdio: 'inherit'`，行为不同，需重测。
- **回滚**：改回 `exit` 会引入"随机少一行"的假红灯。
- **下游**：`dist-boot.e2e.test.ts` 的 `stop()` 实现与注释。

### AJ-12　`@measured` 走纪律而非门禁

### AJ-32　回调早到（订单不存在）采用「宽限期 5xx + 超时转对账」双层，不一律 2xx

- **场景**：二审 N4——`webhooks.ts:60` 把 `ignored:order_not_found` 列为 RETRYABLE（指望机构重发），
  但 `skeleton.ts:311` 对该结果回 **200**，机构**永不重发**；F13 对账任务又不存在，
  于是"钱到单未付"只剩一条 warn 日志。原为 §3 第 9 行，用户 2026-09-23 授权自行拍板。
- **可选**：(a) 一律 2xx + 靠每日对账兜底（现状，但 F13 不存在，等于无底）；
  (b) 一律 5xx 让机构无限重发（订单确实不存在的脏回调会重发到机构放弃，噪音且可能触发机构侧告警）；
  (c) **宽限期分层**：回调到达时间与事件发生时间的差 ≤ 宽限期 → 503（让机构按计划重发，
  `processed_at` 保持 NULL 作为对账信号）；> 宽限期 → 200 + `unmatched` + **error 级**告警（进入对账视野）。
- **选择**：**(c)**，宽限期由配置 `CALLBACK_ORDER_GRACE_MS` 控制，默认 15 分钟。
- **依据**：回调比订单先到的真实窗口极小——建单请求与支付创建几乎同时发生，
  机构首回调通常在秒级到分钟级到达；15 分钟足以覆盖"建单请求网络重试/排队"的全部现实场景，
  又不至于让真脏数据无限重发。双层的关键是**两层都留了信号**：宽限期内靠机构重发（自动恢复），
  超时靠 error 告警 + 对账（人工/定时兜底）——单层方案总有一头静默。
  15 分钟是**拍的**：没有机构实测数据，取的是"远大于建单链路 P99 延迟、远小于机构放弃重发窗口（通常小时级）"
  的中间值；上线后拿到真实回调延迟分布再校准（配置项，改起来不发版）。
  连带采纳 N13：同一订单已 paid，后续到达的**另一事件类型**（如先 `payment_intent.succeeded`
  后 `checkout.session.completed`）应落 `paid:already` + info 日志，不再 warn——那不是异常。
- **反向风险**：宽限期内回 503 依赖机构真的会重发（微信/Stripe 都有重发机制，但重发次数有上限，
  若宽限期内所有重发都撞上订单仍不存在，最后一跳仍进对账层——可接受，对账层本来就是兜底）。
  另一风险：`CALLBACK_ORDER_GRACE_MS` 设太大（如 24h）会让脏回调长时间占用机构重发队列，
  配置加 int 下限 0、上限不做硬约束但在注释写明语义。
- **回滚**：把 order_not_found 的响应从条件 503 改回无条件 200 即可（单点改动，webhooks 路由一处）；
  回滚后 F13 对账任务成为唯一防线，**未完成 R2.5 前不得回滚**。
- **下游**：`server/src/webhooks.ts`（order_not_found 分支）、`server/src/config.ts`（CALLBACK_ORDER_GRACE_MS）、
  二审甄别报告 §5 P0-3 设计；R2.5 的 F13 对账任务是本决策的第二层，两者配套。

### AJ-33　PII 脱敏粒度：地址行/邮编整值遮蔽，姓名保留首字母，整体三类口径（SECRET/IDENTIFIER/PII）

- **场景**：二审 N5/N6——`redact.ts:259-269` 的 `maskByKey` 对**所有**敏感键一律 `maskTail`（留尾 4 位），
  `password:'Summer2024'` → `***2024`、`apiKey` → `***9876`（尾 4 位数字恰是撞库高价值片段）；
  且 `SENSITIVE_WORDS` 不含 recipient/name/line1/postal/zip/address 等收货人 PII 键。
  粒度多细原为 §3 第 10 行，用户授权自行拍板。
- **可选**：(a) 一律整值遮蔽（最安全，但日志里连"这张卡尾号多少"都看不出，排查拒付/退款时对不上号）；
  (b) 维持 maskTail 一刀切（现状，机密泄露风险）；
  (c) **三类分治**：SECRET（口令/密钥/token/签名/cookie/cvv 等）整值 `***`；
  IDENTIFIER（卡号/电话/邮箱/openid 等标识符）保留尾 4 位或域名（现状行为，排查需要）；
  PII（收货人姓名/地址行/邮编）整值遮蔽、姓名保留首字母。
- **选择**：**(c)**。
- **依据**：三类的**泄露后果与排查需求都不同**，一刀切两头都错。
  SECRET 的任何片段都有撞库价值且排查时从不需要"看出口令后几位"——整值遮蔽没有代价。
  IDENTIFIER 的尾 4 位是支付排查的行业惯例（对账时和 Stripe 后台、银行短信对尾号），
  且尾 4 位单独不构成可利用凭证——保留。
  PII 不一样：美国地址行 + 邮编 + 姓氏组合即可指向具体住户（日本 APPI/美国各州隐私法都覆盖），
  而排查订单问题时需要的是 order_id 和 trace_id，**从不需要在日志里看到完整地址**。
  姓名保留首字母（`Tanaka` → `T***`）是给"这批日志大致是哪个客户的"留一个人工辨识度，
  首字母单独无法定位个人。两个保守边界（防止误伤业务字段）：
  ① 裸 `name` **不入**词表（会误伤 `product_name`/`channel_name` 等）；
  ② `city` 保留明文（城市级粒度不构成个人识别，且运费/关税排查要看城市）；
  ③ `address_snapshot`（订单里的整对象快照）按**对象级**整值 `***`，不逐字段处理。
- **反向风险**：词表驱动的遮蔽天然有漏网——新字段名不带词表里任何词时明文落盘。
  词表只能收敛不能穷举，这是机制性局限（写进 `@limitation`），
  对冲手段是"记日志前先想该不该记"的纪律 + 关键路径测试断言脱敏生效。
  另一个反向风险：`product_name` 类字段里若哪天混进用户输入（如备注），词表不管——已确认 MVP 无此场景。
- **回滚**：三类表合并回单一 SENSITIVE_WORDS + maskTail 即可（redact.ts 单文件）；
  表驱动测试会红，同步回改。
- **下游**：`server/src/redact.ts`（三类词表 + 三档遮蔽函数）；redact 全部既有用例需按新口径复核改写；
  二审甄别报告 §5 P0-4 设计。

### AJ-52　`getForCallback`：回调取通道**不受"已下线"影响**（注册表第三个取用方法）

- **场景**：统一回调分发要向注册表取 Provider，而注册表已有的 `get()` 会**拒绝已禁用**通道。
  问题来了：一条**已经发生**的支付，其回调到达时通道可能恰好被下线（我们主动下线、或机构停服），
  这时该用哪个方法取？复用 `get()` 还是新增一个？
- **可选**：(a) 复用 `get()`（下线即不可用，最省事）；(b) 复用 `getForRefund()`（它已经"禁用仍可取"）；
  (c) **新增第三个方法 `getForCallback()`**，语义独立（选）；
  (d) 在 `get()` 上加一个 `opts: { allowDisabled }` 开关。
- **选择**：**(c)**。`getForCallback` 刻意**不判 `enabled`**，且连 `refundableWhenDisabled` 都不看。
  拒绝 (d)：布尔开关会让"这个调用点到底允不允许禁用"散落在每个调用处，
  而这类开关的历史结局一定是"某个调用点顺手传了 true"。
- **依据**：三条路径对应三件不同的事，混用任何两条都会出事故——
  `get()` = 新单（禁用即不可用）；`getForRefund()` = 老单退款（禁用仍可用，但要看能力声明）；
  `getForCallback()` = 老单回调（禁用**也不拦**）。回调比退款更根本：
  退款不做，用户可以来问、客服可以补；回调不做，就是"用户付了钱、订单永远停在未支付、
  货不发、也没有任何告警"。而触发它的往往正是"通道刚被下线"这一刻
  （还有一批在路上、在宽限期内的支付）。用 `get()` 接回调 = 每下线一个通道就静默吞掉一批已付款订单。
- **反向风险**：① 一个被**永久下线且代码已删除**的通道，其迟到回调会拿到 40001
  （`channel_not_registered`）而不是被静默忽略——这是刻意的：验不了签就必须响亮失败，
  让"还有钱在路上"变成一条可检索的告警，而不是变成对账时才发现的差额。
  ② 三个方法名字接近，新人可能随手用错；缓解是每个方法的 @why 里都写清"与另外两条的差别只有哪一处"。
- **回滚**：删 `PaymentRegistry.getForCallback` 与其实现、把 `app/pay-routes.ts` 的调用改回 `get()` 即可；
  其余代码不依赖它。⚠️ 但回滚会重新引入"下线通道吞掉在途回调"这一资金事故，回滚前必须先确认
  没有通道处于"已下线但仍有在途支付"的状态。
- **下游**：`server/src/ports/payment.ts`、`server/src/adapters/payment/registry.ts`、
  `registry.unit.test.ts`（+3 条）、`app/pay-routes.ts`（唯一调用点）、`app/pay-routes.unit.test.ts`、
  `test/e2e/pay-channels.e2e.test.ts`。
- **红灯证据**：给 `getForCallback` 加上 `if (!cfg.enabled)` 判断 → **2 条红**
  （"已下线仍可取"与"已下线 + refundableWhenDisabled=false 仍可取，而退款路径拒绝"）。

### AJ-54　F12 第一单元：重试判定做成**纯函数放 `ports/`**，且 **POST 无幂等键绝不重试**

- **场景**：F12 要给出站 HTTP 加重试。难点不在于"重试几次"，而在于
  **重试是唯一一种"加了之后会让事情更糟"的容错**：不重试最多是失败（用户重试、客服补单），
  而错的重试会制造出本来不存在的第二次扣款——且上下游都认为自己是第一次，
  对账表上两条记录都"合法"。这类事故不可回滚。
- **可选**：(a) **客户端内部无脑重试 N 次**（最省事）；(b) 只重试 GET，写操作一律不重试；
  (c) **判定规则做成纯函数放 `ports/`，由实现显式调用**，POST 必须带幂等键才允许重试（选）；
  (d) 完全不重试，失败交给上层 / 调度器与对账。
- **选择**：**(c)**。规则落在 `shouldRetry` / `classifyHttpFailure` / `httpStatusKind` / `backoffMs`
  四个纯函数里；**抖动由注入的 `rand` 提供**（默认不抖），因为 `ports/` 受纯度门禁约束（AJ-50）。
  默认策略：最多 3 次尝试、200ms 起指数退避、封顶 2s、20% 抖动。
  429 是唯一"POST 无幂等键也可重试"的例外——上游明确**没有处理**这个请求。
- **依据**：① 拒绝 (a)：无脑中间件不知道这笔请求会不会扣款，
  而"超时"恰恰意味着**我们不知道上游处理了没有**——对它重试就是赌。
  ② 拒绝 (b)：MVP 的"建支付会话"本来就是带幂等键的 POST（Stripe 侧按 `Idempotency-Key` 去重），
  一律不重试等于把这条**安全**的路也堵死，逼着将来有人在真实需要时绕过规则。
  ③ 拒绝 (d)：网络抖动导致的 502 占比不低，全不重试会把可用性压到不可接受；
  而且"不重试"并没有消除问题，只是把成本转给客服与对账。
  ④ 选 (c) 的关键理由是**规则必须可审**：钱相关的判定如果散落在实现的 if 里，
  评审时看到的是"这里重试了三次"，看不到"为什么这次能重试"。
- **反向风险**：① **总时长预算还没做**：单次超时 10s × 3 次 = 30s，远超用户在同步链路能等的时间。
  本策略只负责"退避多久"，**总预算由实现层在 F12 第二单元加**（已写进 `ports/http-client.ts` 的注释）。
  ② `classifyHttpFailure` 依赖异常的 `name` / `code` 形状而非类型——不同 Node 版本与不同 HTTP 实现
  给出的对象不完全一样；认不出来时保守归为 `unknown`（按"可能已到达"处理，要求幂等键）。
  ③ 抖动默认**不生效**（`rand` 默认 `() => 0`）：实现层若忘了传 `Math.random`，
  功能正确但会有惊群风险——这是"安全默认"，代价要在实现层补上。
  ④ 没有熔断：上游长时间故障时，每个请求仍会各自重试满 3 次（F12 后续单元）。
- **回滚**：删 `ports/http-client.ts` 里"重试判定"那一节（四个函数 + `RetryPolicy`）与
  `ports/http-client.unit.test.ts`、去掉 `vitest.coverage-gates.ts` 里那条阈值即可。
  ⚠️ 本单元**尚未接进任何实现**（`fetch-client` 仍是"只超时、不重试"），
  所以回滚零影响——这也意味着本单元的价值要等第二单元接线后才兑现。
- **下游**：`server/src/ports/http-client.ts`（+4 个纯函数 + `DEFAULT_RETRY_POLICY`）、
  `server/src/ports/http-client.unit.test.ts`（21 条）、`vitest.coverage-gates.ts`（+1 条 100%）、
  `docs/地基搭建清单.md`（F12 进度）。下一单元接线：`adapters/http/fetch-client.ts`。
- **红灯证据**：把 `req.method === 'POST' && …` 的判定改成恒假（等价于"POST 无幂等键也重试"）
  → **1 条红**，报的正是"超时 / 5xx / 网络错误 / 未知 —— POST 无幂等键时**全部不重试**"。

## 4. 维护约定（用户 2026-09-23 明确要求，长期生效）

> **任何由 AI 自行拍板、没有逐条请示的取舍，都必须在同一次交付内写进本文。**
> 不准"先做完、回头补"，也不准只在对话里说一句。
> @why 这类决策的特征是**当时没人复核**：事后想还原"为什么这么做"，只剩代码里一句看不出理由的 `if`。
> 而恰恰是没人复核的决策，最需要留下"当时怎么想的、哪些是赌的"，条件变化时才知道该改哪一条。

执行细则：

- **时机**：与代码**同一次提交**。决策和落地分两次提交，第二次一定会被忘。
- **位置**：§1 末尾追加，编号 `AJ-xx` **不回收**（作废的条目改为标注"已作废"+ 原因，不删行）。
- **每条七项，缺一不可**：场景 / 可选方案（**含被否掉的**）/ 我的选择 / 判断依据（实测要附证据）/
  反向风险 / 回滚方式 / 受影响下游。
- **实测依据要双写**：文档写结论，代码注释写 `@measured:` + 真实输出（见 CLAUDE.md 约束十）。
  只写一处的话，读代码的人看不到依据，看文档的人定位不到代码。
- **被推翻的判断**：一律进 §2，**不改 §1**。§1 保留"当时为什么这么选"，§2 记录"后来发现错了"——
  两边合起来才是完整的时间线。抹掉 §1 会让人误以为一开始就选对了。
- **每条决策必须写"反向风险"**。没有反向风险的决策，通常是还没想透。
- **区分"我定了"与"该你定"**：只是建议、仍需人拍板的，放 §3，不要混进 §1 假装已经决定。

### 4.1 有强制器，但它管不到最关键的那件事

强制器：`test/lint/decision-log.lint.test.ts`（LM 层，`npm run test:lint` 会跑）。

它验的五件事（**全部做过红灯验证**，不是"写完就绿"）：

| 断言 | 红灯变异方式 | 结果 |
|---|---|---|
| 条目数 ≥ 10（防文档被瘦身） | 删到只剩 5 条 | 红 ✅ |
| 每条七项字段齐全 | 删掉某条的「回滚」 | 红 ✅ |
| 「依据」首行不是空话（≥10 字） | 把依据改成「经验」 | 红 ✅ |
| 编号 `AJ-xx` 唯一 | 把 AJ-17 改成 AJ-05 | 红 ✅ |
| §2 / §3 两节都在 | 把「仍然需要人拍板」改名 | 红 ✅ |

> ⚠️ **红灯验证过程中的一次自我纠错**：第 3 条第一次做变异时，改完的文本残留在同一行，
> 长度仍达标 → 测试全绿。**当时是变异脚本写错，不是断言失效**。
> 记在这里是因为：如果只做一次变异就下结论，很容易把"自己脚本的 bug"错判成"门禁有洞"，
> 也可能反过来把"假绿"当成"验证通过"。**验证门禁时，绿灯不算证据，红灯才算。**

**它管不到的（必须靠人 / 靠 review）**：

1. **"该记的有没有记"** —— 脚本判断不了这次改动里有没有发生自主决策，那是语义判断。
   强制器只能保证"写进去的是完整的"，防不了"压根没写"。这一条仍然靠 CLAUDE.md 抬头的硬要求。
2. **内容质量** —— `- **反向风险**：无` 这种敷衍写法照样过（属 H3 人工项）。
3. **§1 与代码是否同步** —— 决策改了代码没改条目，看不出来。
