## 1. 4 个 P0：逐条核实（全部成立，定级附调整）

### P0-1（N1 幂等无栅栏令牌）——✅ 成立，维持 P0

代码核实（`server/src/idempotency.ts`）：

- **写结果不验归属**（130–137 行）：`update idempotency_keys ... where key = ${args.key}`——没有"这一行还是我抢的吗"的任何条件。
- **撤占位不验归属**（141 行）：`delete ... where key = ? and completed_at is null`——A 慢于租约、B 已接管后，A 失败删掉的正是 B 的占位行（completed_at 为 null）。
- **接管不验指纹**（184–191 行）：`update ... set locked_until, request_hash = ${hash}`——租约过期后同键不同内容的请求直接接管并**覆盖**指纹，40908 保护在" pending 期间"同样失效（这是二审没明说、我核实时的额外发现，并入 N1 一起修）。

二审的时序推演（A 慢→B 接管→A 迟到失败删 B→C 再执行，handler 共 3 次）与代码逐行吻合。注释里只写了"接管后可能重复执行（最多 2 次）"，**没写"会删接管者的占位"**——上限从 2 次变成不设限。支付创建 handler 超 30s 租约在弱网+机构慢时是现实场景。**维持 P0，接受其修法（lease_token 栅栏 + 命中 0 行记 error 不删行 + 续期）**。补充：续期引入定时器，测试要用假时钟（§7.6 的 gate/crashAt 工具正合适）。

### P0-2（N2/N3 幂等模板违约）——✅ 成立，维持 P0

- **N3**（`skeleton.ts:189-195`）：`withIdempotency(deps.db, { key, userId, route }, handler)`——**确实没传 `request`**。于是 `idempotency.ts:122` hash 落为 `''`，150 行的 40908 检查被 `hash !== ''` 条件跳过。D4 修好的指纹保护在**唯一的调用方**上是死的。同键不同内容返回 201 旧单，实测推演成立。
- **N2**：骨架 handler 每次 `sk-${randomUUID()}`（skeleton.ts:198），自身不可重入；且"业务事务已提交、幂等结果未写"的崩溃窗口客观存在（handler 内 `withTransaction` 与结果写库是两个事务）。**这正是我自查时读过却漏掉的**——我当时核对了"40908 已实现"，没核对"调用方有没有接线"。教训：验机制存在 ≠ 验机制生效。
- 接受其修法（`withIdempotencyTx` 同事务入口用于纯写库 handler + 结构测试扫"调用不传 request"）。

### P0-3（N4 回调早到自相矛盾）——✅ 成立，维持 P0（附概率说明）

代码核实：

- `webhooks.ts:60` 把 `ignored:order_not_found` 列为可重试结果，`webhooks.ts:48-51` 的注释设想"随后机构重发同一个 event_id"；
- 但 `skeleton.ts:295-312` 对同一分支回的是 **200**——机构收到 2xx 即认为投递成功，**不会再重发**。两条规则互相抵消，"可重试"永远等不来；而兜底的 F13 对账任务不存在（方案漏排，见 N19）。
- 后果链完整：钱到了 → 订单停在 created → 30 分钟 TTL 关单 → 用户钱单两失，发现机制只有一条 warn 日志。

**概率说明（我的补充，不改变定级）**：Stripe Checkout 时序下订单先于支付创建，"回调早于订单可见"需要主从延迟或建单事务未提交，概率低；但它是**回调范式模板**，F11 照抄即固化。维持 P0。接受其修法（宽限期 5xx + 超时转对账 + N13 的 `paid:already` 幂等成功）。这条需要拍板（二审 §8-1），我的建议是**采纳**（理由：宽限期 5xx 是唯一能让机构重试机制为我们工作的选项，纯对账方案的 MTTR 是小时级）。

### P0-4（N5/N6 脱敏口径）——✅ 成立，**定级调整为：N5→P1，N6→P0-预备**

代码核实（`redact.ts`）：

- **N5**（259–266 行）：`maskByKey` 对**所有**敏感键的字符串值一律 `maskTail`（保留尾 4 位数字）。`password:'Summer2024'` → `***2024`、`sk_live_51Hxyz9876` → `***9876`、十六进制密钥尾部 → `***2345`，推演全部成立。**但注意泄露的是"值中的最后 4 位数字"，不是完整机密**——危害真实但有限（口令里的年份、密钥尾号可缩小爆破空间，不等于明文）。定 **P1**。
- **N6**（38–64 行）：敏感词表确实没有 `recipient/name/line1/line2/city/postal/zip/address/street`——美国收件地址（本业务最核心的 PII）整对象进日志时只有 phone/email 会被遮。**但要诚实说明：当前代码里没有任何调用点把地址对象打进日志**（骨架的 address_snapshot 是 `'{}'` 且不输出）。所以这是**口径缺口**而不是**即期泄露**——一旦任何业务代码记一行带地址的日志即变事故。定 **P0-预备**（立即修，因为修法便宜且修得越晚触碰面越大）。
- 接受其三类口径修法（机密整值 `***` / 标识保留尾 4 / PII 整值遮蔽 + address_snapshot 整对象遮蔽）。PII 遮蔽粒度（二审 §8-2）我的建议：**地址行/邮编整值遮蔽，姓名保留首字母**——排障时"哪个州"可从 state（非姓名地址类键，保留）+ 邮编前三位需求不大，整值更省心；这点可在修复时按表驱动测试敲定。
