# 上线前服务端严格测试（2026-10-12）

> 口径：按上线时的样子跑，而不是按开发时的样子跑。
> - 代码：`npm run build` 打包后的 `server/dist/main.js`，启动参数与 `npm start` 相同（`--conditions=waselect-runtime`）。
> - 配置：`NODE_ENV=staging`。没有 dev 登录、没有模拟自动付款，密钥都是随机生成的 32 字节以上。
> - 数据：模拟库整库复制出的独立库 `japan_shop_prelaunch`，包含 1423 张订单和 222 个商品。测试会写库，所以不碰模拟库本身。
> - 买家和管理员的 token 用预发密钥直接签发，因为 staging 不开 dev 登录。
>
> 只测服务端。后台和小程序的输入测试是另一项任务，单独记录。

## 2. 怎么复现

预发启动脚本、探针、压测脚本都在会话临时目录里，没有进仓库，因为它们直接用预发密钥签 token。复现步骤如下：

1. 复制库：先 `pg_dump -Fc` 模拟库，再 `pg_restore --no-owner` 到新库。
2. 打包：`npm run build`。
3. 启动：用 `NODE_ENV=staging` 和新库的 `DATABASE_URL` 启动 `server/dist/main.js`。
4. 跑契约模糊测试：`API_FUZZ_BASE=http://127.0.0.1:<端口> API_FUZZ_TOKEN=<管理员 token> node scripts/api-fuzz.mjs [--allow-writes]`。
   - `API_FUZZ_TOKEN` 是本轮新加的，因为 staging 没有 dev 管理员口令。
   - ⚠️ `--allow-writes` 会打开"暂停接单"、覆盖运费表。跑完要重新复制库，再测下单。

## 3. 逐项记录

### 3.1 启动闸门
逐个注入坏配置，都在启动阶段被拒（`启动失败：配置校验失败，服务拒绝启动`）：

- 生产环境配置不全时一次列出 7 条缺项：mock 通道、APP_ID、库指向本机、CORS、告警通道、客服联系方式、条款地址。
- staging 带 `WECHAT_DEV_LOGIN`。
- staging 带 `MOCK_AUTO_CONFIRM=on`。
- JWT 密钥太短。
- 回调密钥太短。
- 未知支付通道。
- `SCHEDULER_TICK_MS=0`。
- CORS 配 `*`。
- 库连不上（直接退出，不会半启动）。

### 3.2 响应头与 CORS
- 每个响应都带：`nosniff`、`X-Frame-Options: DENY`、`CSP default-src 'none'`、HSTS、`COOP`、`Referrer-Policy: no-referrer`、`x-trace-id`。
- 白名单来源的预检请求返回 204 并回显来源。
- 非白名单来源和 `null` 来源拿不到 CORS 头。

### 3.3 鉴权
| 情形 | 结果 |
|---|---|
| 没带 token、`Bearer` 后为空、`Basic` 认证 | 401 |
| `alg:none`、错误密钥、已过期、签发方不对 | 401 |
| token 版本已作废（改密或强制下线后的旧 token） | 401 |
| 用户不存在 | 401 |
| 买家 token 调管理端、管理员 token 调买家端 | 403 |
| `role=admin` 但受众是 `mp` | 403 |
| 买家的身份签成管理员 token | 403 |
| 买家读别人的订单 | 404（不暴露订单是否存在） |

### 3.4 畸形请求与边界
- 坏 JSON、`text/plain`、表单体、数组体、`null` 体、`__proto__` 键：都是 400 / 40001。
- 2MB 请求体：413 / 41301。
- 20KB 的 URL：431。
- 路径里有控制字符：400。
- 路径穿越：404。
- 搜索关键词：
  - `%`、`_` 不当通配符（命中 0 条）。
  - SQL 片段原样当文字搜。
  - 超长关键词是 400。
  - 带 `\0` 是 400。
  - emoji 和 HTML 正常处理。
- 分页：
  - `size` 为 0、负数、小数、字母、超大，或重复给两次，都是 400。
  - `page` 为 0 或负数是 400。
  - 页码超出范围时返回空列表，并给出 `total`。
- 日期筛选：非法日期、起止颠倒都是 400。
- 排序：不在白名单内是 400。
- 导出：未知类型是 400。

### 3.5 契约驱动模糊测试
`scripts/api-fuzz.mjs`：

- 只读模式：19 个接口，0 问题。
- 写模式（`--allow-writes`，只在一次性库上跑）：49 个接口，291 次探测，P0 / P1 / P2 全是 0。

### 3.6 并发（钱与状态）
| 场景 | 结果 |
|---|---|
| 库存 1，10 个买家同时下单 | 1 单成功，9 单 409 库存不足；剩余库存 0，没有负数 |
| 同一买家、同一幂等键并发 10 次 | 10 次都拿到同一张单，库里只多 1 单 |
| 同一幂等键、请求体不同 | 409 / 40908 |
| 同一幂等键原样重放 | 返回同一张单 |
| 另一个买家用同一个幂等键 | 另建新单（键按用户隔离） |
| 同一订单并发发起付款 5 次（每次换键） | 都是 200，`payments` 只有 1 行 `initiated` |
| 同一回调事件并发 10 次 | 1 次处理，9 次 503 + `Retry-After: 10`；订单只记 1 次 `paid` |
| 同一回调内容换 10 个事件号并发 | 都是 200；订单仍只记 1 次 `paid`，`payments` 只有 1 行 `succeeded` |
| 回调金额或币种与订单不符 | 200 但标为 `settlement_mismatch`，订单不改；记 error 级 `callback_settlement_mismatch`，进当日对账 |
| 买家取消与成功回调同时到达 | 回调先拿到行锁，订单变 `paid`；取消返回 409 / 40902（状态不允许） |
| 签名错误、缺签名 | 401（验签失败） |
| 未开通的通道 | 400 |
| 订单不存在 | 503，宽限期内等对方重投（`callback_early`） |

**发现（AJ-501，已修）**：上表"并发 10 次"那 9 次 503 是设计内的应答，业务日志记的是 info。但访问日志把它们记成 error，会被 Sentry 分流上报。上线后机构每次正常重投都会触发告警，还会占掉每分钟 30 条的上报额度。

- 修复：带 `Retry-After` 的 503 在访问日志里记 warn（`result: retry_later`），其余 5xx 仍记 error。
- 测试：新增单测 1 条，e2e 断言 2 条。注回 3 种错误写法，单测都会红。
- 验证：重新打包后在预发上复测，9 条都是 warn。

### 3.7 每日作业
- 不带密钥或密钥错误：401。
- 用 GET 调：404。
- 带正确密钥：202，返回 `run_id`。
- 并发触发 3 次：都返回 202，但对账记录只多 1 条，没有重复对账。
- 对账能找出探针造成的异常：金额不符的回调、迟到的付款、悬空的付款意图等，都记 error，会告警。

### 3.8 日志脱敏
下面这些操作做完后，搜整份服务日志：

- 买家新建一条带真实形状的地址（人名、E.164 电话、门牌、邮编）。
- 下单时填联系邮箱。
- 管理端看客户详情、订单详情，改地址。
- 导出订单 CSV。

日志里搜不到人名、电话号码、门牌、邮编、邮箱，也搜不到 JWT、回调、作业这三把密钥。日志里没有任何 `eyJ…` 形状的 token。

### 3.9 压测与停机
**压测**：本机测试，打包代码，单进程，每个端点 10 秒。

| 端点 | 30 并发 rps | p95 |
|---|---|---|
| `/home` | 1567 | 27ms |
| `/products` | 728 | 50ms |
| `/products?keyword` | 783 | 46ms |
| `/products/:id` | 1175 | 32ms |
| 买家 `/orders` | 535 | 71ms |
| 买家 `/orders/:id` | 372 | 94ms |
| 管理端 `/admin/orders` | 420 | 92ms |
| 管理端 `/admin/orders?keyword` | 289 | 126ms |
| 管理端 `/admin/dashboard/sales` | 285 | 125ms |
| 管理端 `/admin/customers` | 212 | 205ms |

- 以上全部 200，没有错误。
- 200 并发时，最重的客户列表 p95 约 1.0 秒，买家订单详情 p95 约 0.55 秒，仍然 0 错误（只是在连接池前排队）。
- ⚠️ 这是本机数字。上线平台的 CPU 只有本机的零头，要在上线平台上再测一次，这里只能说明"没有错误、没有雪崩"。

**停机**：一边压测一边给进程发 SIGTERM。

- 就绪探针在收到信号的同一秒转为 503。
- 先等 5 秒让平台摘掉流量，再排空存量请求，共 8.8 秒，正常退出。
- 3820 个请求成功，另有 9 个被连接重置（`ECONNRESET` / socket 错误）。
- 原因（@measured，见下方探针）：`server.close()` 那一刻，内核已经接受、但还没读到请求的新连接会被一起断开。压测客户端无视就绪探针一直在打，所以会撞上。
  - 试过排空期间给响应加 `Connection: close`。本机探针 3 种做法各跑 3 次，重置数分别是 9–14、12–17、17，**消除不了**，所以没改代码。
- 真实部署时，平台先把流量切到新实例再给旧实例发 SIGTERM，这个窗口里基本没有新请求。
- 上线后如果在部署时段看到 502，先查这一条。

## 4. 观察（不算缺陷，记在这里）

1. **限流按 IP 计数**（`rate-limit.ts` 已写明）。小程序买家多走手机网络，运营商 NAT 后很多人共用一个出口 IP。下单上限是每分钟每个 IP 30 次，对小店的量足够。如果上线后在 429 日志里看到同一 IP 有多个 `user_id`，再考虑按用户计数。
2. **启动失败的提示有两条是英文**，来自 zod 原文：`PORT` 不是数字时是 `expected number, received NaN`，通道名写错时是 `Invalid option: expected one of …`。只有部署的人会看到，字段名已经指明了位置，暂不改。
