# 代码注释规范与日志体系设计

> 状态：已定 ｜ 版本：v1.0（2026-09-22）｜ 适用范围：`jp_project` 全部代码（server / miniprogram / checkout-static / admin-web）
> 来源：用户 2026-09-22 明确要求——**注释要详细，看注释就知道逻辑、缺点和优点**；**出问题能靠日志定位，必须能捕获代码运行信息与用户操作行为，不能缺有价值的分析数据**。
> 配套：《测试策略与验证门禁》《可扩展架构设计》《技术文档 v0.5》《工程框架 v0.5》
> ⚠️ 本文是**工程侧单一事实来源**；治理库只在 ADR-29 存索引与结论。

---

## 0. 一句话结论

> **注释写"为什么这么写、放弃了什么、还有什么坑"**（不是复述代码）；**日志做到"任何一个问题都能回答：谁、什么时候、哪个请求/订单、做了什么、结果如何、耗时多少"**，运行日志、业务审计、用户行为三条流分开且用同一个 `trace_id` 串起来。

# 第一部分：代码注释规范

## 1. 三条原则

| # | 原则 | 说明 |
|---|---|---|
| **C-1** | **注释回答 why，代码回答 what** | 不写"这里循环遍历订单"这种复述；要写"为什么必须先锁再查、为什么不批量、为什么阈值是这个数" |
| **C-2** | **缺点必须写** | 每段非平凡实现都要有 `@limitation`（已知缺陷/未覆盖场景）+ `@tradeoff`（放弃了什么、为什么）。**只写优点的注释视为不合格** |
| **C-3** | **注释可溯源** | 关键决策必须 `@see` 到 ADR / 技术文档章节 / 决策编号（如 `@see ADR-25`、`@see D-46`），让后来人知道这是有依据的，不是随手写的 |

## 2. 三层注释结构

### ① 文件头（每个文件必写）

```ts
/**
 * 职责：运费分档报价（重量 → 价格）
 * 边界：只做"取档 + 取整"，不做汇率换算、不做关税计算（关税见 pricing/duty.ts）
 * 依赖方向：domain 层，禁止 import 任何 adapter（ESLint no-restricted-imports）
 * @see 技术文档 v0.5 §2.5（口径）、D-46（取档方向事故）、ADR-28（扩展性：dest_country 维度）
 * @limitation 当前只按重量分档，未考虑体积重与偏远地区附加费（P2）
 */
```

### ② 函数/方法 JSDoc

标签固定集合：`@param @returns @throws @sideeffects @perf @security @see @limitation @tradeoff`

**示例（本项目真实高风险点）**：

```ts
/**
 * 按包裹总重取运费档位（整数円）。
 *
 * 逻辑：`max_weight_g` 是"档位上限（含）"，所以必须取**第一个 max_weight_g >= 包裹重**的档（向上取档）。
 * @see D-46 —— 模型曾长期用 VLOOKUP(…,TRUE) 向下取档，每单少收 900–1,000 円且静默不报错，属运营事故级。
 *
 * @param weightG 包裹实重（含包材，PACKAGING_WEIGHT_G=250 + 商品重量×件数）
 * @returns 该档 price_jpy（整数円）；无匹配档抛 NoRateError（调用方映射 50004）
 *
 * @tradeoff 单一 SQL 而非 ORM 条件构造：语义钉死在 SQL 里，杜绝"实现与契约漂移"（D-46 发现的第 2 个问题）。
 *          代价：换库要改 SQL，但本项目不换库。
 * @limitation 未做体积重（ dimensional weight ）：抛重包裹（保温杯空箱）会低估运费 → 每单可能少收一档。
 *             缓解：包材重量 250g 已含缓冲；真出问题在 shipping_rates 调档，不改代码。
 * @perf 单条主键范围查询 + LIMIT 1；加 (carrier, dest_country, max_weight_g) 索引后可走索引扫描
 */
```

### ③ 行内块注释（决策点才写）

只在这几处写：非常规写法、踩过的坑、看起来可优化但不能动的地方、魔法数字来源、并发/事务边界。

```ts
// 必须在事务内取 advisory lock：Render 多实例/重启时会有多个调度器，靠 Postgres 锁保证同一时刻只有一个 tick 生效（D-43）
// ⚠️ 不要用 pg_try_advisory_lock（会话级）：连接复用会让锁永不释放，必须事务级（D-45）
await sql`SELECT pg_try_advisory_xact_lock(${LOCK_KEY})`;

// 30 分钟是最短可设值：Stripe Checkout Session 的 expires_at 最短 30 分钟，低于它会被拒绝（D-49）
const expiresAt = max(addMinutes(now, 30), order.expiresAt);
```

## 3. 缺陷与待办登记（强制）

- 禁止裸 `TODO` / `FIXME` / `XXX`。格式：`// TODO(#I1-07, owner=向, due=2026-10-05): 体积重未处理，见 @limitation`
- 每条 TODO 必须同时在《任务看板》有对应行，注释里写编号，双向可查
- `@limitation` 允许无期限（属于"已知但不做"），但必须在文档中留痕，避免后来人以为遗漏

## 4. 同步纪律

- **改代码不改注释 = bug**（review 必查项，列进 DoD）
- 注释里引用的 ADR / 决策编号若被取代，必须同步改（`grep -E "ADR-1[0-9]|D-[0-9]+"` 定期扫一次）
- ESLint 规则：`jsdoc` 插件只强制**导出函数**必须有 JSDoc；内部小函数不强求，避免注释噪声

# 第二部分：日志体系设计

## 5. 目标（出问题时的六个必须回答）

> 谁（user/openid/admin）｜何时（ts）｜哪个请求/订单（`trace_id` / `req_id` / `order_id`）｜做了什么（`event` + 入参摘要）｜结果（status / err）｜耗时（duration_ms）

做不到这六条的日志，视为没记。

## 6. 三条日志流（严格分开，不混用）

| 流 | 用途 | 载体 | 保留 | 采样 |
|---|---|---|---|---|
| **A. 运行日志** | 排查故障：HTTP 进出、外部调用、慢查询、异常 | `pino` JSON → stdout（Render） + Sentry（error 聚合，`beforeSend` 脱敏，D-52） | 平台 7–30 天 | 全量（生产 info+） |
| **B. 业务审计日志** | 不可否认定责：状态迁移、支付回调、退款、拒付、改价、上下架、管理员操作 | **DB `order_events`**（事实来源）+ `admin_audit` 表 | 永久 | 100%，禁止采样 |
| **C. 用户行为日志** | 转化分析：浏览/搜索/加购/下单/支付入口点击/复制链接/支付结果 | DB `user_events` 表 + 小程序 RealtimeLogManager | ≥12 个月 | 高频浏览可采样，**下单与支付 100%** |

## 7. 字段约定（统一，不许各自发明）

```jsonc
{
  "ts": "2026-09-22T10:00:00.123Z",   // ISO8601，UTC
  "level": "info",                     // debug|info|warn|error
  "msg": "order.pay.create",
  "trace_id": "01J…",                  // 一次用户操作贯穿：小程序 → API → DB → 回调（回调侧靠 order_id 回填）
  "req_id": "01J…",                    // 单次 HTTP（中间件生成，响应头回传 X-Request-Id）
  "user_id": "u_01J…",                 // 内部用户 ID（不写 openid 明文）
  "actor": "user|admin|system|provider",
  "order_id": "o_01J…", "order_no": "W20260922XXXX",
  "channel": "mock|stripe|wechat",
  "module": "payment", "event": "create_payment",
  "duration_ms": 128,
  "result": "ok|error|ignored", "code": 0,
  "err": { "type": "StripeApiError", "message": "…", "stack": "…" },   // 仅 error
  "ctx": { "amount_jpy": 12800, "currency": "USD", "attempt": 1 }      // 业务关键入参，禁止放敏感值
}
```

**小程序端**：`utils/request.ts` 统一注入 `X-Trace-Id` + `X-Request-Id`；关键行为上报 `POST /beacon`（批量、失败静默重试）；`wx.getRealtimeLogManager()` 打实时日志（线上问题可查，需真机）。

## 8. 脱敏红线（写进 lint 与 review）

| 禁止记录 | 允许记录 |
|---|---|
| `APP_SECRET`、JWT 原文、`Idempotency-Key` 原文、Stripe `whsec`、密码 | 它们的**校验结果**（ok/fail） |
| 卡号 / CVV / 完整邮箱 / 完整电话 / 完整地址 | 掩码：`a***@gmail.com`、`+1***1234`、只记城市与州 |
| openid 明文 | 内部 `user_id`；确需时截断前 8 位 |
| 回调**原始报文**（含签名与个人信息） | 事件类型、`provider_ref`、`transaction_id`、验签结果、处理结论 |

统一走 `redact()` 工具（一处定义、全局调用），Sentry `beforeSend` 复用它（D-52 已要求脱敏，此处补实现口径）。

## 9. 必记事件清单（缺一条视为日志缺失）

| 类别 | 事件（`event` 名） | 级别 | 落 DB |
|---|---|---|---|
| HTTP | `http.request` / `http.response`（含 status、duration、req_id） | info | — |
| 认证 | `auth.login.ok/fail`、`auth.admin.login.fail`（含 IP，用于限流与风控） | info/warn | — |
| 商品 | `catalog.view`、`catalog.search`（含关键词）、`catalog.detail.view` | info | C |
| 购物车 | `cart.add` / `cart.remove` / `cart.quote`（含件数、重量、运费档） | info | C |
| 订单 | `order.created`（含金额、件数、terms_version）、`order.status_changed`（from→to）、`order.expired` | info | B |
| 支付 | `pay.create`（channel/amount/currency）、`pay.callback`（事件类型 + 验签结果 + 处理结论）、`pay.callback.duplicate`、`pay.callback.late`、`pay.refund`、`pay.dispute` | info/warn | B |
| 外部调用 | `ext.stripe.call`、`ext.wechat.call`（含 duration、retry、失败原因） | info/warn | — |
| 调度器 | `job.tick.start/end`（含 job_runs 心跳、子任务耗时、失败子任务） | info | B(`job_runs`) |
| 管理端 | `admin.*`（改价 / 上下架 / 发货 / 退款 / 改汇率 / 拉黑）——**记 actor + 改前改后值** | info | B(`admin_audit`) |
| 异常 | 任何未捕获异常（含 stack、trace_id） | error | Sentry |
| 慢 | DB > 200ms、外部 HTTP > 2s | warn | — |

## 10. 可查询性（让日志真的能用）

- **订单时间线页（admin-web）**：一屏看全 `order_events` + `payments` + 相关运行日志摘要（按 `trace_id` 过滤），客服/排障第一入口
- **管理端审计页**：按 admin、时间、对象查 `admin_audit`
- **转化漏斗**：`user_events` 预置查询（浏览 → 详情 → 加购 → 建单 → 支付成功），周会看
- **告警**：`error` 级 5 分钟内 > N 条、支付回调连续失败、调度器心跳超时（job_runs 无更新）→ Sentry / 邮件

## 11. 与测试门禁的接口（T-1/T-3 的一部分）

- 关键路径测试**必须断言日志/事件落库**：建单产生 `order.created`、回调重复只产生一条入账事件、拒付产生 `pay.dispute`、管理改价产生 `admin.*` 且含改前改后
- 脱敏测试：`redact()` 单测断言——喂入含邮箱/电话/openid/secret 的对象，输出不得出现原文（分支覆盖 100%）
- 结构化测试：断言日志可被 JSON 解析且必填字段齐全（`trace_id` 不为空）
- 注释纪律进 DoD：PR review 检查"改了逻辑是否改了注释、是否有 @limitation"

## 12. 落地时序（小步）

| 优先级 | 内容 |
|---|---|
| **P0（第 0 步，与测试基础设施同批）** | `logger.ts`（pino + 字段约定）+ `redact.ts` + 请求中间件（`trace_id`/`req_id`）+ 文件头/JSDoc 模板 + ESLint jsdoc 规则 |
| **P1（I1 内）** | `user_events` / `admin_audit` 两张表 + `/beacon` 接口 + 必记事件清单逐条接入（每接一条配一条测试断言） |
| **P2** | 订单时间线页、审计页、转化漏斗查询、告警规则 |
