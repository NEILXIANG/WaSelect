## 四、P1（MP3-04）的完整修改方案与落地

### 4.1 问题

买家在 Stripe 托管页付完款 → 切回微信**只要几秒** → `checkout.session.completed` 常常还没到。
此刻我方库里订单 `pending_payment`、支付行 `initiated`，**每一处本地判定都合法**：

- 取消 → 关单 + 回补库存；
- 几秒后通知到达 → 判成 **迟到付款** → 转对账、**人工退款**，而货可能已被别人买走。

银行卡是当前唯一付款路径，所以这不是理论问题。

### 4.2 方案（前端标记 + 服务端兜底，两条都要）

| 层 | 做法 | 为什么必须两层 |
|---|---|---|
| 小程序 | 支付页微信支付 `success` 跳详情带 `justPaid=1`；详情页 vm 在 `justPaid` 且仍可付时 `canCancel=false` / `canPay=false`，显示"支付结果确认中，请稍后刷新"；薄壳**最多退避重查两次**后放弃假设、恢复按钮 | 标记是**事实**（"谁刚付过"只有支付页知道，从订单数据推不出来），但**可丢失**（用户绕路从订单列表进详情就没有了） |
| 服务端 | 新增端口能力 `supportsSessionQuery` + 可选方法 `sessionStatus()`；取消前在**事务外**查一次：`paid` → 40902 `payment_already_paid`；`processing` → 40902 `payment_in_flight`；查不到 → 50300（fail-closed） | 它是**兜底**（任何入口都挡住），但要一次出站 HTTP，**绝不能进事务**——持锁等外部调用是 ORD3-02 的同型缺陷（那时点取消的人会拿到 50000） |

**三值而不是布尔**：`paid / unpaid / processing`。二值会逼着把"不确定"并进 `unpaid`（= 允许取消），**那正是这个洞本身**。
**`unpaid` 直接放行而不是一律保守**：Stripe 对卡支付**同步**翻转 `payment_status`，所以"付了但通知没到"查出来就是 `paid`；
判 `unpaid` 放行的都是真没付。若一律保守成 processing，"建了会话没付款的人也取消不了"——
那是把防洞的补丁变成**日常可用性的倒退**（订单要等 30 分钟才自动关）。

### 4.3 涉及文件

- `server/src/ports/payment.ts`：`SessionStatus` / `supportsSessionQuery` / `sessionStatus()`
- `server/src/adapters/payment/registry.ts`：声明与实现**同进同退**的一致性检查（注册期炸，不是用户点取消时炸）
- `server/src/adapters/payment/stripe-checkout.ts`：`sessionOutcome()` + `sessionStatus()`（唯一实现者）
- `server/src/adapters/payment/mock.ts`：**不声明**该能力（in_app 通道机构侧没有可查对象）
- `server/src/app/cancel-order.ts`：`assertNoPaidSession()`
- `server/src/app/order-routes.ts` / `mount.ts`：`registry` 变成订单路由的**必填**依赖
- `server/src/app/cancel-paid-session.db.test.ts`（新，7 条）
- `miniprogram/pages/order-detail/{index.vm.js,index.js,index.wxml}`、`miniprogram/pages/pay/index.js`
- `test/helpers/fake-stripe-http.ts`：`setSessionPaymentStatus()`

### 4.4 残余风险（明确写出来，不夸大）

1. **毫秒级残余窗口**：查完"未付"到取消事务提交之间仍可能完成支付。彻底堵死需要
   "取消时把支付行推进到 `closing`、由回调裁决"的两阶段协议（I2 改造）。
   残余窗口的兜底是既有的 `late_payment` 告警 + 人工退款（我核过 `mark-paid.ts` 的 @limitation 一b：
   已关成 `cancelled` 之后到账同样按迟到付款处理，转对账）。
2. **机构故障时取消被拒（50300）**：用户点不动取消，但订单 30 分钟后自动关单，**不会永久卡住**。
3. `justPaid` 是**假设**：付款其实没成时，两次复核（约 4.5 秒）内按钮不可点，之后自动恢复。

## 五、OPS3-03（退款在途 + 拒付）的修法与取舍

- **改法**：`refundGuard` 里 `refunding` 判定移到拒付判定**之前**；
  `refund-execution.ts` 新增 `hasDispute` 入参，**只在 `attempt > 0`（这一把是新键）时**抛 40907，
  且放在"记录确认失败**之后**"（那笔失败是事实，`attempt` 必须进位，否则下次会拿同一把键去撞一个已确认失败的单号）。
- **为什么拦点必须跟着"新键"走**：`refundGuard` 只看 `status × has_dispute`，**看不出这一把是不是新键**
  （那在 `findRefundProgress`）。会动第二笔钱的只有换键那一步。
- **反向风险（已入档）**：拒付在途时同键重放仍可能把退款落定 → 买家**既拿到退款又赢了拒付**。
  选它是因为另一个方向的后果更硬：订单**永久卡在 refunding 且没有任何出口**；
  而这条路钱只动一次、`has_dispute` 仍在、对账看得见。
