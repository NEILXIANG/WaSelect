# 工程实现缺点分析（自评 + 对 WorkBuddy 报告的逐条核验，2026-10-08）

> 性质：**只分析，不改代码**。范围：server / admin-web / miniprogram / packages / scripts / render.yaml / deploy / CI。
> 依据：逐条回到代码与配置核实（文件:行号），并结合当天三端联动走查（《三端联动走查报告-2026-10-08》）的实际观察。
> 对照对象：WorkBuddy《工程实现缺点分析-2026-10-08》（下称"WB 报告"）。

---

## 一、结论先说

1. **代码层纪律强，运行态有短板**——这一点我同意 WB 报告。但 WB 报告有 **9 处与仓库现状直接矛盾**（见第四节），
   其中 2 条建议**照做会出事故**：生产用 Stripe test key 演练会被 config 拒启；构建末尾加 `npm prune --omit=dev` 会删掉迁移工具。
2. 我独立找到 WB 报告**没有提到**、但对本项目更要紧的一条：**订单邮件可能丢**——事件总线进程内、发后不等、没有 outbox，
   而邮件是买家目前**唯一**的通知渠道（订阅消息未做）。部署或崩溃恰好落在"提交后、发信前"，那封发货 / 退款邮件就永远不会发。
3. "单实例"不只是调度器一件事：**限流计数也在进程内存**。扩到两台时调度器重复、限流额度翻倍，两件必须一起改。

## 二、坐标系（决定优先级）

单商户、日百单量级、审核期（生产跑 mock + REVIEW_MODE）、一人 + AI 维护、Render 单实例 + Cloudflare 静态站。
在这个坐标系下，**"钱对不对"与"买家知不知道"优先于"可用性 9 的个数"**；扩容、压测、APM 都是"上量前"的事。

## 三、我的独立发现（按对本项目的伤害排序）

### P0（上线前应处理或至少有对策）

**E-1 订单通知邮件可丢失（无 outbox）**
- 证据：`server/src/adapters/event-bus.ts` 文件头 @limitation 一/二——"进程内、内存态……已提交但还没分发完的事件会丢"、"发后不等"；
  同文件 `@upgrade` 写了 outbox 升级路径但未做。邮件订阅者经事件总线触发（AJ-369）。
- 为什么是 P0：小程序订阅消息未做（受 AppID 阻塞），**邮件是付款 / 发货 / 退款的唯一主动通知**；
  丢一封发货邮件 = 买家不知道已发货、不知道运单号（订单详情页能查，但买家不会主动去看）。
- 对策（按成本）：① 最小：发信记录落表（谁、哪个事件、成功否），daily 作业补发未成功的；② 标准：`outbox_events` 同事务写 + 投递 worker 重试。
- 局限：Resend 端的退信 / 投诉不回调（`mail/resend.ts` @limitation），"发出去了但没送达"仍看不见。

**E-2 真支付通道"生产首验"，且生产无法用 test key 演练**
- 证据：`render.yaml:118-131`（生产 `PAYMENT_CHANNELS: mock`、`REVIEW_MODE: 'on'`）；`server/src/config.ts:966-975`（生产必须 `sk_live_`）。
- 已有的：`docs/上线运维手册-首次部署·回滚·审核期切正式.md` §3 切换步骤（真卡小额下单、回调、退款核对）、§4 回滚；config 跨字段校验齐全（三键必填 + 前缀）。
- 缺口：test mode 的全链路只能在**非生产环境**跑，而部署层没有 staging（见 E-3）。所以真正的"首次真实回调"仍在生产。
- 对策：上线切换前开一个临时 staging（同 Blueprint、`NODE_ENV=staging`、Stripe test key）跑一遍"建单 → 回调 → 入账 → 部分退款 → 对账"，跑完可关。

**E-3 部署层没有 staging（代码层已支持）**
- 证据：`render.yaml` 只有 web / cron / admin / 一个库；`config.ts:261` 已支持 `NODE_ENV=staging`，`config.ts:939` 等有 staging 专属规则。
- 影响：`render.yaml:71` 自认 `TRUST_PROXY_HOPS` 没有 @measured，"staging 实测 XFF 之前不许改"——上 Cloudflare 前置这一步注定要在生产首验。
- 对策：同 E-2，按需临时开、用完关；优先验 preDeploy 迁移顺序、XFF 跳数、源站校验头、优雅停机摘流。

### P1（影响排障效率或上量前必须做）

**E-4 单实例的隐性耦合有两处，扩容要一起改**
- 调度器在 web 进程（`render.yaml:53-56`、`main.ts:324-335`；advisory lock 防多跑不防单点）。
- **限流计数在进程内存**（`server/src/adapters/rate-limit-memory.ts` @limitation 一："多实例即失效……实际限额变成 2× 配置值"）。WB 报告未提。
- 另有 mock 支付会话 Map（`adapters/payment/mock.ts`，审核期用，影响小）。
- 对策：在技术债清单里把三者写成**同一个触发条件**（"实例数 > 1 之前"），避免只拆了调度器、忘了限流。

**E-5 前端错误不可见**
- 管理端：无 ErrorBoundary（`admin-web/src/router.ts:88` 自述），无前端 Sentry——白屏只有运营报障才知道。
- 小程序：无 `App.onError` 上报；`app.js:111` 只把 api_ok / api_failed 写进微信实时日志（WB 报告漏了这条部分可见性）。
- 对策：管理端加 ErrorBoundary + 把错误打到现有 `/beacon` 或 Sentry；小程序 `App.onError` / `onUnhandledRejection` 走实时日志 + beacon。

**E-6 运行日志无长期留存**
- 证据：`render.yaml` 无 log drain；审计（流 B）与行为（流 C）落库，但运行日志（流 A）只在 Render 面板按档位保留。
- 对策：Render log drain 到外部免费档（纯配置）。

**E-7 本地联调的环境开关不在仓库里**（走查实测）
- 现象：sim 环境 `REVIEW_MODE=off` 且未开 `MOCK_AUTO_CONFIRM` 时，小程序内模拟支付走不通（`pay-plan.js` 判 unsupported）；
  当天靠临时启动脚本（不在仓库）打开 `MOCK_AUTO_CONFIRM=on` 才走通。
- 影响：下一个人（或下一次的我）照 README 起本地环境，会在付款这一步卡住且以为是 bug。
- 对策：`scripts/dev-up.ts` 增加"联调模式"开关或在 README 写明；`.env.example` 注释里点名这个组合。

**E-8 契约只验请求侧上限，不验响应形状**
- 已有：`check-contract.mjs`（错误码 / 枚举双向比对）+ `server/src/contract-document.contract.test.ts`（js-yaml 真解析、`$ref` 可解、路由集合、约 10 个请求字段上限）。
- 缺口：响应字段改名 / 删字段没有机械检查——当天就踩到一次同类问题（同类推荐按详情的 `images[]` 读列表的 `image`，测试数据也按错的形状写，模拟器里才发现）。
- 对策：关键响应（Product / ProductCard / Order / OrderListItem）在路由集成测试里用契约 schema 校验一次。

## 五、不建议做（与 WB 报告一致处略）

- **不要**为"多实例"提前引入 Redis：E-4 的三件在单实例下都是正确的，提前引入是多一种故障形态。写清触发条件即可。
- **不要**在生产环境做任何 test-mode 演练：config 的拒启是对的（配错 key = 真实用户付不了款）。
- **不要**为契约响应校验上全量代码生成（openapi-typescript 等）：先在关键 4 个响应上做 schema 校验，性价比最高。

## 六、建议顺序（仅排序，本文不改代码）

1. **上线前**：E-1 发信记录 + 补发（最小版）；E-2/E-3 临时 staging 跑一遍真通道 test mode；E-5 管理端 ErrorBoundary + 小程序 onError；E-6 log drain。
2. **上 Cloudflare 前置前**：E-3 staging 实测 `TRUST_PROXY_HOPS`。
3. **实例数 > 1 之前**：E-4 三件一起改（调度器拆 worker、限流换共享存储、mock 会话外置或确认审核期结束）。
4. **顺手**：E-7 本地联调开关进仓库；E-8 关键响应 schema 校验；E-11 CI 拆分。
