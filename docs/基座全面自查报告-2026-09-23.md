## 2. 定级口径（本次自查的自主定义，已入档 AJ-25）

- **P0 正确性**：会导致算错钱、丢数据、越权、或绕过验签/鉴权的缺陷。
- **P1 健壮性**：特定但**现实会发生**的故障/配置组合下行为错误（错误码语义错、资源泄漏、启动校验缺位），现有测试抓不到。
- **P2 架构债**：有已定设计（ADR-28/29、清单 v1.2）但代码未落位；或现有实现与已定设计方向冲突。判 P2 的前提是"业务代码开写前必须解决，否则债随代码量利滚利"。
- **P3 优化**：不影响行为，但会误导后来者（陈旧注释）、放大维护成本（脆弱正则）、或留下慢性风险（无界缓存）。

**发现的问题**：

- **P2-1（配置表缺口）**：ADR-28 要求的 4 张配置表（`country_profiles` / `payment_channels` / `duty_rates` / `app_config`）未建，`shipping_rates` 无 `dest_country` 列。这是"表 13→17"口径变更，按治理规则需先改技术文档 v0.6 + 契约 0.6.0 确认。**当前所有"运行时改配置不发版"的能力都没有落点**——F3 设计的三层配置（默认值→环境变量→app_config 表）只实现了前两层。

- **P3-1（配置下限）**：`config.ts:174` `PACKAGING_WEIGHT_G: int(250, 0)` 允许 0——包材 0 克在业务上无意义，且会让运费取档向下偏一档（D-46 的方向性错误同源）。应改下限 1。

### 3.2 维度二：代码结构与错误处理（P1 集中在这里）

- **P1-1（auth.ts:227，错误折叠）**：`requireRole` 的 `.catch` 把**所有**非 AppError 折叠成 40101。`verifyToken` 自己的失败已转成 AppError，所以能漏进这个分支的非 AppError 只剩两类：`identity.load()` 的数据库异常、或代码 bug。**后果**：DB 抖动/连接池耗尽时，每个带 token 的请求都收到 40101，前端按 action"静默重新登录并重放"——形成**全站无限重登风暴**，且日志里没有任何 500 告警指向真正的 DB 故障。修法：非 AppError 原样透传（全局兜底会折叠成 50000 + 完整日志）。
- **P1-2（config.ts:202，跨字段缺位）**：`CHECKOUT_BASE_URL` 是纯 optional。D-49 的 H5 收银页依赖它拼支付链接；生产启用 stripe 而漏配它，症状是"小程序外支付链接拼不出来"——运行时才暴露。应在 crossField 补：`isProd && channels含stripe → CHECKOUT_BASE_URL 必填`。
- **P1-3（http.ts:138/228，前缀误匹配）**：CORS `pathPrefixes` 与 `rawBodyPaths` 用 `req.path === p || req.path.startsWith(p)`。`/api/v1/adminx` 会匹配 `/api/v1/admin`；未来若新增 `/api/v1/pay/callback/mock-v2` 这类路径，会被当成 raw-body 路由，`req.body` 变成 Buffer，handler 静默拿到错类型。修法：补分隔符判定 `p + '/'`。
- **P1-4（main.ts:118，密钥复用）**：mock 回调的 `callbackSecret` 直接复用 `JWT_SECRET`。骨架期可接受（mock 进不了生产，SEC2 闸门），但 F11 接真实通道时**每通道必须独立密钥**——若把这个先例带进 Stripe/微信适配器，一次 JWT 密钥轮换会让所有回调验签失效，且回调密钥与登录密钥的泄露半径应当不同。修法：现在就在 config 里把 `CALLBACK_SECRETS` 按通道分键，mock 用独立默认值。
- **P3-3（http.ts:462，陈旧注释）**：`ShutdownHooks.beforeDrain` 的 @limitation 写着"本仓库目前还没有 `/readyz`"——但 `/readyz` 在 251 行已实现且 main.ts 已接线。违反"改代码不改注释 = bug"的自家纪律。
- **P3-4（http.ts:436–441，sweeper 泄漏）**：`closeServer` 超时分支 `settled = true` 后 `reject`，**没有 `clearInterval(sweeper)`**；`done()` 在 `settled` 时早退也不清。正常路径无问题，超时路径每秒 10 次的 interval 会挂到进程退出。生产超时后进程本就退出，危害低；但测试里会留 open handle。

### 3.5 维度五：工程架构（分层 / ports-adapters / 可插拔）

- **P2-7（F10 分层未建，最高杠杆）**：`server/src` 当前是 12 个扁平文件，没有 `domain / ports / adapters / app` 目录，ESLint 没有依赖方向规则。ADR-28 的依赖单向（app→domain→ports←adapters）目前**只靠自觉**。今天"在 domain 里 import 一个 adapter"不会红——清单 F10 的验收标准（import 必须报红）尚未达成。**业务代码开写前必须完成**：每多一个业务单元，回头分层就多一份成本。
- **P2-8（F11 注册表未建）**：支付目前只有硬编码的 `/pay/callback/mock` 一条路由（skeleton.ts:62），没有 Provider 接口、没有注册表、没有 `/pay/callback/:channel` 分发、没有 `GET /pay/channels`。加第二个通道（Stripe）今天的成本 = 改 skeleton + 改 main 装配 + 改 config + 改契约，且业务核心会认识"mock/stripe"这两个具体通道——正是 ADR-28 要消除的耦合。
- **P2-9（F9 假数据工厂半成）**：rng + 美国地址 manifest 已完成，但实体工厂（entities/catalog/stripe fixture）只建了骨架，订单域/支付回调域的形态清单未注册（已知未登记形态：乡村路线 RR、酒店代收、宿舍、监狱信箱）。F9 是业务期测试的数据基础，应在业务单元开写前补完。

### 3.6 维度六：对业务的灵活支持度（扩展成本矩阵）

按 ADR-28 的目标形态，逐项评估"今天做这个扩展要动多少地方"：

| 扩展动作 | 目标成本（ADR-28） | **今天的实际成本** | 差距根因 |
|---|---|---|---|
| 加一个支付通道 | 注册 Provider + 配置表加一行，不发版 | 改 skeleton 路由 + main 装配 + config 枚举 + 契约，发版 | F11/配置表未建（P2-8/P2-1） |
| 加一个收货国家 | `country_profiles` 加一行 + 运费/关税表加行 | **改 DB CHECK**（见下）+ 改契约 + 改 shared COUNTRY 枚举，发版 | 地址格式校验写死在 DB |
| 加一个产地国 | `products.origin_country` 放开 | 改 `products_origin_jp` CHECK（D-43 刻意，MVP 不动 ✅） | 计划内 |
| 改首页区块/主题 | 改配置 | 改 WXML/WXSS 代码，发版 | F14 延后项（设计允许） |
| 加错误码 | shared + 技术文档 + 契约三处 | 同左，且 gate 会拦漏改 ✅ | 已达标 |
| 加订单状态 | 改状态机迁移表 | shared 枚举 + DB CHECK + 契约 + switch 全改（lint 会逼你改 ✅） | 部分达标 |

- **P2-10（地址格式写死在 DB CHECK，多国家最大硬点）**：`migrations/001_init.sql:31-37` 把美国地址格式编译进了 CHECK：`phone ~ '^\+1[0-9]{10}$'`、`postal_code ~ '^[0-9]{5}(-[0-9]{4})?$'`、`recipient/line1/city ~ '^[ -~]+$'`（纯 ASCII）。加第二个国家 = 一次 expand/contract 迁移 + 所有既有行的校验口径变更，与 ADR-28"国家 = 配置"的目标直接冲突。AJ-07 已裁定 `state`/`country` 不在 DB 层加 CHECK（F-A1 有表征测试），**同理建议**：业务期把格式校验整体上移到应用层（按 `country_profiles` 驱动），DB 只留非空与长度约束。**此项涉及表结构口径变更，列入待用户确认。**

**灵活度的另一面（已达标的）**：金额/汇率取整/订单号/业务日/错误码/状态枚举全部集中在 shared 且纯函数——这些是"每个业务单元都会用"的东西，只有一份实现，扩展不会发散。这是地基最值钱的部分。
