## 三、P1 问题（8 条）

### A1｜管理员登录锁定可被并发突发越过，锁定后正确口令仍能登录

- **来源**：SEC-01、DB-01（两片独立发现）
- **位置**：`server/src/app/admin-auth-routes.ts:74-113`；`server/src/adapters/admin-auth.ts:61-88`；`migrations/014_admin_login_lockout.sql:6-7`（注释）
- **问题**：锁只在请求开头读一次（`findAdminCredential` → `lockedUntil > now`），随后做约 100ms 的 bcrypt，最后才 `recordLoginFailure` 计数。计数的 UPDATE 本身没有"未锁定"条件，锁定时还会把计数归零；成功路径 `recordLoginSuccess` 无条件清锁。于是同一批并发请求全部越过锁闸，正确口令只要落在这一批里就能拿到 token 并顺手清掉锁。
- **证据**：
  ```ts
  const cred = await findAdminCredential(deps.db, email);                  // 只在这里读锁
  if (cred?.lockedUntil != null && cred.lockedUntil > now) { … 42901 }
  const ok = await verifyPassword(password, cred?.passwordHash ?? DUMMY_HASH); // ~100ms
  … await recordLoginFailure(deps.db, cred.id, now, …)                      // 事后计数，无锁定条件
  await recordLoginSuccess(deps.db, cred.id);                               // 无条件清锁
  ```
  探针（关闭 IP 限流以隔离账号维度）：60 个并发错误口令中有 18 次口令校验穿过锁闸（设计上限 5）；20 个 IP 各发 1 次、第 13 个是正确口令，连跑 3 次都返回 200。
- **后果**：头注释和 AJ-181 所说"口令爆破在账号维度被封顶"不成立。攻击者用 N 个出口（正是注释要防的住宅代理池）每 15 分钟可试 N 次，上限只剩服务器的 bcrypt 吞吐；大量 bcrypt 同时压满 0.5 核实例，拖慢全站。
- **解决方案**：改成"先扣次数、再比对"。在 bcrypt 之前执行一条带条件的原子 UPDATE：`where id=$id and (login_locked_until is null or login_locked_until <= $now)`，返回 0 行即 42901 且不做 bcrypt；成功清零也带同样条件，0 行同样 42901。失败分支不再单独计数。与 B14（邮箱枚举）一并改时，可把锁定键改为 `sha256(lower(email))`，不存在的邮箱也计数、也上锁。
- **测试**：db 测试在关闭 IP 限流时并发 30 个错误口令 + 1 个正确口令，断言 401 不超过 5 条、其余 42901、正确口令拿不到 token；注回"先读后判"必须变红。
- **置信度**：已探针证实（两片各自复现）｜**新发现**（AJ-181 的依据只证明"会锁一次"，没证明"封顶"）

### A2｜限流取到的是 Cloudflare 边缘 IP：全站限流桶被同一 PoP 的用户共用，管理员登录可被他人锁死

- **来源**：SEC-02、INF-05；关联 SEC-07（IPv6）
- **位置**：`render.yaml:60-61`（`TRUST_PROXY_HOPS=1`，注释"Render 前置一层反代"）；`server/src/config.ts:224`；`server/src/http.ts:223`；`server/src/app/rate-limit.ts:92`
- **问题**：jp《技术文档》§5a 写明"api 前挂 Cloudflare 代理"（第 611 行），每日作业一节还专门讨论了 Cloudflare 524 上限（第 705 行）；契约 `/internal/jobs/daily` 同样写"经 Cloudflare 代理"。在"客户端 → Cloudflare → Render 反代 → 应用"的拓扑下，XFF 为 `client, cf-edge`，`trust proxy = 1` 取到的 `req.ip` 是 Cloudflare 边缘节点。
- **证据**：探针 `X-Forwarded-For: 198.51.100.7, 172.70.1.1`、hops=1 → `req.ip = "172.70.1.1"`。"Render 前一层 = 1"这个数没有任何 `@measured` 记录。
- **后果**：五个按 IP 限流的入口（报价、建单、发起支付、微信登录、短链）每分钟 30 次的配额由同一 PoP 的全体买家共享，中等流量就会成片返回 42901；管理员登录 5 次/15 分钟按边缘 IP 计，同 PoP 任何人连发 5 次即可把经同一出口的真管理员挡在外面；访问日志的 `client_ip` 失去意义。反过来，如果改成 2 而源站 `*.onrender.com` 仍可直连，直连者伪造的 XFF 又会被采信。
- **解决方案**：先定拓扑（api 是否走 Cloudflare 代理）。若走：`TRUST_PROXY_HOPS=2`，同时让源站只接受来自 Cloudflare 的请求（例如 Cloudflare Transform Rule 注入密钥头、http.ts 校验，缺头即拒或至少不采信 XFF）。在 staging 用已知出口 IP 实测一次 `x-forwarded-for` / `socket.remoteAddress` / `req.ips`，把真实输出写进 config.ts 与 render.yaml 的 `@measured`。schema 默认值改为 0（宁小勿大），生产由 render.yaml 显式给值。顺带把 IPv6 限流键收敛到 /64（B18）。
- **测试**：http 单测覆盖 XFF 为 `client, cf` 且 hops=2 时 `req.ip = client`。
- **置信度**：**疑似**——Express 取值行为已探针证实，拓扑有文档证据，Render + Cloudflare 下真实 XFF 形态尚未实测。之所以仍列 P1：若拓扑如文档所写，上线第一天就会出现大面积 429 与管理员登录被锁。｜**新发现**

### A3｜取消订单 / 批量关单回补库存与建单仍会死锁（40P01）

- **来源**：ORD-01
- **位置**：`server/src/adapters/orders.ts:206-213`（`restoreStockForOrder`）；`server/src/app/cancel-order.ts:61`；`server/src/app/expire-orders.ts:59-67`；对端 `server/src/app/create-order.ts:176-186`
- **问题**：2026-09-26 的 P1 修复让建单按 product_id 排序加锁，但回补库存用的是 `UPDATE products … FROM order_items`，加锁顺序跟随执行计划与插入序，且关单作业在**一个事务里**跨多张订单逐单回补。回补路径与排序后的建单路径之间仍然形成 AB/BA 互等。create-order.ts:179 的注释"统一顺序后只会排队不会互等"只对"建单对建单"成立。
- **证据**：
  ```ts
  update products p set stock = stock + oi.qty, updated_at = now()
    from order_items oi where oi.order_id = ${orderId} and oi.product_id = p.id   // 无序
  for (const id of ids) { if (await markOrderExpired(...)) await restoreStockForOrder(ctx.tx, id); }
  ```
  探针在小表（Seq Scan + Nested Loop）与批量数据（索引 Nested Loop）两种计划下都复现了 `cancel: 40P01 deadlock detected`；关单批 X1=[B]、X2=[A] 与建单 A→B 并发，复现 `expire job: 40P01`，**整批回滚**。
- **后果**：取消或建单返回 50000；关单整批回滚、推迟到下一轮，tick 记失败；批次越大持锁越多、冲突越频繁。建单处在幂等执行器 `lock_timeout ≤ 2s` 预算内，等锁超时的 55P03 同样变成 50000（见 B6）。
- **解决方案**：回补前按确定序预锁：`select id from products where id in (select product_id from order_items where order_id = any($ids)) order by id collate "C" for update`（`collate "C"` 与 JS 侧 `compareProductIdForLock` 的码元序一致；生产库排序规则未知，不加会出现两种锁序）。关单作业改为：先对本批全部 `markOrderExpired`，收集真正迁移成功的 id，一次性排序预锁全部相关商品，再回补。建单遇 40P01 可在执行器外整体重试一次（pendingEvents 在 createOrder 返回后才写，重试安全）。
- **测试**：db 并发用例——建单（A→B）对取消（插入序 [B,A]）、对关单批（X1=[B], X2=[A]）各 20 轮，要求零 40P01。分片已用 `fix-probe` 验证修法：两种计划下均无死锁。
- **置信度**：已探针证实｜**新发现**（上次 P1 修复的遗漏面）

### A4｜拒付金额只要不等于扣款全额就拒绝落库：部分拒付、汇率波动拒付、退款后拒付全部"看不见"

- **来源**：PAY-01、TSA-03
- **位置**：`server/src/app/mark-disputed.ts:219-257`；`server/src/app/mount.ts:156-164`；测试 `mark-disputed.db.test.ts:461-466`（把当前行为钉成期望）
- **问题**：`markOrderDisputed` 取 `status='succeeded'` 的支付行，并要求 `charge_amount === d.amountMinor`，否则抛 `amount_mismatch`。Stripe 官方对 `Dispute.amount` 的说明是"通常等于扣款额，但可能不同（通常因为汇率波动，或只对部分订单发起争议）"。已退款的单（支付行是 `refunded`）来拒付时落到 `no_succeeded_payment`。
- **证据**：
  ```ts
  where order_id = ${orderId} and status = 'succeeded'            // 223
  if (Number(p.charge_amount) !== d.amountMinor) { throw … 'amount_mismatch' }   // 251
  ```
- **后果**：外币卡持卡人发起拒付、金额差几美分，或只争议部分货品时：管线记 `mismatch:amount_mismatch` + error 日志、返回 200，Stripe 不再重发；`has_dispute` 仍为 false，发货闸门不拦，自动签收/完成照走；风控页看不到这条拒付，举证期限只能靠人从对账里发现；随后的退款被 Stripe 以 `charge_disputed` 拒绝，订单卡在 refunding。
- **解决方案**：币种不符仍拒；金额不同照常落库（`dispute_amount` 本来就单独存，按机构报的金额写），另打 `dispute_amount_differs`（金额大于扣款额时升为 error）；取支付行改为 `status in ('succeeded','refunded')`；从 `DISPUTE_MISMATCH_REASONS` 移除这两种情形，同步契约 `Dispute.dispute_amount` 描述。
- **测试**：部分拒付 → `has_dispute=true` 且 `dispute_amount` 为部分值；金额大于扣款 → 落库 + error；已退款单来拒付 → 落库；`stripe-golden-chain` 增加部分金额样本。现有"金额不符 → 40902"的用例改写。
- **置信度**：已读代码证实，有官方文档佐证｜**新发现**

### A5｜结算页每次点提交都生成新幂等键：超时重试或连点会建出两张订单

- **来源**：MP-01、TSB-01
- **位置**：`miniprogram/pages/checkout/index.js:17-19`（注释）、`:197-202`、`:204-229`；`miniprogram/pages/pay/index.js:118-123`；`miniprogram/utils/idem-key.js`

### 4.3 安全、鉴权与审计

**B14｜换一个出口 IP 就能用"429 还是 401"判断某邮箱是不是管理员**（SEC-03；已探针证实；AJ-181 ⑥ 已登记但描述有误）

**B15｜管理端审计挂在 `finish` 上：客户端在业务提交后断开，操作不留审计也不留日志**（SEC-04；关联 INF-14；已探针证实；新发现）

**B16｜审计脱敏另起一份 7 个键名的清单，与全库 redact.ts 分裂：邮编、openid、token 等永久写进 append-only 表**（SEC-05；已探针证实；新发现）

### 4.4 商品、运营配置、地址与上传

**B21｜一个畸形 multipart 上传就能让进程崩溃退出**（CAT-01；已探针证实；新发现；R2 驱动落地后升 P1）

**B23｜更新一个不存在（或已删除）的地址并勾选默认：返回 404，却把用户原来的默认地址清掉了**（CAT-03；已探针证实；新发现）

**B29｜大像素图片会把 512MB 实例打到 OOM**（CAT-09；已探针证实；新发现；R2 落地后升 P1）

## 六、测试体系的有效性（总评）

测试数量本身是充足的：服务端、小程序、管理端合计约 46,000 行测试代码，分层清楚，门禁严格。这一轮暴露的问题不在"少"，而在三种"绿得不对"：

**测试把错误行为钉成了正确。** 这是最需要警惕的一类，因为修生产代码时测试会红，修的人很可能以为自己改错了。本轮找到六处：拒付金额不等 → 40902（A4）；5xx + 幂等键 → 重发成功（B4）；审计保留邮编（B16）；订单详情显示"预估关税 0 円"（B40）；美元金额显示为 `USD 8600`（B43）；e2e 断言拒付被忽略（B49）。修这几处时要同时改测试，并在交付说明里写清"旧断言为什么是错的"。

**自证。** 期望值由被测代码自己的常量或函数算出（Stripe 会话 TTL，B47；toMinor / allocate / applyRate 复算，TSA-13），被测逻辑改错时期望值跟着一起错。外部事实和业务口径至少要有一处用字面量加出处钉住。

**替身与夹具失真。** fake-stripe-http 没有模拟 Stripe 的五种真实行为（缓存 5xx、Should-Retry、会话 TTL 窗口、expire 的状态限制、并发同键冲突）；回调主链路走了生产走不到的预留边（B50）；订单号、运费档、错误码、HTTP 状态的夹具与真实形态不符（TSB-13）。约束三要求"假数据要像真的"，目前的清单机制只覆盖了业务实体，没有覆盖"外部系统的行为"。

另外有两处门禁本身的漏洞值得单独点出：迁移往返测试对 003–014 的 down 完全失明（B51）；扫描型门禁的范围不含 admin-web、scripts 与小程序 vm（TSB-11）。

## 七、系统性根因与防复发机制（约束九）

按"下一次还会不会再犯"的思路，这一轮的问题可以归到七个根因。每一条都给出能变成自动检查的机制；翻译不成检查的，建议写进 CLAUDE.md 的"机器管不了的检查项"。

1. **并发没有测试工具。** A1、A3、B22、B23、CAT-11、SEC-08 都是"串行测试全绿、并发必出"。建议在 `test/helpers` 增加并发编排工具（基于 `pg_blocking_pids` 等到指定等待者数再放锁，替代固定 sleep），并在链路覆盖矩阵（测试策略 §3.3）增加一列"并发用例落点"：每个写路径至少一条并发用例，空着即红。

2. **外部系统的行为没有"真实形态清单"。** 建议仿照 `test/factories/manifest/`，为 Stripe（以及将来的微信支付）建立行为清单：每条写官方原文出处，替身必须实现、并有一条用例验证替身确实这样表现（清单与替身双向核对）。首批条目：同键缓存含 5xx、`Stripe-Should-Retry`、会话 TTL 30 分钟至 24 小时、expire 只对 open 会话有效、并发同键报冲突、metadata 值 500 字符、`Dispute.amount` 可与扣款额不同、`warning_needs_response / warning_closed / prevented`。另立一条纪律：凡外部约束常量，至少一处用字面量钉住并附出处（B47）。

3. **输入校验与数据库列宽、整数范围不同源。** B24、B32、ORD-08、SEC-09 同属一类。建议加一条 db 测试：维护"写入字段 → 表列"登记表，从 `information_schema` 读出列宽与类型，自动对每个登记字段构造"上限 + 1"的输入，断言返回 40001 而不是 50000；配置项写入库列的（`TERMS_VERSION`）同样登记。新增写路由不登记就红。

4. **前端薄壳里的逻辑没有测试环境。** A5、A6、B41、B42、B44 都在 `index.js` / `.tsx` 里。建议：管理端新增 vitest 的 jsdom project（本轮探针已证明 jsdom 在根依赖里可用），把 ADM 分片的 7 个探针改写为组件用例；小程序把本轮 MP 探针的 stub 宿主整理成页面级 harness。机制上扩展 vm-guard：页面文件里凡是发起写请求（POST/PUT/DELETE）或做选择逻辑的函数，必须出现在 vm 或页面级测试里。同时按约束二拆分超过 150 行的页面（ADM-15）。

5. **注释里的"断言式说法"没有依据。** "只会排队不会互等"（A3）、"口令爆破在账号维度被封顶"（A1）、"无 TOCTOU"（ORD-07）、"能挡住 0.0067 打成 67"（A8）——这些都是写的时候没有实测的结论。建议把 CLAUDE.md H5 细化为可检查的形式：注释中出现"不会 / 无 / 已防住 / 封顶 / 挡住"这类断言时，同一段必须带 `@measured` 或指向具体测试名；可以做一个宽松的 lint（关键词命中且附近 5 行内没有 `@measured` 或 `.test.` 引用就告警）。另外，修复旧决策时要 grep 旧说法（本轮 B33 就是 0.6.10 改了口径、三处旧描述没跟上）；可以仿照 contract-document 测试建一张"已废止说法黑名单"。

6. **同一规则出现第二份实现。** 审计脱敏另起一份键名清单（B16），三端各自一套校验规则（B27），报关禁词前后端语义相反（B26）。建议把"规则表"一律放进 `@waselect/shared`，并加 lint：`redact.ts` 之外不得定义 PII / secret 键名集合；前端不得定义与 shared 同名的规则常量。

7. **测试期望值来自实现而不是来自规格。** 六处"把错误钉成正确"的测试都有这个特征。建议在单元完成模板里增加一问："这条用例的期望值出自哪里（文档 / 官方原文 / 决策编号），还是读实现得来的？"涉及外部系统或业务口径的期望值必须注明出处。

## 十一、看过但确认没有问题的高风险点（节选）

下面这些是审查时重点怀疑过、逐一核实后确认正确的地方，列出来便于以后复核时不必重复怀疑。完整清单见各分片原文第 3 节。

支付安全面：Stripe 验签用原始字节拼接、多个 v1 任一命中、先比长度再 `timingSafeEqual`、NaN 时间戳被拦、容差对未来时间戳同样生效；短链 token 约 244 bit 随机、库里只存 sha256、格式校验先于查库；回调租约的迟到持有者只打 warn、抢不到租约返回 503、早到宽限用 DB 时钟；退款三态在并发点击下不会退两次（机构全额上限兜底）；Adaptive Pricing 不影响金额核对。

鉴权与越权：44 条路由的守卫与契约 `security` 逐条一致，并有矩阵测试；买家对地址与订单的读写全部在 WHERE 里带 user_id，越权与不存在统一 40400；JWT 算法白名单只有 HS256、aud 按期望角色比对、ver 回源；管理端回源查 `is_admin`；dev 登录在配置层与装配层两道闸门；CORS 精确白名单、非白名单来源不回任何 CORS 头。

数据与事务：运费向上取档（`w=1850 → 4950` 成立）；申报价值分摊之和恒等于总额；关单与取消都先做带状态条件的 UPDATE 再回补，不会双倍回血；订单号撞号 savepoint 重试、日期按 JST；14 个迁移 up/down 全部可跑通、外键索引齐全、append-only 触发器对 UPDATE/DELETE 有效；`npm audit --omit=dev` 为 0。

前端：管理端无 XSS 注入点（无 `dangerouslySetInnerHTML`、无数据生成的 href），构建产物只注入 `VITE_` 前缀变量、sourcemap 关闭；小程序 40101 重放只做一次不递归、single-flight 成功失败都清句柄；wxml 绑定字段与 vm 输出逐一核对无拼错；支付页美元金额与服务端实扣同一算法。
