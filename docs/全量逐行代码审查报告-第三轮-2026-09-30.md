## 四、P1

### MP3-04　付款后、支付通知到达前，订单详情仍可「取消订单」：取消后钱只能人工退

- **位置**：`miniprogram/pages/pay/index.js:184-195`（银行卡回前台只查一次状态）、`:246-249`（微信支付成功立即跳详情）；`pages/order-detail/index.vm.js:100,113`（`canPay` / `canCancel` 只看状态）；`server/src/app/cancel-order.ts`（只作废我方 initiated 支付行，不向机构核实）。
- **触发**：买家在浏览器里付完款，几秒内切回微信 → 回查仍是"付款中" → 点「查看订单」→ 详情页显示「继续支付」「取消订单」→ 以为没付上，点取消 → 服务端关单、回补库存 → Stripe 通知随后到达，被判为迟到付款 → 转对账、人工退款，商品可能已被别人买走。
- **为什么升 P1**：银行卡目前是唯一付款路径；支付通知晚于用户切回是常态（秒级，且无上限）；后果是真实扣款后订单被关、需要人工处理。
- **复核**：【读码确认】`cancel-order.ts` 的迁移表允许 `pending_payment → cancelled`，只调 `voidInitiatedPayment`；前端各行号属实。回调时序属【推断】。
- **修复方案**：
  1. 前端（立即可做）：支付页在"微信支付成功 / 银行卡回前台"时带 `justPaid=1` 去详情页；详情 vm 在 `justPaid` 且状态仍可付时 `canCancel=false`，显示"支付结果确认中，请稍后刷新"，薄壳退避重查 1～2 次。
  2. 服务端（接微信支付前）：取消 `pending_payment` 且存在 initiated 支付行时，先向机构查一次会话 / 订单状态；已付或处理中 → 拒绝取消（新 reason，走 40902）。这一步要改 `cancel-order.ts` 与 PaymentProvider 端口（新增"查询会话"能力声明），属约束四范围内的扩展。
- **应补测试**：`order-detail/index.vm.unit.test.ts`：`detailView(pending, { justPaid: true }).canCancel === false`（现状 vm 不收第二参数，红）；服务端 db 用例：Stripe stub 返回会话已完成 → 取消应被拒且库存不回补。

### 5.2 拒付（OPS3-01、OPS3-02、OPS3-03）

**OPS3-02　AJ-233 回归：败诉后接受新单号，新单号撤回 / 胜诉就解锁**

**OPS3-01　拒付事件乱序：新拒付被丢，或订单永久锁住**
- 查询函撤回与正式拒付是同一时刻产生的两条事件。"新单号开案"先到 → `dispute_id_conflict` → 200 不重发 → 正式拒付进不了系统；"结案"先到 → `dispute_not_open` → 200 → 之后开案到达 → 订单永久锁住。

- 测试：管线级两条（见分片 OPS3-01）。

**OPS3-03　退款在途时来了拒付，再点"退款"被 40907 挡死**

### 5.4 停机（INF3-01）

**INF3-01　AJ-237 之后"排空失败"分支可能超过平台宽限被强杀**【实测 postgres.js 行为】
