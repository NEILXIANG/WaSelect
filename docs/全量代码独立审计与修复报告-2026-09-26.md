## 一、总体结论

**整体质量：地基与资金链路扎实，业务层刚成形、接缝处有真缺陷。** 全仓 ~1.5 万行生产代码、2.4 万行测试；

## 四、未修复问题及原因

- **P2-5 限流驱逐绕过**：改成"过期优先驱逐、否则拒绝新键"会改变限流语义，属设计决策；单实例 + 30/min 当前风险低。
- **P2-6 换通道不作废旧会话**：需要在事务提交后做出站调用（与 `close-session-events` 同形态），涉及事件与重试设计；P1-1 修后该场景至少会进对账。
- **P2-7 回补锁序**：概率低（每分钟一轮 vs 取消量），且改 `restoreStockForOrder` 为逐行需要重写 adapter 与其用例；建议 I2 与库存模块一起做。
- **P2-8 / 9 / 10**：需要真实 Stripe 实测（30 分钟下限容差）或运维取舍，不做推测性修改。
- **P2-11 / 12 三端**：admin 登录端点与小程序登录/首页属未开工的业务单元，不在"修复"范围；但要明确：**当前三端没有一条能走通的用户路径**，这是下一阶段的第一件事，不是缺陷修复。
- **P2-13 / 14 / 15 / 16**：报关口径（raw_rate vs rate）、dest 与地址国家、`duty_jpy` 语义、迁移表唯一性、合规标签执行点——都是**业务口径或结构性决策**，按"禁止改变业务逻辑、禁止引入新架构"的要求只登记不改。
- **P2-17 / 18**：重复常量与脚本提示方向属卫生问题，改动收益小于风险扰动，留给顺手的单元。

## 五、剩余风险

技术：`restoreStockForOrder` 与建单的潜在互锁（P2-7）；内存限流可被撑爆（P2-5）。
架构：迁移表不是唯一真源（P2-15）；展示币双真源（P2-14）；010 配置表无读者、合规标签无执行点（P2-16）。
业务：报关申报价含 3% 缓冲、dest 不看地址国家（P2-13）；三端无可走通路径（P2-12）。
支付：换通道旧会话可付（P2-6）；Stripe `expires_at` 贴边（P2-8）；`preDeployCommand` 字段与 Stripe 同键行为均 NEEDS VERIFICATION。
数据：`webhook_events.result` 列宽 32 已靠测试守住，但仍是紧的。
安全：issuer 不分环境（P2-9）；内部 job 路径无限流。
运维：CF Pages `_redirects` 是否保留查询串、Render 构建期是否注入 envVars——两条只能真平台验。
第三方：Stripe 端点实际订阅的事件类型决定 P1-5 的触发频率。

## 六、最终判断

1. **是否存在阻塞性问题**：修复后**没有**。修复前有 1 个 P0（对账盲区）和 2 个部署级 P1（构建必失败、无迁移），任何一条都会让首次上线失败或让资金异常无人发现。
2. **是否具备继续开发条件**：**具备**。gate 全绿，资金与安全核心经突变验证稳固。
3. **下一阶段开发前必须完成的事项**：① 用户在 Mac 复跑 `npm run gate` 并处理自己的 6 个 WIP 文件（scheduler / 迁移 012）后再提交；② 用 Stripe test key 实测两件事并把 `@measured` 写回：同键复放语义（P1-7/8 的前提）与 `expires_at` 下限容差（P2-8）；③ 决定 P2-13 的两条业务口径（申报价基数、dest 取自地址国家）——它们影响 I1 报价实现，不能带着模糊进下一单元；④ 小程序端接登录与首页（P2-12），否则后续每个单元都没有端到端验证对象。
4. **代码质量是否达到可持续迭代标准**：**达到，但有条件**——核心层是；业务层的"接缝"问题（两个模块各自对、拼起来错）在本轮集中出现了 5 次，说明单元级红灯验证不能替代链路级断言。建议每个新单元交付时强制回答"它与相邻模块的接缝断言在哪"，这一条比再加任何门禁都有效。
