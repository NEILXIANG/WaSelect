# 测试缺口复盘：为什么这两天的问题测试一个都没拦住（2026-10-12）

> 范围：2026-10-11 起"三端模拟测试"与"全入口点击测试"在真实界面上发现、已修复的 46 个提交（约 60 处问题）。
> 结论先说：**不是测试少**（修复前已有 5,600+ 条用例、关键模块 100% 覆盖），而是测试**问错了问题**——
> 它们问"代码按我写的那样运行了吗"，没有问"运营 / 买家看到的东西对吗、看得懂吗、一件事能从头做到尾吗"。

## 1. 数据

逐个提交统计"修复时有没有改旧断言"（`git show <提交> -- '*.test.ts'` 里被删掉的 expect 行）：

| 情形 | 提交数 | 含义 |
|---|---|---|
| 修复时**必须改旧断言** | 17 / 46 | 旧测试把缺陷当成正确行为**锁住了**：例如时间线断言 `待发货 · 支付机构 mock`、登录失败断言要显示报障编号、批量发货断言 `批量发货 0 单` |
| 旧测试一条都没碰，只新增用例 | 29 / 46 | 问题所在的维度**根本没有测试**：布局、跨页流程、空值 / 0 件组合 |

## 3. 根因（为什么测试没拦住）

1. **断言照着实现抄（自证）**。期望值是写完代码后从输出里抄来的，没有"读者判据"。代码输出 `支付机构 mock`，测试就断言 `支付机构 mock`——测试越多，缺陷锁得越牢。
2. **测试数据不像真的**。前后端接缝测试（`chain-server`）的商品叫 `Chef Knife` / `Tea Cup`、收件人 `Jane Doe`、标题都很短——违反约束三。真实数据是中文标题 + 日文原名、有 255 字的礼盒名、有没留邮箱的买家、有 0 单的日子；问题全出在这些数据上。
3. **只测"一个函数 / 一页挂一次"，不测"一件事做到底"**。单测验证每一块各自对；但运营"从列表点进详情、处理完返回列表"、买家"再次购买 → 购物车 → 结算"这类跨页的连续动作，没有任何测试形态。
4. **测试环境与生产不一致**。后台组件测试挂载时没开 React StrictMode（生产开了），所以"挂载两次"类缺陷在测试里不可能出现；jsdom 没有布局引擎，所有"挤、遮、折行"都看不见。
5. **只测主状态**。用例多落在"正常已付款单"上；0 件、缺可选字段（没邮箱 / 没图）、后续状态（付款后、已发货后）的组合没有列成矩阵。
6. **三端各测各的**。同一事实（金额单位、状态词、支付通道名）在后台、小程序、导出里各有一份，三处测试各自绿，拼起来说法不一（后台表单写"日元"、列表写"円"）。

## 4.1 业务旅程测试第一次跑就读出的问题（已修）

| 问题 | 原因类 | 修复 |

## 4.2 观察到、判断为不改的

- 同一个"已签收"状态，导出表与后台写「已签收」，买家端写「已送达」：两边读者不同（运营核对签收、买家关心到没到），词表各自统一即可。
- 买家确认收货后，时间线写「已送达」而不是「确认收货」：自动确认收货也走同一状态，写「已送达」两种情况都对。

## 5. 仍然只能靠人看的（不夸大）

- **布局与视觉**：不引入浏览器自动化工具（不装软件），jsdom 看不见布局。兜底是"全入口点击清单"+ 模拟库里的边界商品（255 字标题、180,000 日元、无图、售罄、0 库存）——**每次改界面后用这批数据在模拟器 / 后台各看一遍**。
- **措辞好不好**：机器能拦"出现了内部码"，拦不了"这句话新手看不看得懂"。仍靠走查。
