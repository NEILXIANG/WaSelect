## 1. 目标与范围定义

### 1.1 目标

把"骨架行走"换成**订单域业务闭环**：买家侧可登录 → 浏览商品 → 维护地址 → 报价 → 建单 → 发起支付 → 回调落账（已有）→ 超时自动关单。全部 API 与契约同源、有机器比对，无硬编码、无临时方案。

### 1.2 范围内（本批交付）

| # | 单元 | 内容 | 来源 |
|---|------|------|------|
| U1 | 契约-路由机器比对 | "代码路由 ⊆ 契约"自动断言，进 gate | 三审最高雪崩风险 |
| U2 | 超时关单 job + mark-paid 守卫 | expires_at 消费（D-33，30 分钟）、迟到付款拒落账转对账、40904 接线 | 欠账①（致命级） |
| U3 | 限流器 | 42901；挂在 login / quote / pay-link / 建单 | 欠账③、三审 P5 |
| U4 | 报价域 | 运费向上取档（D-46 红线）、duty_rates 表+seed、关税信息字段、fx 换算、50003/50004 | I1 核心 |
| U5 | 商品/地址/订单路由 | GET /products(+{id})、地址 CRUD、POST /orders/quote、POST /orders（D32 重试+40011）、GET /orders(+{id})、POST /orders/{id}/cancel、GET /terms、GET /fx | 欠账⑥ |
| U6 | 支付意图 + 登录 + 短链 | POST /orders/{id}/pay（先写 payments 行，AJ-93）、POST /auth/wechat/login、GET /pay/link/{id}（D-49） | 欠账⑤ |
| U7 | 三表 + 小项 | duty_rates / payment_channels / app_config（全库 20 张）、formatUsdCents/formatCnyFen、Idempotency-Key ≤128 | 欠账④⑦⑧ |

### 1.3 范围外（明确不做，防止范围蔓延）

- 管理端业务路由（/admin/orders、发货、退款、拒付处理）→ I2/售后阶段。
- 迟到付款的**自动全额退款**：依赖真实通道退款能力，I1 只做"拒落账 + status_conflict + 告警 + 对账"（管线已有），自动退款登记为遗留项。
- 小程序真实页面（首页/商品/结算/订单页）→ I2 前端落地；本批只交付 API 与 shared 工具。
- Stripe 售后 5 事件分派（refund/dispute 系列）→ 售后阶段。
- payment_channels / app_config 两表的**消费方接线**：表与 seed 落地（D-56 口径），消费接线留到有真实消费方时做（同 F11 口径：无消费方不进 ports 滥用）。

## 3. 技术方案设计

### 3.1 U1 契约-路由机器比对

- 形态：`server/src/routes.contract.test.ts`（vitest，无 DB），测试内构建 Express app（各 mount 模块注入**调用即抛**的 stub 依赖——挂载期不触依赖），遍历 `app.router.stack` 收集 `METHOD + path`，与契约文本解析出的 `paths` 做**双向**比对：
  - 代码路由 ⊆ 契约（多一条 = 红）；
  - 契约中标注 `x-implemented: true`（或属 I1 本批清单）的路由 ⊆ 代码（少一条 = 红）；未实现路由在契约侧显式标注，避免"契约写了代码没做"被当成漂移。
- Express `:id` ↔ 契约 `{id}` 归一化后比较。
- 自检（缺陷注入）：mount 里加一条契约没有的路由 → 必须红；从契约删一条已实现路由 → 必须红。
- 不引入 YAML 依赖（沿用 check-contract.mjs 的文本解析口径）。

### 3.2 U2 超时关单 job

- 新 job `expire-orders` 插进 scheduler jobs 列表（顺序：关单**最先**，见 scheduler.ts @limitation 一"先关单"）：
  - `UPDATE orders SET status='expired' … WHERE status IN ('created','pending_payment') AND expires_at < now()`，逐单 `FOR UPDATE SKIP LOCKED` + 批量上限（防长事务），每单写 order_events（actor='system'）+ emit `order.expired`。
  - 批次大小、TTL 均来自 config（`ORDER_TTL_MINUTES` 默认 30，D-33；`EXPIRE_BATCH_LIMIT` 默认 100），**禁硬编码**。
- mark-paid 守卫：`markOrderPaid` 接受 `pending_payment → paid`（业务期）并保留 `created → paid`（骨架 simulate 路径在 U5/U6 落地后退役，见 §7）；回调到达时若 `expires_at < clock.now()` → 抛 40902 `reason:'late_payment'` → 管线落 status_conflict + 告警 + 对账（不自动退款，见 §1.3）。
- POST /orders/{id}/pay 对已过期订单抛 **40904**（首次接线）。
- 测试红线：30 分钟 TTL 边界（恰好等于 expires_at 不关、超 1ms 关）、与回调并发（for update 排队）、迟到付款三件套（拒落账/告警/对账可查）。

### 3.3 U3 限流器

- 端口 `ports/rate-limit.ts`：纯判定函数 `decide(state, now, limits)`（固定窗口计数），状态存储为注入接口。
- 适配器：**进程内 Map 实现**（`adapters/rate-limit-memory.ts`）。
  - @limitation 必须写明：以"Render 单 web 实例"为前提；多实例部署前必须换 DB/共享存储实现（进风险登记 R-I1-2）；进程重启计数清零（登录类限流的攻击面可接受，因为密码/验证码错误锁定另有服务端计数）。
- 中间件 `app/rate-limit.ts`：按 `key = route_key + client_ip`（登录类叠加账号维度）限速，超限抛 **42901**，响应带 `Retry-After`。
- 挂载点：`/auth/wechat/login`、`/auth/admin/login`（已有路由补挂）、`/orders/quote`、`/orders/{id}/pay`、`/pay/link/{id}`、建单。阈值进 config（`RATE_LIMIT_*`），不写死。
- 测试：边界（第 N 次过、第 N+1 次 42901）、窗口滚动复位、不同 key 互不影响、trust proxy 下 IP 取值（D23）。

### 3.4 U4 报价域（纯函数 + 仓储）

- `domain/quote.ts`（纯函数，≤60 行/函数）：
  - 输入：商品行快照（price_jpy、weight_g、数量）、目的国、包裹总重、运费档、关税率、fx 汇率。
  - 输出：`items_total_jpy`、`shipping_jpy`、`duty_jpy`（**信息字段，不计入 total**，13b 未定 @limitation）、`total_jpy = items + shipping`、charge 币种金额（JPY→USD，经 `money.toMinor` 唯一取整 + 3% 汇率缓冲口径与商业测算一致，fx 缺失 → 50003）。
- 运费取档**唯一 SQL**（adapters）：`WHERE dest_country=$c AND max_weight_g >= $w ORDER BY max_weight_g ASC LIMIT 1`（向上取档，D-46）；超重返回空 → **50004**。（实际：`shipping_rates` 未建 `dest_country` 列，取档 SQL 没有国家条件——见 §10 偏差 2）
  - 红线测试：`w=1850 → 4950`（返回 4050 即失败）+ `tierBoundaryCases()` 全量 + `TIER_REDLINE_CASES`（与 F9 场景集共用同一批向量，不另造）。
- `duty_rates(origin,dest,rate)`：迁移 010 建表 + seed `('JP','US',0.15)`；报价按 `(origin,dest)` 查，查不到 → duty_jpy=null 并在响应标注 `duty_estimate: false`（信息缺失不阻止下单，因为 duty 本就不计入 total）。
- `POST /orders/quote` = 上述纯函数 + 仓储装配的路由薄壳；响应对齐契约 `QuoteResult`。
- 13b 未定：rate=0.15 只是 seed 占位，`duty_jpy` 字段注释与 @limitation 写明"基数口径未定（15%/13.04%/17.25% 三口径待 D 决策），本字段仅供展示"。

### 3.5 U5 商品/地址/订单路由

- 商品：`GET /products`（上架态分页）、`GET /products/{id}`（下架/不存在 → 40401）。地址：CRUD + 默认地址唯一（DB 已有约束），英文/拼音校验 → 40002。
- 建单 `POST /orders`：
  - 走 `idempotency.runInTx`（skeleton 已验证模式：占位+业务写+结果写回同事务）；
  - `terms_version` 必带且等于当前版本 → 否则 40011（当前版本由 `GET /terms` 下发，来源 app_config 或静态配置——接线决策见 §6 D-I1-3）；
  - 金额**服务端重算**（复用 U4 报价），客户端传价与重算不符 → 40905；
  - `order_no` = `buildOrderNo(clock, idGen.orderSeq())`；撞唯一约束（23505）→ `crypto.randomInt` 重取，最多 3 次（D32），仍撞 → 50000 + error 日志；
  - `expires_at = clock.now() + ORDER_TTL_MINUTES`；fx_snapshot / address_snapshot JSONB 落快照；
  - 初始状态 `created`；库存校验（stock）→ 40901。
- 订单查询：`GET /orders`（status 过滤，**契约双词表统一**：以 shared `OrderStatus` 10 态为唯一真源，契约 `status` 参数枚举改为 10 态子集并注明映射）、`GET /orders/{id}`（`readOwnedOrder`：非本人 → 40400 防存在性探测）。
- 取消 `POST /orders/{id}/cancel`：`created/pending_payment → cancelled`（若有 initiated 支付行则同事务作废该行为 cancelled），其余 → 40902。
- `GET /terms`、`GET /fx`：公开配置端点（与 /pay/channels 同级不鉴权）。
- skeleton 退役：`/skeleton/create-order`、`/skeleton/simulate-paid` 在 U6 真链路跑通后删除（含 SEC2 闸门、main.ts 装配、相关测试改写为业务路径）——不是破坏功能，是用真业务替换骨架（地基清单既定口径）。

### 3.6 U6 支付意图 + 登录 + 短链

- `POST /orders/{id}/pay`：
  1. 校验订单归属/状态（expired → 40904）；
  2. **先写 payments 行**（status='initiated'，AJ-93 连带：否则回调核对不到 → 付了钱落不了账）；已有 initiated 行 → 直接复用返回（幂等，对齐 `uq_payments_one_initiated`）；
  3. 调注册表 `get(channel).create(...)`（带 expiresAt 透传，端口已有该字段）；
  4. 回写 provider_ref + checkout_url（迁移 010 加列 `payments.checkout_url TEXT`，D-49 短链 302 需要持久化 URL）；（实际：未建 `checkout_url` 列，沿用 001 已有的 `payments.pay_url`——见 §10 偏差 1）
  5. 订单 `created → pending_payment`；
  6. 返回契约 `PaymentIntent`（entry mode 由通道能力决定，不写死）。
- `POST /auth/wechat/login`：
  - 端口 `ports/wechat-auth.ts`（`code2session(code) → {openid, unionid?}`）；
  - 适配器两枚：真实（走 ports/http-client 调微信 API，熔断/重试沿用既有纪律）与 dev（`WECHAT_DEV_LOGIN` 非生产才注册，接受 `dev_openid` 直通）；
  - 未配置（公司登记前常态）→ 明确错误而非静默（50000 reason='wechat_login_not_configured'）；
  - 用户首次登录建行（users 表），签发用户 token（复用既有 auth 签发机制，见 D-I1-2）。
- `GET /pay/link/{id}?t=`：校验 `pay_token_hash` + 订单存在 initiated 支付行 → 302 到 checkout_url；token 错/失效 → **40102**；无 checkout_url（通道非 copylink）→ 40001。限流必挂（U3）。（实际：跳转目标读 `payments.pay_url`；所有失败一律 **302 到 checkout 静态站失效页**（绝对地址），不返回 4xx JSON——见 `app/pay-link-routes.ts` @why 与 §10 偏差 1）

### 3.7 U7 三表与小项

- 迁移 010：`duty_rates`、`payment_channels`、`app_config` + seeds + `payments.checkout_url` 加列（实际：未加列）→ 全库 **20 张**，同步更新 `adapters/db.db.test.ts` 表清单断言（唯一真源）与两库技术文档/契约版本（契约 0.6.0，jp 技术文档 v0.6——按既定欠账口径一次性同步）。
- payment_channels seed 与当前 env 装配口径一致（mock + stripe 三要素齐全才注册）；app_config seed 最小集（terms_version 等，随 D-I1-3 定）。
- `formatUsdCents` / `formatCnyFen`：进 `packages/shared/src/money.ts` 邻近或 miniprogram utils（按地基清单口径：前端 utils 补两函数 + 单测；Display 展示价=整数分前端格式化）。
- `Idempotency-Key` 路由层限长 ≤128（adapters/idempotency 入口校验，超限 40001）。

### 4.2 状态机（I1 落地子集）

```

   │                      │
   ├──expires_at 到点（job）──▶ expired
   └──用户取消──▶ cancelled
```

- 迁移表放 `domain/order.ts`（纯函数 `canTransition(from,to)` + `assertTransition`），job/路由/落账三处共用一份——迁移规则不得散写。

## 6. 风险点与依赖项

| 编号 | 风险/依赖 | 影响 | 对策 |
