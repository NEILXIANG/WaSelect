# 测试质量审计与业务流覆盖（自评 + 对 WorkBuddy 报告的逐条核验，2026-10-08）

> 性质：**只记录，不修改**（审计期间的两次实测都是临时替换 / 临时探针，跑完即还原、删除；文件校验和前后一致）。
> 范围：全仓测试（受版本控制的测试文件 364 个）、业务流全链路；结合当天三端联动走查中测试"没拦住"的真实案例。
> 对照对象：WorkBuddy《测试质量审计与业务流覆盖-2026-10-08》（下称"WB 报告"）。

## 一、结论先说

1. **"为过而写的测试"在本仓库确实很少**——假断言、skip / only、快照、mock 掉验签鉴权都是 0；这点同意 WB 报告。
2. **但 WB 报告最该被采纳的那条测试（A1 地址死锁探针）是无效的**——我实测：把锁序修复换回旧代码，它**照样全绿**。
   同时用确定性交错探针实测：旧代码**真的死锁**（`40P01 deadlock detected`），WB 的源码修复**确实消除**了它。
   结论：**源码修复该收，测试要换**。
3. 我自己发现的、比 WB 报告各条更要紧的缺口是**测试数据形状靠手写**：当天同类推荐按详情的 `images[]` 读了列表的 `image`，
   测试数据也照着错的形状写——**单测全绿、模拟器里才看出图片全是占位**。"真实服务端响应喂 vm"的 e2e 只覆盖 4 组视图，
   购物车 / 结算报价、支付页、同类推荐都不在内。

## 二、我的独立发现

### T-1 WB A1 的死锁测试无效（实测），死锁本身真实存在（实测）

| 实测 | 结果 |
|---|---|
| 旧代码（HEAD 的 `addresses.ts`）+ WB 新增测试 | **1 passed**——测不出缺陷 |
| 确定性探针（挡片持住旧默认行 a-0 → 先发 `update('a-0', is_default)` → 再发 `create(新默认)` → 放开挡片）跑旧代码 | `["ok","ERR 40P01 deadlock detected"]` |
| 同一探针跑 WB 修复后的代码 | `["ok","ok"]` |

- WB 测试为何无效：update 的目标是**非默认行 a-1**，create 根本不需要 update 持有的锁，结构上成不了环；它的注释却写"目标正是要清掉的旧默认行"——**注释与实现不符**。
- 建议（不在本次修改）：保留 `addresses.ts` 的锁序修复；用"目标 = 旧默认行 + 挡片控制先后"的确定性探针替换 WB 的 10 轮随机测试，并按约束八做注回验证（换回旧锁序必须红）。

### T-2 测试数据形状靠手写，契约漂移测不出来（当天真实案例）

- 现象：小程序 vm / 薄壳测试里的 API 响应是手写对象；同一个人既写实现又写测试数据时，**理解错的形状会被两边一起"确认"**。
- 案例：`relatedCards` 读 `images[0]`、测试数据也写 `images`，契约 `ProductCard` 是单张 `image`——单测绿、模拟器里推荐图全是占位（已修，`c9c9f5d` 之前的 e1207aa 引入、当天修复）。
- 现有防线：`test/e2e/miniprogram-vm-real-response.e2e.test.ts` 用**真服务端响应**喂 vm，但只覆盖首页卡片 / 详情、订单列表 / 详情、地址列表四组（`:66 / :90 / :155 / :207`）。
- 缺口：购物车与结算的报价视图（`quote-view.js`）、支付页通道 / 意图、同类推荐（列表响应进详情页）、再次购买（订单响应进购物车）。
- 建议：把这四处加进真实响应 e2e；或让手写 fixture 过一次契约 schema 校验（工程分析 E-8 同一件事）。

### T-3 "读源码文本"的结构测试在增加——包括我当天自己加的

- 小程序没有 wxml 渲染测试，结构类保证只能读 wxml 文本：当天新增的 `buybar` / `media-square` / `skeleton` 三个文件、各页 shell 测试里的 wxml 正则都属此类。
- 它们能防"结构被改掉"，**不能**证明"用户看得见"：底栏 class 在、但被别的样式盖住，测试照绿。当天 tabBar 透明、角标逃逸、竖条图，都是这类测试拦不住、模拟器一眼看出的。
- 建议：结构测试只守"不变量"（有 / 没有某个结构），不扩成"样式断言"；把"开发者工具模拟器截图走查"作为 UI 改动的固定验收步骤（当天已证明可自动化：官方自动化端口 + 截图）。

### T-4 文案精确断言让"改文案"必须改测试

- 当天改两句文案（"付款已完成，该订单已付款" 去重、"累计实付"改名）都要改既有断言。精确断言本身是对的（防英文状态码漏给用户），
  风险在于形成"改测试去配合实现"的习惯。
- 建议：文案集中成 vm / view 常量，测试断言常量的**不变式**（非空、中文、不含状态码）+ 少量关键句精确断言。

### T-5 通知"丢失"不可测

- `server/src/app/order-mail.db.test.ts` 6 条都是"事件触发 → 发信"正路径；"提交后、发信前进程退出"这条没有、也写不出来——
  因为架构上没有 outbox（工程分析 E-1）。这是"测试覆盖不到的根因在架构"的典型，记在这里避免被误读成"邮件链路已测透"。

### T-6 WB 补丁自身的两处瑕疵（B 级门禁）

- `vm-guard` 新增的"测试里必须有 `expect(`"拦不住 WB 自己举的 `expect(true).toBe(true)` 空壳；它的正则自检又是**复制一份正则**来测——与 B1 补丁注释警告的"副本"问题相同。
- `component-registration` 自检的反例断言带 `.filter((t) => t !== '')`，会掩盖"正则抓到空串"这种错误。
  （B1 的"副本漏剥注释、自检自己红"已由我在审计前改为与正式扫描共用 `usedTags()`，未提交，属 WB 那批文件。）
