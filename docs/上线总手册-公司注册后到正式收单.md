# 上线总手册：公司注册下来之后，到正式收第一笔钱，再到撤掉测试环境

> 写给向（唯一开发与运维）。前提：日本株式会社已登记完成；**目前所有东西都只在本机跑过，还没有上过任何服务器**。
> 本手册按办事顺序排列，每一步写清"做什么、在哪做、要什么、怎么验收"。技术细节（环境变量含义、回滚、迁移纪律）
> 不重复抄，指向 `docs/上线运维手册-首次部署·回滚·审核期切正式.md`（下称《运维手册》）、`render.yaml`、`.env.example`。
> 法律 / 税务 / 银行类事项只列"要办什么"，具体口径以行政書士 / 税理士 / 银行为准，本手册不替它们下结论。
> 编号 D-xx 指 jp 库《决策日志》；AJ-xx 指 `docs/自主决策记录.md`。

## 0. 总路线与依赖

```
公司登记完成
  ├─ ① 公司后续手续（法人番号、税务届出、法人银行账户、法人邮箱）──────────┐
  ├─ ② 域名与账号（Cloudflare、Render、Sentry、Resend、R2）                    │
  │        └─ ③ 预发布环境 staging（真域名、真平台、Stripe 测试模式）          │
  ├─ ④ 微信小程序：境外主体注册 → 认证 → 拿 AppID → 登记服务器域名           │
  └─ ⑤ Stripe 日本账户开户（要 ①的法人资料与银行账户）─────────────────────┘
                 ↓ 以上齐了
          ⑥ 生产环境首次部署（审核期配置：只开 mock 通道、只有审核商品能下单）
                 ↓
          ⑦ 清理测试阶段残留 → 提交微信审核
                 ↓
          ⑧ 审核通过 → 切正式（Stripe live、关审核模式）→ 首笔真钱 + 退款验证
                 ↓
          ⑨ 删除 staging 与本机临时环境 → 进入日常运维
```

能并行的：① ② ④ ⑤ 四条线互不依赖，建议第一周同时启动，因为 ④ 和 ⑤ 的审批最慢（各 1～3 周）。
③ 依赖 ②；⑥ 依赖 ②③④⑤ 全部；⑦⑧⑨ 串行。

| 阶段 | 预计耗时 | 卡点 |
|---|---|---|
| ① 公司后续手续 | 2～4 周 | 法人银行开户（网络银行快、实体银行慢） |
| ② 域名与账号 | 1 天 | 无 |
| ③ staging | 2～3 天 | 无（AppID 没下来前买家流程走不了，先验管理端与作业） |
| ④ 小程序主体 | 1～3 周 | 境外主体认证审核 |
| ⑤ Stripe | 1～2 周 | 法人资料审核、银行账户 |
| ⑥ 生产部署 | 1～2 天 | 无 |
| ⑦ 提审 | 微信审核 1～7 天 | 审核被打回（见 7.4） |
| ⑧ 切正式 | 半天 | 无 |
| ⑨ 清理 | 半天 | 无 |

## 1. 公司登记完成后要办的（非技术，但后面每一步都要用）

| 事项 | 为什么后面要用 | 产出物 |
|---|---|---|
| 取得**登記事項証明書**（履歴事項全部証明書）与**印鑑証明書**各数份，记下**法人番号** | Stripe 开户、微信境外主体认证、银行开户都要 | PDF 扫描件（彩色） |
| 税务届出：法人設立届出書、青色申告承認申請、给与支払事務所開設届；**消費税課税事業者選択届出書**（出口退税的前提，设立时若已提交则确认已受理） | 出口免税退回消费税（jp《支付环节与费用》§二-8） | 受理回执 |
| **法人银行账户**（优先网络银行：GMOあおぞら / 住信SBI / 楽天，开户快；实体行作备选） | Stripe 结算打款的目标账户；没有它 Stripe 审核过不了 | 口座番号、支店名 |
| **法人邮箱**（用自己的域名，见第 2 节；例如 `ops@<domain>`、`support@<domain>`） | 微信、Stripe、Render、Cloudflare 全部用公司邮箱注册，不用个人邮箱 | 可收信的邮箱 |
| 确定**特定商取引法表示**的内容：販売業者名、代表者、所在地、電話、メール、返品条件 | 写进 `SELLER_*` 环境变量，法务页与 Stripe 都要 | 一份定稿文字 |
| 条款四件套定稿：利用規約、プライバシーポリシー、返金ポリシー、特商法表示（现在 `checkout-static/legal/` 里是草案） | 提审与收单都要能打开；改版后 `TERMS_VERSION` 要换 | 四个 HTML 的最终文字 |
| 密码管理器（1Password / Bitwarden）建公司保险库 | 后面十几个平台的密码、密钥、恢复码都放这里，**不走微信 / 邮件** | 保险库 |

## 2. 域名与各平台账号（1 天）

### 2.1 域名
1. 买一个 `.com`（推荐在 Cloudflare Registrar 买，DNS 直接在同一处管；用公司邮箱注册，开 2FA）。
2. 规划子域，**一次定完**（微信后台服务器域名每月只能改 5 次；`deploy/wechat-domains.json` 要照此填）：

| 子域 | 用途 | 托管 |
|---|---|---|
| `api.<domain>` | 服务端 API（小程序、后台、Stripe 回调都打它） | Render web `waselect-api` |
| `admin.<domain>` | 管理后台 | Render static `waselect-admin` |
| `checkout.<domain>` | 支付短链落地页 + 法务四页 | Cloudflare Pages `waselect-checkout` |
| `img.<domain>` | 商品图（R2 自定义域） | Cloudflare R2 |
| `staging-api.<domain>` / `staging-admin.<domain>` | 预发布（第 3 节），用完删 | Render |

3. Cloudflare 的 DNS 代理（橙云）：`api` 建议**先不开橙云**（灰云，直连 Render）。理由：开了橙云就多一层反代，`TRUST_PROXY_HOPS` 要改 2 且必须配 `ORIGIN_VERIFY_SECRET`，而这一组合至今没在真平台实测（`render.yaml` 注释）。等上线稳定后再考虑。

### 2.2 账号（全部用公司邮箱 + 2FA，恢复码进密码管理器）
- **Render**：一个 Team（付费档，禁免费档，原因见 `render.yaml`）。
- **Cloudflare**：Pages + R2 + DNS。
- **Sentry**：免费档够用；建项目取 DSN → `SENTRY_DSN`。生产**至少要有 Sentry 或告警邮件之一**，否则拒启。
- **Resend**（邮件）：加域名 `<domain>`，按它给的 SPF / DKIM 记录在 Cloudflare 加 DNS，验证通过后取 API key → `MAIL_PROVIDER_API_KEY`，发件人 `MAIL_FROM=WaSelect <noreply@<domain>>`，告警收件 `ALERT_EMAIL`。
- **GitHub**：仓库已在 `NEILXIANG/WaSelect`；Render 用 GitHub 登录授权读仓库。
- **R2**：建桶 `waselect-img-prod`，绑自定义域 `img.<domain>`，建一把只读写该桶的 API token → `R2_ACCOUNT_ID / R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY / R2_BUCKET`，`STORAGE_DRIVER=r2`，`IMG_BASE_URL=https://img.<domain>`。

## 3. 预发布环境 staging（2～3 天，强烈建议做，不要直接上生产）

目的：把本机测不到的东西在公网上先撞一遍——真 https、Render 反代层数、Stripe 回调能不能打进来、每日作业能不能跑、管理端 CSP 有没有拦东西。做法见《运维手册》§7，这里只列顺序：

1. Render 上用 `render.yaml` 建 Blueprint，服务名后缀 `-staging`，**独立的 Postgres**（绝不与生产共用）。
2. 环境变量按《运维手册》§7 的表填：`NODE_ENV=staging`、`PAYMENT_CHANNELS=stripe`（Stripe **测试模式** `sk_test_…`）、不配 `MOCK_AUTO_CONFIRM` / `WECHAT_DEV_LOGIN`、所有密钥新生成。
3. 管理员：`DATABASE_URL=<staging> npm run admin:create -- <邮箱> --yes` → `npm run admin:totp -- <邮箱> --yes`（staging 也强制手机验证）。
4. Cloudflare Pages 建 `waselect-checkout` 的预览部署，`PUBLIC_API_BASE=https://staging-api.<domain>`。
5. Stripe 测试模式：按《运维手册》§8 建 webhook 指向 `https://staging-api.<domain>/api/v1/pay/callback/stripe`，用测试卡 `4242…` 走一笔 → 回调落账 → 后台退款。
6. 手动触发 Render cron "Trigger Run"，后台「运营日志」看到对账时间更新。
7. 核对《运维手册》§1.4 的清单；每一条打勾。**这里撞到的问题都在 staging 修完再动生产。**

AppID 下来之前，staging 走不了买家端（真实微信登录要 AppID）；下来后把小程序体验版指向 staging 再走一遍买家全流程。

## 4. 微信小程序：境外主体注册、认证、AppID、域名（1～3 周，最早启动）

> 以下流程按微信公众平台当前规则写，**办理时以 mp.weixin.qq.com 页面为准**，规则会变。

1. **注册**：mp.weixin.qq.com → 小程序 → 注册 → 主体类型选**企业（境外）**，用公司邮箱；管理员用你本人微信号。
2. **认证**（境外主体必须认证才能发布、才能用支付类接口）：上传登記事項証明書、法人代表证件、公司英文名 / 日文名对照；认证费以页面显示为准（jp《支付环节与费用》记为 99 美元一次性）。认证由微信委托的第三方审核，1～3 周。
3. 认证通过后：开发 → 开发管理 → 开发设置：
   - 记下 **AppID / AppSecret** → 生产环境变量 `APP_ID` / `APP_SECRET`（AppSecret 只在这里和密码管理器，不进聊天）。
   - **服务器域名**：按 `deploy/wechat-domains.json` 的四栏**一次填完**：request = `https://api.<domain>`；downloadFile = `https://img.<domain>`；uploadFile / socket 留空。每月只能改 5 次，先确认域名已 https 可访问再填。
   - 业务域名不需要（小程序内不打开网页，法务页是"复制链接到浏览器"）。
4. **类目**：选与"跨境电商 / 海外购物"对应的类目；若页面要求补充资质（例如电商类目要营业执照对应经营范围），按提示传登記資料。
5. **用户隐私保护指引**：设置 → 基本设置 → 用户隐私保护指引，按小程序实际收集的信息填（微信昵称不收；收集：收货地址、电话、邮箱、订单）。不填提审会被打回。
6. **订阅消息模板**（付款成功 / 已发货 / 已送达）：功能 → 订阅消息 → 选公共模板或申请，三个模板 id → `SUBSCRIBE_TMPL_PAID / SHIPPED / DELIVERED`（目前代码未使用这三项，可以先空着，不影响提审）。
7. **体验版**：微信开发者工具 → 上传 → 后台「版本管理」设为体验版 → 添加体验成员（合伙人微信号）。体验版连 staging 或生产由 `miniprogram/config.js` 的 `API_BASES.trial` 决定。

## 5. Stripe 日本账户（1～2 周，与第 4 节并行）

1. dashboard.stripe.com 注册，国家选**日本**，用公司邮箱。
2. 激活账户要填：法人番号 / 登記資料、代表者身份证件、法人银行口座、**公开的网站**（填 `https://checkout.<domain>/legal/tokushoho/`，所以法务四页要先上线，哪怕内容先是定稿前版本）、商品描述（海外向け日本商品の代理購入）。
3. 设置：
   - 结算币种：日元入账（Stripe 自动把 USD 扣款换成 JPY，费率以 Stripe 公示为准）。
   - 产品只用 **Checkout 托管页**（D-49），不需要注册 payment method domain。
   - 退款、拒付通知邮件收件人 = `ops@<domain>`。
4. 先在**测试模式**接 staging（第 3 节），全流程过了再拿 **live** 密钥：`STRIPE_SECRET_KEY=sk_live_…`，webhook 端点 `https://api.<domain>/api/v1/pay/callback/stripe`（事件选 checkout.session.*、payment_intent.*、charge.refund.*、charge.dispute.*、refund.*），取 `STRIPE_WEBHOOK_SECRET=whsec_…`。
5. 微信支付（机构模式，R1）**不在首版**：代码里 `PAYMENT_CHANNELS` 写 `wechat` 会被静默跳过。收单机构的事前相談发信包在 jp `40-支付与资金/`，什么时候发由合伙人定，与本手册无关。

## 6. 生产环境首次部署（审核期配置，1～2 天）

顺序：**Postgres → API → 管理端 → checkout 静态站 → 每日作业**。详细步骤在《运维手册》§0～§1，这里给操作顺序与每个值从哪来。

### 6.1 Render Blueprint
1. Render → New → Blueprint → 选仓库 `NEILXIANG/WaSelect` 分支 `main` → 它会按 `render.yaml` 建出 `waselect-pg`（Postgres 16，库名 `japan_shop_prod`，**建后不可改名**）、`waselect-api`、`waselect-admin`、`waselect-daily`。
2. 所有 `sync: false` 的变量要在控制台手填（下表）。填完才点部署；漏一个必填项服务会拒绝启动并在日志里用中文说缺什么——这是设计好的，照日志补。

### 6.2 生产环境变量（审核期取值）

| 变量 | 值从哪来 | 审核期取值 |
|---|---|---|
| `JWT_SECRET` | `openssl rand -hex 32` | 新生成 |
| `ADMIN_EMAIL` / `ADMIN_INITIAL_PASSWORD` | 你定 | 建号后**删掉** `ADMIN_INITIAL_PASSWORD` |
| `CORS_ORIGINS` | 第 2 节 | `https://admin.<domain>` |
| `PUBLIC_API_BASE` | 第 2 节 | `https://api.<domain>` |
| `IMG_BASE_URL` / `STORAGE_DRIVER` / `R2_*` | 第 2.2 节 | `https://img.<domain>` / `r2` / 四个 R2 值 |
| `SENTRY_DSN`、`MAIL_PROVIDER_API_KEY`、`MAIL_FROM`、`ALERT_EMAIL` | 第 2.2 节 | 全填 |
| `LEGAL_BASE_URL` | 第 6.4 节 | `https://checkout.<domain>`（审核期没有 `CHECKOUT_BASE_URL`，必须配它） |
| `SELLER_*`、`SUPPORT_EMAIL`、`SUPPORT_WECHAT`、`SUPPORT_HOURS` | 第 1 节 | 全填（`SUPPORT_EMAIL` / `SUPPORT_WECHAT` 至少一个，否则拒启） |
| `APP_ID` / `APP_SECRET` | 第 4 节 | 真实值 |
| `PAYMENT_CHANNELS` | — | `mock` |
| `REVIEW_MODE` / `REVIEW_MODE_UNTIL` | — | `'on'` / 审核期截止日（建议今天 + 45 天；到期服务拒启，是提醒机制） |
| `REVIEW_SKU_ID` | 第 6.5 节 | 先填占位 `review-sku-tbd`，建好审核商品后换成真 id |
| `MOCK_CALLBACK_SECRET` | `openssl rand -hex 32` | 新生成，**不同于** `JWT_SECRET` |
| `INTERNAL_JOB_SECRET` | `openssl rand -hex 32` | 新生成（cron 服务自动引用） |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `CHECKOUT_BASE_URL` | 第 5 节 | 审核期**先不填**（通道没开，填了也不用） |
| `TRUST_PROXY_HOPS` | `render.yaml` 已写 1 | 不动（api 不开橙云） |
| `ORIGIN_VERIFY_SECRET` | — | 留空 |
| `WECHAT_DEV_LOGIN`、`MOCK_AUTO_CONFIRM` | — | **绝不配**（生产配了拒启） |
| `VITE_API_BASE_URL`（admin 静态站） | — | `https://api.<domain>` |

### 6.3 第一个管理员
按《运维手册》§1.2：部署后先 `DATABASE_URL=<生产> npm run admin:totp -- <ADMIN_EMAIL> --yes` 开手机验证（生产不给没开 TOTP 的管理员签 token），再登录，再 `admin:password` 换掉初始口令，再在控制台删掉 `ADMIN_INITIAL_PASSWORD`。

### 6.4 checkout 静态站（Cloudflare Pages）
按 `deploy/cloudflare-pages.json`：构建命令、输出目录 `checkout-static/dist`、`NODE_VERSION=22`、`PUBLIC_API_BASE=https://api.<domain>`、`SELLER_*` 五项。绑自定义域 `checkout.<domain>`。验收：`curl -I https://checkout.<domain>/legal/terms/` 200；`GET https://api.<domain>/api/v1/terms` 返回四个绝对地址都能打开。

### 6.5 开张前的业务配置（空库）
按《运维手册》§1.5：运费分档 → 汇率（USD、CNY 各一条）→ 新建**审核测试商品**（≥1 日元、上架、有库存）→ 把它的 id 写进 `REVIEW_SKU_ID` → 重启 → 启动日志看到 `launch_ready`。真实商品可以同时录入（审核期买家只能买审核商品，别的商品只是展示）。

### 6.6 小程序指向生产
`miniprogram/config.js`：`API_BASES.release = 'https://api.<domain>'`，`trial` 同样或指向 staging；`miniprogram/project.config.json` 的 `appid` 从 `touristappid` 改成真 AppID。提交到仓库（`test/config/wechat-domains.unit.test.ts` 会拿 `deploy/wechat-domains.json` 与它对账，两边一起改）。

## 7. 提审前：清理"测试阶段"的残留（逐项打勾）

目前仓库里为本机开发、审核期、骨架演示留下的东西，分三类：**提审前必须处理**、**切正式时处理**、**不用动（已被闸门管住）**。

### 7.1 提审前必须处理

| 残留 | 在哪 | 怎么处理 |
|---|---|---|
| 开发者工具的"不校验合法域名、TLS…"勾选 | 微信开发者工具 → 详情 → 本地设置 | 提审前**取消勾选**，用真域名跑一遍；否则本机能跑、审核员打开全是请求失败 |
| `appid: "touristappid"` | `miniprogram/project.config.json` | 改真 AppID（6.6） |
| `API_BASES.trial / release` 为空 | `miniprogram/config.js` | 填 https 地址（6.6）；空着的话真机直接抛 `api_base_not_configured` |
| 骨架演示页 `pages/index`、组件样例页 `pages/comp` | `miniprogram/pages/index`、`pages/comp` | 两者都**不在** `app.json` 的 pages 里，不会打进包；为免混淆建议删除目录（删前确认没有测试引用它们：`grep -rn "pages/index\|pages/comp" miniprogram --include=*.ts`） |
| 法务四页是草案 | `checkout-static/legal/{terms,privacy,refund,tokushoho}/index.html` | 换成定稿文字；`TERMS_VERSION` 改成新版本号（例如 `TOS-2026-11-01`）并同步 `render.yaml` 与 `.env.example`；改版本号 = 旧客户端建单会 40011，审核期无旧客户端，正是改的时机 |
| 特商法信息"公司登记后公布" | 法务页构建期由 `SELLER_*` 填 | 第 1 节定稿后，在 CF Pages 与 API 两处填同样的值，**重新构建** Pages |
| 用户隐私保护指引、类目资质 | 微信后台 | 第 4 节 5、4 |
| 审核备注 | 微信后台提审表单 | 写明："审核期仅测试商品可下单，支付为审核专用模拟通道，点击支付即完成，不产生真实扣款"；提供一个测试微信号（体验成员） |
| 客服联系方式 | `SUPPORT_EMAIL` / `SUPPORT_WECHAT` | 必须是真的能联系上的；审核员可能会试 |
| 小程序分享、首页 Banner | 后台 | Banner 至少一张真图；没有也能过审，但首页空着难看 |

### 7.2 审核通过、切正式时处理（第 8 节一并做）

| 残留 | 处理 |
|---|---|
| `REVIEW_MODE=on`、`REVIEW_MODE_UNTIL`、`REVIEW_SKU_ID`、`MOCK_CALLBACK_SECRET`、`PAYMENT_CHANNELS=mock` | 按第 8 节改 / 删；生产留着 `MOCK_CALLBACK_SECRET` 而不开 mock 会**拒启**，不是可选清理 |
| 审核测试商品 | 下架或删除（买过它的测试单由每日作业 `archive_test_orders` 自动作废并回补库存，不用手工） |
| 审核期测试单 | 不用动；后台默认不显示（"显示测试订单"勾选才看得到） |
| 后台设置页显示"审核模式 开启（只收模拟支付）" | 切完自动变 |

### 7.3 不用动（已经被代码闸门管住，列出来是让你知道为什么不用管）

- `WECHAT_DEV_LOGIN`、`MOCK_AUTO_CONFIRM`：生产 / staging 配了就拒启。
- `npm run db:seed`（灌演示数据）：只认 localhost 且库名含 prod 就拒，不会误灌生产。
- `.claude/launch.json`、`.claude/sim-local/`、本机 `japan_shop_sim` 库：都不进仓库 / 不进部署，第 9 节本机清理时一并删。
- 后台与小程序里出现的 `name@example.com`、`94102` 这类**输入框示例**：是格式提示，不是占位数据，保留。
- `.env` 里的 `CHECKOUT_BASE_URL=http://localhost:5173`、`IMG_BASE_URL=https://img.example.com`：只在本机生效；生产另填，且 `example.com` 这类保留域生产会拒启。

### 7.4 审核常见打回与对策
- "无法下单 / 支付失败"：多半是服务器域名没登记或 `release` 地址没填 → 7.1 前两条。
- "缺少隐私协议 / 用户隐私保护指引"：第 4 节 5。
- "类目不符 / 需补资质"：第 4 节 4。
- "页面有测试内容"：检查有没有把审核商品叫"测试商品"——商品名用正常商品名，审核说明写在后台提审备注里，不写在界面上（AJ-244）。

## 8. 审核通过 → 切正式 → 第一笔真钱（半天）

按《运维手册》§3 的顺序，每步做完再做下一步：

1. Stripe live 密钥与 webhook（第 5 节 4）填进 `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET`；`CHECKOUT_BASE_URL=https://checkout.<domain>`。
2. `REVIEW_MODE=off`、`PAYMENT_CHANNELS=stripe`；**删除** `REVIEW_MODE_UNTIL`、`MOCK_CALLBACK_SECRET`、`REVIEW_SKU_ID`。保存后 Render 重启，看日志 `launch_ready`。
3. 微信后台把审核通过的版本**发布**；`API_BASES.release` 已指向生产。
4. 验收（都用真卡、小金额）：
   - [ ] 任意在售商品可下单，支付页只有银行卡；
   - [ ] 付一笔 → 后台"待发货"出现 → Stripe 后台看到这笔；
   - [ ] 后台全额退款 → 订单"已退款"→ Stripe 后台看到退款 → 买家卡上几天后到账；
   - [ ] 发货一单（真运单号）→ 买家收到发货邮件 → 小程序能复制查件链接；
   - [ ] 第二天"运营日志"的对账无异常；Sentry 没有新 error。
5. 汇率：上线后**每 72 小时内**必须录一次新汇率（过期买家下不了单，后台汇率页会标红）。先定一个人、一个固定时间。

## 11. 还没在真平台验证过、第一次部署时要留意的（来自代码注释，逐条验完划掉）

- Render 的 `/healthz` 作为健康检查、`/readyz` 停机转 503 的行为（`render.yaml` 注释）。
- `TRUST_PROXY_HOPS=1` 在 Render 上取到的客户端 IP 是否正确（看日志里的 `ip` 字段是不是你的公网 IP，而不是 10.x）。
- Cloudflare Pages `/o/<token>?t=…` 的 302 是否保留查询串（`deploy/cloudflare-pages.json` notes 第 4 条）。
- Stripe 退款 4xx / 409 的真实形态（本机无测试密钥，按文档写的，AJ-527）。
- `preDeployCommand` 跑迁移时旧实例仍在接流量（AJ-317）：第一次部署没有旧实例，无影响；以后每次有破坏性迁移都要记得两步走。

这些都写在《运维手册》§6"本手册尚未实测的地方"，验完在那里打勾。
