## 0. 结论速览

- **主链路代码已基本打通**：首页（分类/搜索/轮播/分页）→ 详情 → 加购（本地持久化）→ 购物车（服务端报价）→ 结算（地址/条款/邮箱/幂等建单）→ 支付（按 `/pay/channels` 渲染：微信 in_app / 银行卡 copylink / 审核期 auto）→ 订单列表/详情/取消。并发、重复点击、幂等键、40101 自动重登、配置缺失时的显式报错这些"工程防线"做得很细。
- **离"真实用户能用"还差的主要是三类**：
  1. **配置与合规外壳**：API 域名为空、条款链接是占位相对路径且对应静态页不存在、特商法表示与客服入口都没有；
  2. **售后闭环**：付款之后用户没有任何渠道联系商家或申请退款，也没有通知；
  3. **体验层与 PRD 有差距**：无分享、无立即购买、州不是下拉、无倒计时和三步图示、空态没有引导、错误文案里直接带错误码和宿主原文。
- 粗估：**阻塞项约 6–9 人日**（不含等外部值），**重要项约 10–14 人日**，**改进项约 5–8 人日**。

## 2. 上线阻塞项（提审会被拒 / 真实用户无法完成闭环）

### B1. 体验版/正式版 API 域名为空，域名登记清单为空【码】
- 证据：`miniprogram/config.js:57-61`（`trial: ''`、`release: ''`）；`deploy/wechat-domains.json` 的 `request/uploadFile/downloadFile/socket` 全是空数组。
- 现状的好处：没配时会显式报错，不会白屏（`app.js:111-148`）。但审核员打开正式版必然是"所有请求失败"。
- 代码侧要做：域名确定后填 `API_BASES.trial/release`（https）、填 `wechat-domains.json` 的 `request` 和 `downloadFile`；跑对账测试 `test/config/wechat-domains.unit.test.ts`。
- ⚠️ 待实测：`wechat-domains.json` 说"`<image>` 加载网络图片也需要 downloadFile 域名，否则图片全不显示"。按我对平台规则的理解，`<image>` 的网络图片**不受**合法域名限制【推断】——方向相反，用真机核一次，免得多花一次每月 5 次的改域名额度，也免得排障方向跑偏。
- 工作量：0.5 人日（不含等域名）。

### B2. 条款/隐私/退货文本用户实际看不到【码】
- 证据：服务端 `/terms` 返回的 `urls` 是相对路径占位 `'/legal/terms.zh.html'` 等（`server/src/app/product-routes.ts:16,335`）；`checkout-static/` 下只有 `pay/cancelled|done|expired` 三个页面，**没有任何 legal 页**；小程序法务页只能"复制链接去浏览器"（`pages/legal/index.js:17-19`），复制到的是一段相对路径，浏览器打不开。
- 影响：结算页要求"阅读并同意购买条款"，但条款正文在任何地方都看不到——用户同意了一份看不到的文本。电商类提审一般会检查用户协议/隐私政策入口【推断】。
- 方案（二选一，建议 a）：
  a) 在 `checkout-static` 增加 `legal/terms.{zh,ja,en}.html`、`privacy.*`、`returns.*` 静态页，服务端 `/terms` 改为返回绝对 URL（配置 `CHECKOUT_BASE_URL` 拼接）；小程序法务页**同时**在页内展示一份摘要（退货规则、运营主体、联系邮箱），全文仍复制链接查看。
  b) 条款正文作为内容走 `/terms` 下发（契约加 `sections` 字段），小程序页内直接渲染——无需外跳，审核员和用户都能直接读到；代价是契约变更 + 单一事实源要放在服务端。
- 文本内容本身来自文档库《法务文本要点》，需要人工定稿。
- 工作量：工程 2–3 人日（静态页 + 契约/服务端 + 小程序展示），文本定稿另计。

### B3. 特定商取引法表示缺失【码】
- 证据：`pages/legal/index.js:23-27` 自注没有；契约 `/terms` 无相应字段。
- 影响：日本法对通信販売的硬性要求（販売業者、所在地、電話、返品規約等）。没有它，"真实运营"层面不合规；也是 PRD「法务」P0 项。
- 方案：契约 `/terms` 加 `seller` 对象（name/address/phone/email/returns_policy_url），服务端由配置表或 `app_config` 下发（管理端可维护）；小程序法务页加一节。真实值等公司登记完成（用户自理）。
- 工作量：1.5 人日。

### B4. 付款后用户没有任何联系渠道（客服/售后）【码】
- 证据：「我的」页刻意不放客服（`pages/user/index.vm.js:16-20`、`pages/user/index.wxml:10-11`）；订单详情、法务页均无联系方式；全库无 `open-type="contact"`（grep 无结果）。已付款单前端不可取消（`utils/order-status.js` `PAYABLE`）。
- 影响：缺货、地址填错、想退款、包裹没到——用户唯一的办法是放弃。按"真实用户能用"的标准这是闭环缺口；电商类提审一般要求有售后/客服途径【推断】。
- 方案（MVP 最小集）：
  1. 契约/服务端加 `GET /home` 或 `/terms` 中的 `support: {email, wechat_id?, hours}`，由管理端配置（避免写死在前端）；
  2. 「我的」页加"联系客服"行：展示邮箱/微信号，点击复制；有条件时加 `<button open-type="contact">`（海外主体能否用待实测）；
  3. 订单详情底部加"对这单有疑问？联系客服"并带上单号（复制"单号 + 邮箱"）；
  4. 已付款未发货的单，显示"如需取消/退款请联系客服"。
- 工作量：2 人日（含契约 + 管理端配置项 + 小程序两处）。

### B5. 隐私保护指引的代码侧对齐【推断，需在微信后台核对】
- 现状：代码调用的隐私相关接口是 `setClipboardData`（支付页、法务页、订单详情三处：`pay/index.js:332`、`legal/index.js:116`、`order-detail/index.js:149`）；用户手填收件人/电话/地址/邮箱（`address-edit`、`checkout`）。全库无 `requirePrivacyAuthorize` / `getPrivacySetting`。
- 平台口径：自 2023 年起调用隐私接口时平台会自动弹出授权，但前提是后台《用户隐私保护指引》**已声明对应项**，否则接口直接失败【推断】。代码已经为复制失败准备了"长按手动复制"的兜底（`pay/index.wxml:115`），这一点做得好。
- 代码侧要交付的东西：一份"需要声明的隐私项清单"（剪切板；收集姓名、电话、收货地址、邮箱——用途：跨境配送与订单联系），交给用户去后台填写；PRD §4 要求的"地址表单前 `wx.requirePrivacyAuthorize`"建议补上（地址编辑页 `onLoad` 调用，拒绝时说明并返回）。
- 工作量：0.5–1 人日。

### B6. 支付合规：银行卡走"复制链接到外部浏览器付款"【推断，高风险，需首审验证】
- 证据：`utils/pay-plan.js` copylink 分支；审核备注草稿 §3 已自认"外部浏览器完成实物支付不在禁止之列"这一判断**尚未经实际提审验证**。
- 风险：微信对"引导用户离开小程序完成支付"的口径审核尺度不稳定；首审期间服务端开审核模式只显示"模拟支付"，审核员看不到 copylink，但**上线后**若被举报或复审可能被要求下架该入口。

- 工作量：0（代码）/ 需外部验证。

## 4. 体验与设计质量问题

### 重要
1. **错误文案直接把错误码和宿主原文给用户看**【码 `utils/error-text.js:29-37`，`utils/request.js:151,169`】：断网时显示"-1 request:fail timeout"，没配域名时显示一整句 config.js 的开发者说明。
   方案：`errorMessage` 分两层——用户文案按码查表（网络类统一为"网络不太稳定，请稍后重试"），错误码和 trace_id 放在一行小字里方便截图排障；`-2` 对用户只说"服务暂不可用"。0.5 人日。
2. **购物车整车卡死**（第 1 节第 4 步④）：服务端 `toErrorResponse` 只返回 `{code, message}`（`server/src/errors.ts:66-68`），`details.product_id` 被丢掉。
   方案：对 40401/40901 把 `product_id` 白名单放进响应 `data`（契约同步）；购物车按它标红对应行，并给"移除失效商品"按钮。1–1.5 人日（含服务端与契约）。
3. **支付页通道为空时没有空态**（`pay/index.wxml:83`）：方案是加"暂无可用支付方式，请稍后再试或联系客服"并带客服入口。0.3 人日。
4. **订单详情合计标签固定写"应付合计"**（`order-detail/index.wxml:75`）：按状态切换成"订单合计"，与支付页 `pay/index.wxml:47-49` 同一口径。0.2 人日。
5. **结算→支付用 `navigateTo`**（`checkout/index.js:307`）：返回后落到一个空的结算页。改为 `redirectTo`，支付页返回直接回购物车/上一页。0.2 人日。
6. **空态没有出路**：购物车空（`cart/index.wxml:17-21`）、订单空（`order/index.wxml:26-30`）都只有一句话。改用 `ws-state-block` 加"去逛逛"（`switchTab` 首页）。0.3 人日。
7. **详情页、订单详情页错误态没有重试**（`detail/index.wxml:20-24`；`order-detail/index.wxml:18-22`）：换成 `ws-state-block` + `onRetry`。0.3 人日。
8. **`justPaid` 复查两次失败后静默恢复取消按钮**（`order-detail/index.js:126-131`）：回调延迟超过约 4.5 秒时，用户已经付了款却看到"取消订单"。方案：恢复按钮的同时显示"如已在微信中完成付款，结果可能稍有延迟，请勿重复支付"，并且取消确认框里也写上这句。0.3 人日。

### 改进
9. **对比度不达标**：`--ws-ink-mute #8f8a80` 在底色 `#fbf9f5` 上对比度 3.27:1（`.ws-note` 用它，`app.wxss:391-395`），`--ws-ink-faint #b5afa3` 只有 2.07:1（`.ws-caption` 用它，`app.wxss:397-400`）；而 `.ws-caption` 承载了"条款版本""点此切换地址""去结算禁用原因""点运单号复制"等**有操作意义**的提示，字号还只有 20rpx（约 10px）。WCAG AA 正文要求 4.5:1。
   方案：`--ws-ink-mute` 加深到约 `#6f6a61`（≈4.9:1），`.ws-caption` 改用 ink-mute、字号提到 22–24rpx；ink-faint 只留给真正的禁用态。0.5 人日（token 门禁会帮忙扫全站）。
10. **图片性能**：所有 `<image>` 都没有 `lazy-load`（grep 无结果）；首页列表用 `card` 档没问题，但详情轮播也用 `card` 档（第 1 节第 3 步②）。方案：列表加 `lazy-load`；详情用 `detail` 档并支持 `previewImage`。0.5 人日。
11. **主包与分包**：当前目录约 1.2MB（含测试源码，打包时会被 `packOptions` 排除），11 页都在主包。PRD §4 主包要求 < 1.5MB，目前够用；建议在 `app.json` 加 `"lazyCodeLoading": "requiredComponents"`（开发者工具的代码质量检查会提示），地址/法务等低频页将来可以拆分包。0.2 人日。
12. **首页重复入口**：首页的「购物车」「我的」按钮与 tabBar 重复（`home/index.wxml:53-56`），占掉首屏位置。建议删除，或换成购物车件数角标放在 tabBar 上。0.2 人日。
13. **条款勾选的视觉**：只有文字前加"✓"（`checkout/index.wxml:100-102`），不像一个可勾选控件。换成明确的复选框样式。0.2 人日。
14. **英文 kicker 与中文正文混排**（"Shipping to""Order Summary""Before You Pay"）：品牌调性的选择，但目标用户是北美华人，"Before You Pay"放在合规提示上方会弱化提示本身。建议合规相关卡片的标题只用中文。0.1 人日。
15. **订单列表信息不足**：卡片没有商品图和品名（`order/index.wxml:41-58`），加载卡片每次 `onShow` 都闪一下（`order/index.wxml:14-18`）。方案：契约 `OrderSummary` 加首件商品图/名与件数；已有数据时用静默刷新。0.5–1 人日（含契约）。
16. **可访问性**：可点击元素多为 `view + bindtap`（如购物车 ±、条款、法务复制），没有 `aria-role`/`aria-label`，读屏软件读不出"按钮"。核心操作按钮补上。0.3 人日。
17. **「我的」页登录态不可信**：只看本地 token（`user/index.vm.js:53-56`），建议改成"微信已授权"之类不承诺服务端状态的说法，或干脆去掉这一行，换成版本号 + 客服。0.1 人日。
18. **设计 token 使用**：页面 wxss 有门禁扫描硬编码（注释多处提到），抽查未发现违规；`app.json` 的 `tabBar.color/selectedColor` 和 `window.navigationBarBackgroundColor` 是硬编码颜色（`app.json`），平台限制只能写死，可接受，但应与 `--ws-ink-mute/--ws-ink` 保持同值（目前一致）。
