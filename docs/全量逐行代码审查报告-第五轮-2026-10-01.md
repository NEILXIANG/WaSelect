### 3.2 INF3-01：停机总预算 + `db.end()` 强关上限

预算定时器**在 handler 入口**上膛（`finish` 里上膛太晚），`closeDb` 收毫秒、按秒换算给 postgres.js。

- 注回：预算不上膛 → 红 1；`closeDb` 忽略 timeout → 红 1；配置契约先红后绿。
- 决策：AJ-253。

### 3.3 OPS3-04：登录失败计数加时间窗

邮箱桶的 30 次原本是**累计**计数，`first_failed_at` 写进库后从未参与判定——
于是"30 次 / 15 分钟"的后半句是假的，一个 IP 慢慢攒就能锁住**所有来源**（含管理员本人）。
两层桶都改成：`first_failed_at <= now − 15min` 时从新窗口起算。

- 注回（窗口永不过期）→ 红 **2**。

### 3.4 PAY3-01：登录入口防线三件

1. **登录来源 IPv6 用 `/56` 归一**（原来 `/64`：一台持有 `/56` 的主机就有 256 个来源，
   "要锁死管理员得凑够 6 个来源"这个论证在 IPv6 下不花钱）。只改登录额度，**全站限流仍是 `/64`**——
   限流要粒度，登录额度要不可轮换，同一个 IP 两处要的属性相反。
2. **生产缺 `ORIGIN_VERIFY_SECRET` → error 级启动告警**。清单 ⑦-0 与路由注释都写着
   "放到 Cloudflare Access 之后，外部碰不到"，但 Access 只拦**经过 CF** 的流量，
   源站 `*.onrender.com` 公网可达、密钥没配时源站闸门不生效 ⇒ 直连源站就绕过了 Access，
   **包括绕过它保护的管理端登录口**。
   **选择"出声"而不是"拒启"**：A2 拓扑未实测前，"还没配源站校验"是合法中间态，
   拒启等于宣布生产永远起不来；但绝不能静默。日志里**点名那个入口**（泛指的告警没人知道看哪里）。
3. 更正注释与清单里"6 个来源"的错误论证。

- 注回：`/56` 改回 `/64` → 红 2；告警条件反转 → 红 **3**（实验组不再告警 + 控制组反而告警）。
- 控制组是本轮新加的：只测"该报时报"等于没测条件，把 `=== undefined` 写反也能绿。
- 决策：AJ-254。

### 3.5 PAY3-02：商品详情长图被误报"图片解码失败"

三档只按**宽度**缩放 + `withoutEnlargement`，于是宽度小于档宽的长图（中日电商最常见的详情图，750×20000）
高度原样保留 → 超过 WebP 单边 16383 硬上限 → 编码抛错 → 路由翻成 40001 `image_decode_failed`。
**运营看到"图坏了"，而图完全合法**：这是错误码把排障方向带偏，不是输入有问题。

- 修法：`resize` 加 `height: 16383, fit: 'inside'`。
  ⚠️ `fit` 必须显式写——sharp 默认是 `cover`，只给 height 会把长图**裁**成中间一块，
  那不是缩放失败，是**内容被吃掉**，而且同样静默（管理端缩略图看着正常）。
- 注回（去掉 height 与 fit）→ 红 **2**；还原 → 8 过。
- 决策：AJ-255。

### 3.6 OPS3-07：拒付的两个领域事件 emit 了却没人订阅

`order.dispute_opened` / `order.dispute_closed` 不在 `LOGGED_EVENTS` 里，
`mark-disputed.ts` 的注释却写着"事件会进日志"（注释与事实相反，约束六）。
后果是"拒付何时落库"只能从**回调管线**反推，不在业务事件流里。

- 修法：登记两个事件 + 加一条**扫源码的守卫**：把所有 emit 的事件名扫出来，断言都在列表里。
  守卫扫源码而不是维护第二份名单——第二份名单会漂移，而"忘了登记"恰恰发生在改代码的人不记得还有一份名单的时候。
- 注回两种退化：移除登记 → 红 **1**（报错直接点名漏掉的两个事件）；登记了但漏挂订阅者 → 红 **2**。

### 3.7 ADM3-01：风控页拉黑会拉黑错人（不可逆）

点"处理"取详情拿 `user_id` → 二次确认拉黑。`prepare` 只在**成功时**改写 `orderId`/`userId`，
失败只 `setError`：A 成功、B 超时 → 顶部红字、底部面板**仍是 A 的** → 点"确认拉黑"拉黑的是 **user-A**。
拉黑不可逆、契约没有解除接口，且会在同一事务里取消该用户所有未付款订单、回补库存、作废机构会话。

- 修法：`prepare` 进来**先清空**待确认态（失败时面板自然消失——不是"把显示改对"，是"让不该存在的东西不存在"）；
  面板改显示 `order_no`（原来显示 UUID，列表行显示订单号，运营根本对不上是哪一单）；`confirmBlock` 开头清 error。
- **没有**做"服务端二次校验 order_id × user_id"：它只能挡篡改请求，挡不住"人看错了面板"——
  而本缺陷恰恰是后者。见 AJ-256 依据段。
- ⚠️ 我自己写出来又删掉的一处：加了"响应 order_id 核对"后发现**它走不到**（`busy` 已禁用按钮，
  同一时刻只有一个 `prepare` 在飞），留着就是一段永远拿不到红灯证据的分支。已删并写进注释。
- 注回（去掉三行清空）→ 红 **1**；还原 → admin-web **305 passed**。

### ADM3-02 落地时的一处必要偏离（记在这里，因为它改了报告给的修法）

报告原文写的是"PUT 带 `expected_updated_at`，服务端 `where updated_at = $x`"。照它实现会**破坏 AJ-175**：

- `decrementStock` / `incrementStock`（下单扣减、取消与关单回补）原本也写 `updated_at = now()`，
  于是**买家每下一单，运营手上的编辑凭据当场失效**，"编辑期间下单、只改标题保存、不覆盖库存"
  这条上一轮专门实现并被 e2e 钉住的行为就没了。
- 同一个 `updated_at` 还是管理端列表的排序键 → 每次成交把商品顶到第 1 位 → 翻页漏行 + 重行
  （报告里独立登记的 **DB3-02**，根因完全相同）。

处置：**两者一起做**——`updated_at` 的语义收窄为「商品**信息**最后被改的时刻」，
库存变动不再推进它（上下架仍然推进）。决策全文见 `docs/自主决策记录.md` **AJ-258**，
含五处注回缺陷的红灯证据（最要紧的一条：把 `updated_at = now()` 注回 `decrementStock`，
e2e 里 **AJ-175 那条用例立刻变红**——两条修复互为前提）。

### ADM3-05 落地时的一处口径选择（报告给了两个备选，选了其中一个）

报告写的是"服务端为每行下发 `is_current`……**或者**响应里带服务端 `now`"。选了前者：

- 下发 `now` 只是把"用哪个时钟"换成"用哪个 now"，**"哪一行是当前生效"这份判定仍然有两份实现**
  （前端一份、服务端 `findLatestFxRate` 一份）。两份口径必然漂移，而漂移到"两边说的当前值不是同一条"时，
  保存前的量级核对就失去意义——**且没有任何报错**。
- 下发 `is_current` 之后前端不再需要知道现在几点；判定**只复用** `findLatestFxRate`，
  `GET` 里不重写 SQL 最值（窗口函数 / `distinct on` 都会造出第二份口径）。
  代价是每个币种多一次查询：quote 是契约枚举（CNY / USD），规模固定。
- ⚠️ `is_current` **缺省按"不是当前"处理**，不回退到用本机时钟猜：猜出一个基准、算出"不可疑"
  会让运营**一键写库**；"没有基准"由 `fxSaveStep` 变成"必须勾选确认"（AJ-229：算不出倍数不等于安全）。
- 顺带把 ADM-10 的"列表不标当前生效行"也做掉了（布尔可直接渲染"（当前生效）"）。

决策全文见 **AJ-259**；红灯证据三处（注回浏览器时钟 → 红 3；`fxRowKey` 去掉 quote → 红 1）。

| ORD3-04 映射范围 | "把 SQLSTATE `22xxx` 映射为 40001" —— 没说只映射 `22021` 还是整类 | **整个 22 类** | 22 类全是"值本身有问题"（超长 / 越界 / `22P02`），没有一个是系统故障；只映射 NUL 的话，`page=1e300` 那类分页溢出（**历史上真发生过**，CAT-13）会再来一次 5xx。⚠️ 代价：`22P02` 也可能是我们校验缺失，所以 reason 里带 SQLSTATE 以便区分 |
| OPS3-06 去重 vs 加锁 | "按 `count(distinct note)`" 或 "`select … for update` / advisory lock 串行化" | **按单号去重** | 键的选择只取决于"这把键失败过几次"，去重后并发两次失败 = 1 次，与串行化**等价**；加锁要在资金路径上论证锁的范围与释放，且会抹掉一条有用的留痕 |
| PAY3-04 不扣来源桶 | "先只读邮箱桶的 `locked_until`" 或 "把来源桶这次扣减退回" | **只读窥视** | "先扣后退"要制造一个半回滚状态（`failed_count - 1` 但保留锁），并发时序要单独论证；"根本不消耗"没有中间态，也不削弱封顶（窥视后别人上的锁，claim 照样撞 0 行） |
| OPS3-08 审计跳过 | "0 行命中时 `setAuditBefore(res, null)` 并标注 noop，**或** `res.locals.adminAuditSkip`" | **显式 `skipAudit`** | 报告写的 `adminAuditSkip` 当时**并不存在**（现状与报告不符，需新增）；不让中间件按"before 为 null"猜——那会让"真的删了但改前值取不到"静默丢一行审计，而审计 append-only 补不回来 |

其余两条（PAY3-05 用 `resolve` 拼根、OPS3-08 的改前值先读后删）照报告给的修法实现，无自主取舍。

⚠️ 两处"照报告做的时候发现的额外事实"：
- `contact_email` 的旧正则 `^[^\s@]+@[^\s@]+$` 除了放行 NUL，还放行 **BEL（0x07）等其它控制字符**，
  而 PG **收**下它们（实测 `a@b\u0007` 旧实现是 201 直接入库）——所以入口这层的字符类排除不是兜底的重复劳动。
- PAY3-04 的触发前提是"管理端不读 Retry-After"（SEC2-08，仍未修），否则管理员不会在锁定期里连试 5 次。

### 三个"我方已定、你若不同意请说"的判断

1. **登录分桶用固定窗口重置**（不是滑动窗口）：`first_failed_at` 本来就在表里、本来就在写，只是没参与判定——
   改一行 SQL 让它参与。代价是窗口边界处可两倍速率，要利用它得精准计时。
2. **生产缺源站校验只告警不拒启**：反过来说，"部署时忘配会起不来"才是拒启想要的效果——
   但那要等 A2 实测出拓扑（`TRUST_PROXY_HOPS` 定几）之后才能确定，现在拒启会误伤 staging。
3. **ADM3-02 用 `expected_updated_at` 而不是版本号列**：`AdminProductLike` 已经带 `updated_at`，
   前端也已经拿得到，不需要新增列、不需要迁移。代价是旧页面不带这个字段会被拒（只有一个管理端，同步发布即可）。
