## 二、代码系统模型（从代码本身回答的 12 个问题）

1. **系统由哪些模块组成？**
   四端：`miniprogram`（原生小程序买家侧）、`admin-web`（React 管理端）、`server`（Express + postgres.js，103 个非测试 TS）、`checkout-static`（静态结账 / 失效页）。共享契约包 `packages/shared`（金额、枚举、错误码、订单号、营业日）。

2. **模块之间的调用关系？**
   单向依赖，已**实测**（非听注释）：`grep -rnE "from '\.\./(app|adapters)/" domain/ ports/` → **零命中**。domain 只引用 `@waselect/shared`、`errors`、`ports/clock`、同级 domain；ports 只引用 `errors`、`logger`、`redact`、同级 ports、`node:crypto`。分层约束是真被遵守的，不是文档里画的。

3. **一个 HTTP 请求如何被处理？**
   `http.ts`（解析 → 安全头 → 路由 → 404 兜底 → 统一错误中间件）→ `mount.ts` 装配的路由 → 路由薄壳（形状校验 + 幂等包装）→ 核心函数（事务内业务）→ `adapters`（SQL）。
   错误终局在 `http.ts:318-351`：报文解析错 → warn；非 AppError → error + 50000；AppError ≥500 → error；其余 → warn。响应体由 `errors.ts:66 toErrorResponse` 生成，**堆栈与 details 只进 errorLogFields（日志），绝不进响应**（`errors.ts:89` 注释与实现一致）。

4. **数据如何进入 DB？**
   只有 `adapters/**` 持有 SQL；未发现非参数化拼接。写路径一律走 `withTransaction` / `withSavepoint` / `withUnitOfWork`。JSONB 列传对象而非字符串二次编码（`create-order.ts:190` 有防复发注释）。

5. **状态在哪里产生、在哪里变化？**
   订单 10 态，迁移表**唯一一份**在 `domain/order.ts:28-47`，形态是 `Record<from, to[]>`（数据而非 switch，可被整体断言）。
   写 `orders.status` 的入口：`create-order`(created)、`pay-intent`(pending_payment)、`mark-paid`(paid)、`expire-orders`(expired)、`cancel-order`(cancelled)、`admin-order-routes`(shipped / refunding / refunded)。每处都先 `asOrderStatus` 收窄再问迁移表 —— 脏状态在边界上抛 50000，不会被当成"不可迁移"糊过去。

6. **同步与异步的边界？**
   请求内全部业务同步 + 事务。异步边界只有两处：① `withUnitOfWork`（`unit-of-work.ts:52-57`）**事务提交之后**才 `publishAll`，回滚时那一行到不了（靠代码路径而非约定）；② 内部 job 端点 202 后 detached 执行（`internal-jobs-routes.ts:76`）。
   跑到事务外的外部 IO 只有退款（`admin-order-routes.ts:300`），注释说明是刻意的：不拿 DB 行锁去等 HTTP。

7. **重试 / 并发 / 幂等 / 事务分布？**
   - 幂等：`idempotency_keys` + 栅栏令牌（迁移 004），创建键与业务写在**同一事务**（`adapters/idempotency.ts` 的 `withIdempotencyTx`）。
   - 出站重试：判定 Gate 在 `ports/http-client.ts`，预算与策略来自 `app/http-outbound.ts`；POST 无幂等键不重试（红线）。
   - 回调去重：`webhook_events` 唯一 `(provider,event_id)` + 租约；早到宽限期用 **DB 时钟**做减法（`pay-callback.ts:292` 刻意不用 `Date.now()`，注释解释了时钟不同源会扭曲宽限期）。
   - 并发写：库存用原子条件更新，且**按 product_id 定序取锁**（`create-order.ts:161-167`）—— 注释写明曾经真实复现过 40P01 死锁（并发 20 轮出现 17 次）。用 `<` 比较而非 `localeCompare`，理由写得对：后者随 ICU 构建而变，跨实例会重新退化成 AB/BA 互等。

8. **外部依赖？**
   PostgreSQL、Stripe（`stripe-checkout.ts`）、微信 code2session、对象存储（端口已有，生产 R2/S3 适配器待凭据）、pino 日志。

9. **错误如何处理？**
   `AppError(code)` + `errors.ts` 错误表；`CircuitOpenError` 在**通用序列化层**统一映射 50300（`errors.ts:70-84`），注释解释为什么必须在这一层而不是各 route 的 catch：熔断可能从任何出站链路冒出，逐条 catch 会漏。

10. **日志？**
    三流：A 运行日志（pino）、B 业务审计（`order_events`）、C 用户行为（`user_events`）；脱敏集中在 `redact.ts`。
    ⚠️ **B 流的管理端那一半是断的 —— 见 F-02。**

11. **完整业务流程的代码路径？** 见第五节。

12. **配置 / secrets 如何进入运行时？**
    `config.ts`（673 行）zod schema + `crossField` 跨字段规则（例：启用 stripe 时生产必配 `CHECKOUT_BASE_URL`，`config.ts:543`；生产对外 URL 必须 https，`config.ts:583-588`）；`REQUIRED_ENV_KEYS` 由 schema 反推，`config.contract.test.ts` 守卫 `.env.example` 与 schema 键集合一致。

## 五、核心业务全链路（代码级追踪）

### 5.1 报价 → 建单 → 支付意图 → 短链 → 回调落账

```

                         → summarizeQuoteItems（校验 / 商品小计 / 商品总重）
                         → catalog.findShippingPriceJpy（D-46 唯一取档 SQL）
                         → domain/quote.computeQuote（total = items + shipping，duty 不进应收）

POST /orders         → order-routes（形状校验 + Idempotency-Key 必带）
                     → idempotency.runInTx（键与业务同事务）
                       → create-order：
                           terms_version 比对（D-43）→ findOwnedAddress（归属，非本人与不存在同码）
                           → findProductsForQuote → summarizeQuoteItems → assembleQuote（事务内重算）
                           → 40905 期望总价对账 → 40906 单笔上限
                           → 按 product_id 定序 decrementStock（原子条件更新，防 40P01）
                           → insertOrder（savepoint 重试 order_no 三连撞）+ insertOrderItems
                           → order_events('created')

POST /orders/:id/pay → pay-intent（createPayIntent）：锁单 → 迁移 pending_payment
                          + recordPaymentIntent（同一事务）
                       → issuePayLink：明文 token 只进响应，sha256 落库

GET  /pay/link/:id?t= → pay-link 落地 → 302 → checkout 静态站 → Stripe 托管页

POST /pay/callback/:channel → 验签（stripe-checkout.verify，40103）
                       → pay-callback 管线：
                          claim（登记先行，崩溃也不丢）
                          → duplicate / inflight 分层
                          → 订单不存在：宽限期内 503 交还租约；超期 2xx + error 转对账
                          → applier.succeeded → markOrderPaid：
                              for update → CLOSED_UNPAID（迟到）→ canTransition → expiresAt 守卫
                              → assertSettlementMatches（通道 / 单号 / 币种 / 金额）
                              → orders.paid + payments.succeeded + order_events 同一事务
                       → 事务提交后 publishAll(order.paid)
                          → 订阅者作废该单其它未成功的会话（含今日新增的 order.paid 分支）
```

**逐跳评价**：每一跳的金额都由服务端重算或核对。客户端唯一能传的金额字段是 `expected_total_jpy`，而它**只能让自己对不上被拒（40905）**，不能让服务端采信它。收款口径永远来自 JPY 锚 + 服务端重算。这条链上不存在前端参与算钱的路径。

### 5.2 管理端发货 / 退款 / 改址

三条写操作形状一致：**事务内持锁判定 → 迁移 →（退款的机构调用在事务外）**。
退款刻意把"记账"与"对外"分两段（`@limitation 一`）：代价是可能停在 `refunding`，换来的是**看得见的中间态**，而不是回滚后钱货两空且无人知晓。重试路径（今日修）沿用**首次** reason，因为机构幂等键绑定 `refund:{orderId}`（`stripe-checkout.ts:515`）—— 换 reason 等于同键异参，机构返回 400。这条判断是对的。

### 5.3 尚未闭环的链路（诚实列出）

- **退款异步完成**：机构侧 refunded 事件已能被归一化，但**没有注册落账器**，所以不会自动从 `refunding` 迁到 `refunded`（F-03）。
- **上传半套残留**：三档图分别入库，中间失败没有清理或补偿；需故障注入装配才能验，属已知缺口。

## 六、数据与状态一致性

1. **状态迁移合法性**：`domain/order.ts` 单一迁移表，10 态；`cancelled / expired / completed / refunded` 为空数组（终态）。写状态的每个入口都已确认走 `assertTransition` 或 `canTransition`。**未发现缺失边导致业务卡死**（例如 `paid → shipped` 与 `paid → refunding` 都在）。
2. **跨表一致性**：`orders.paid` 与 `payments.succeeded` 在**同一事务**（`mark-paid.ts:227-243`）。注释解释了为什么必须一起提交：分开写会出现"订单已付、支付行还在 initiated"，而对账任务正是按 `status='initiated'` 找"收了钱没落单"的。
3. **由 DB 约束承担的不变量**：`orders_status_domain`、`payments_status_domain`、`products_status_domain` 三个 CHECK，以及 `uq_payments_one_initiated`（部分唯一索引，至多一条在途支付）、`addresses_one_default_per_user`。应用层之外的最后一道防线是齐的。
4. **缺失的唯一约束**：同一 (quote, effective_from) 的汇率重复行由**应用层** 40910 拦（`fx-input` + 路由），DB 无唯一约束 —— 绕过应用层直接灌数据会破坏"每日一行"的口径。判定 **P3 / Accept**（需要有人绕过应用层且并发双写才会真正破坏，风险低）。
5. **索引**：`(user_id, created_at desc)` 与外键列索引齐备；`idx_orders_open_status` 部分索引正好覆盖关单扫描的三个开放状态；`payments` 的查询恒按 `order_id`，无需 status 单列索引。管理端按 `refunding` 筛选会走全表扫描 —— MVP 数据量下 Accept。
6. **迁移可重复性与对称性**：13 个迁移均带 down（`DROP COLUMN / INDEX / TABLE`），大量使用 `IF EXISTS / IF NOT EXISTS`。**未发现 up/down 不对称**。
7. **一处需要点名的历史决策**（不是问题，是防止后人误改）：`009` 的头注释写的是"保留 005 建的那份索引、删掉 003 那份"，理由是两者定义逐字相同；但**删的动作实际没做成**（`009:43` 只是 `CREATE INDEX IF NOT EXISTS`，同名已存在会被静默跳过）。判定 **Accept / 待确认**：后果仅是维护一份冗余索引，无正确性问题。这是"注释说的是计划、代码还没执行到"的一个实例，值得单独立项确认是否还有同类残留。

## 九、最终结论（8 个明确回答）

1. **当前代码是否存在致命缺陷（P0）？**
   **没有。** 未发现会导致资金静默丢失、越权读写、数据不可逆损坏的 P0。钱的每一跳都有服务端重算与至少一处核对；回调落不了账会转对账而不是静默丢弃。

2. **当前是否存在真实错误（C 级）？**
   **有且只有 1 个：F-01，契约 YAML 非法且门禁对此是盲的。** 它在 HEAD 及此前连续 7 个 commit 存在，`check-contract.mjs` 按设计不做 YAML 解析所以拦不住。修复已写好在工作区，**处置动作是提交，不是开发**。

3. **哪些是"当前阶段不足"而非缺陷？**
   F-02（`admin_audit` 零写入方）、F-03（退款 pending 停在 `refunding`）、F-04（部分 webhook outcome 无落账器）。三者都在注释里被显式登记为已知缺口且给出升级路径，**不适合现在由审查顺手改** —— 它们牵涉口径与设计，改了会把审查变成一轮未评审的行为变更。

4. **哪些是"未来阶段"问题，现在不该动？**
   JWT 黑名单、多实例下的限流分摊、outbox 异步化（`unit-of-work.ts` @limitation 三 已写明触发升级的判据：订阅者开始做网络调用时）。**都不应现在做。**

5. **是否存在过度设计？**
   **未发现。** 我没有把"注释写得厚"当成过度设计 —— 那些 `@why / @limitation / @measured` 记录的是已经踩过的坑，属于防复发资产。唯一接近的是 `redact.ts` 420 行的覆盖面，但脱敏是合规红线，证据不足，不下 D 级结论。

6. **测试是否可信、到什么程度？**
   本次亲手实跑四层全绿（unit 1588 / db 603 / contract 44 / e2e 44）。**可以据此相信"模块合起来在被测形态下是对的"**；**不能**据此相信 typecheck / lint / cov / audit 通过（本次未跑），也不能据此相信所有边界都已被覆盖（仍有 2 个已知测不到的缺口）。

7. **代码是否可以继续使用 / 推进？**
   **可以。** 架构约束（分层、挂载唯一性、金额唯一出口、迁移表唯一、时间全部注入）是真被代码遵守的，不是文档承诺。这是继续推进的充分依据。

8. **下一步做什么（按优先级）？**
   ① **先把工作区这批改动提交** —— 含 F-01 的契约修复与新增的 YAML 解析器守卫。这是唯一"不提交就会丢、且不报错"的事。
   ② 提交后跑一次完整 `npm run gate`，取一次真实的门禁结论（本报告未跑全链）。
