## 一、结论

1. **钱和状态的核心链路没有发现会直接丢钱的缺陷。**
   - 越权实测：另一个买家读别人的订单、售后一律 404（不泄露存在性），调管理端接口 403。
   - 日志脱敏实测：sim 服务 284 行日志里，电话、邮箱、地址样本值一条都没有出现。
   - 连点付款实测：只产生 1 笔支付。
   - 取消订单库存回补实测：11→10→11、48→45→48。
   - 两位运营同时处理同一单：服务端正确拒绝，界面会自动刷新（今天已修）。
2. **上线前必须处理的有 6 件**（P0，见第七节 7.3）。其中两件是今天新确认的"操作端看到的数字或能力不对"：
   - 全额退款的确认框写的是订单合计，不是实际要退的金额（A-2）；
   - 发错货无法撤回（A-1）。
   另外一件是安全底线：管理员两步验证没有强制（S-2）。
3. **小程序的问题集中在"说法前后矛盾"和"出口指向空处"**：
   - 迟到付款的已关闭订单，顶部叫买家重新下单，底部又说钱已收到、无需再付（M-2）；
   - 客服入口完全依赖可选配置，不配就整块消失，而多处出错提示都写着"联系客服"（M-1）。
4. **对标的核心结论**：
   - 我们的取舍（单商户、不做拼团分销秒杀）是合理的；
   - 真正的差距在**微信平台能力**：发货信息录入、订阅消息、原生客服都还没接，全部卡在 AppID / 微信支付上；
   - 支付方面，官方资料显示亚米这类在美华人电商**不收微信支付**、以银行卡为主。我们的瓶颈不是"缺微信支付"，而是"复制链接去浏览器付款"多出来的这一步。

## 四、已核实没有问题的关键点

- **状态机**：所有改状态的 SQL 都带"当前状态"条件。【读码】
- **重复点击**：
  - 连点付款只产生 1 笔支付【实测】；

- **金额输入**：
  - 日元可带"円 / 日元"；
  - `¥`、全角数字、`1e3`、负数、多余小数一律拒。
  【实测】
- **并发**：两位运营同时改址或发货时，服务端拒绝，界面刷新为最新状态。【实测】
- **会话过期**：
  - 浮层重新登录，页面内容保留【实测】；

## 七、与主流微信商城 / 跨境电商对标

### 7.1 能力矩阵

| 维度 | 我们的现状 | 主流做法 | 差距判断 |
|---|---|---|---|
| 商品与搜索 | 首页关键词搜索 + 4 个分类；详情有保障区、"为什么值得买"、分享卡 | 独立搜索页、历史、联想、多级类目 | SKU 只有 20～200 个，**刻意不做**合理 |
| 购物车与结算 | 服务端报价为准、勾选结算、撤销删除、立即购买、结算页新增地址自动选中 | 同类 | 持平 |
| 支付 | Stripe 银行卡，方式是"复制链接到浏览器付款"；微信支付未接 | 亚米：卡、支付宝、PayPal、礼卡，不含微信支付【官方】 | **流程多一步**是主要差距 |
| 物流与查件 | 运单号 + 复制日本邮政查件链接 + 引导；进度条 | 页内物流轨迹；微信"发货信息录入"`upload_shipping_info`【官方】 | 页内轨迹 P2；**发货信息录入接微信支付时必须** |
| 售后与退款 | 5 类原因 + 描述；部分 / 整单退款；拒付处理 | 区分仅退款 / 退货退款、上传凭证照片 | 缺照片上传（P1） |
| 会员与营销 | 无优惠券、满减、积分、会员价、分销 | 有赞等 SaaS 标配拼团、分销、会员积分（来源为应用商店自述，二手） | 增长期再议（P2）；拼团分销**刻意不做** |
| 消息通知 | 只有英文邮件（付款、发货、部分退款、退款），每日补发漏发 | 订阅消息：一次最多 5 个模板、须用户点击或支付回调触发、一次性与永久模板不能混用【官方】 | **订阅消息未接**（等 AppID） |
| 客服 | 客服微信号 / 邮箱（依赖配置，见 M-1）；未接原生客服 | 原生客服 / 企业微信客服（`openCustomerServiceChat` 需 corpId）【官方摘要，未逐条核】 | 原生客服等 AppID |
| 内容与信任 | "价格含美国关税"、发货时效说明；无评价、晒单、销量 | 评价晒单是标配；跨境到岸价担保（Zonos 官方文档） | 评价晒单 P2 |
| 运营后台 | 工作台（待办、销售、漏斗）、订单全流程、客户与拉黑、商品、运营配置、Banner、风控、运营日志、三类导出 | 漏斗、复购、商品排行 | 复购与商品排行 P2 |
| 风控与安全 | 限流、拉黑连带取消、审计、脱敏、行为记录可删 | 平台兜底为主 | 两步验证未强制（S-2）；买家账号注销入口无（审核是否要求【未核】） |

### 7.2 我们的不足（归纳）

1. **微信平台能力全部未接**：发货信息录入、订阅消息、原生客服、微信支付。原因都卡在 AppID / 微信支付审核上，属外部阻塞，但上线前要排好接入顺序。
   - 其中**发货信息录入与资金结算直接挂钩**：官方原文是"用户交易后，默认资金将会进入冻结状态"，要录入发货信息并完成确认收货流程后才结算。
   - 哪些小程序属于"特定类型"，官方文档没有列明，要在 AppID 下来后查 `is_trade_managed`。
2. **买家通知只有邮件**，而邮箱校验过宽（M-6）。邮件填错，买家就完全失联。
3. **售后缺凭证照片**，只能靠"联系客服"补，而客服入口又依赖配置（M-1）。
4. **营销与信任内容（优惠券、评价）为零**。早期合理，增长期要补。

### 7.3 改进优先级

**P0：上线前必须**
1. 管理员强制两步验证（S-2）。
2. 全额退款确认框写实际可退金额（A-2）。
3. 生产环境客服方式必填，审核期条款地址必填（M-1、M-1b）。
4. 发错货的补救路径：撤销发货，或至少一份可执行的应急操作说明（A-1）。
5. 迟到付款的已关闭订单，不再叫买家重新下单（M-2）。
6. 接微信支付时同步接**发货信息录入**，否则资金可能一直冻结（【官方】）；订阅消息至少接"已发货"一条。

**P1：上线后一个月**
- 售后上传照片，并在买家提交售后后及时提醒运营。
- Stripe 会话作废失败重试（S-1）。
- 订单详情加物流与金额拆分（A-9）。
- 邮箱校验收紧（M-6）。
- 关键提示对比度（M-5）。
- 取消 / 确认收货失败重取（M-3）。
- 运费表乐观锁（A-6）。
- 拉黑原因与真实 actor（A-7）。
- 退出登录服务端失效（A-8）。
- CSV 坏单号拦截（A-10）。

**P2：增长期，看数据再定**
- 优惠券、满减（必须服务端计算金额，严格档）。
- 真实评价与晒单。
- 分享海报。
- 页内物流轨迹（需接第三方）。
- 收藏、到货通知。
- 复购与商品排行报表。

**刻意不做（合理取舍）**
- 拼团、砍价、分销、秒杀、直播。理由是单商户、日百单、一人维护，维护成本远大于收益。
- 多级类目、独立搜索页。
- 显示库存数字。
- 长期订阅消息：长期订阅仅开放给公共服务类目，这一点仅见于二手资料，官方未见原文。
