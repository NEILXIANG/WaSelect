### 【1】P1 ｜ 功能错误/误导 ｜ 订单列表行认不出“迟到付款”，引导买家再付一笔

**证据**（契约层就没有这个字段）：

```yaml
# contracts/api-contract.yaml:1236（列表行的基类，无 late_paid）
OrderSummary: {type: object, properties: {order_id, order_no, total_jpy, display, status, created_at}}
# contracts/api-contract.yaml:1264（GET /orders 列表行 = OrderSummary + 下列字段，仍无 late_paid）
OrderListItem: {… required: [item_count, line_count, after_sale_state, expires_at], properties: {expires_at, payment_dispute, item_count, line_count, after_sale_state, first_image, first_title}}
# contracts/api-contract.yaml:1265（只有详情 Order 有）
late_paid: {type: boolean, description: '0.6.37（P2-11 / AJ-386）：关单后才到的付款（钱已扣）。买家侧据此说"已收到付款，会原路退回"，而不是"未完成付款，请重新下单"'}
```

小程序列表行对 expired 状态的指引：

```
# miniprogram/utils/order-status.js:93（列表无 nextInList，回落到 next）
expired: { title: '已超时关闭', next: '超过支付时间，订单已自动关闭；需要的话可以重新下单。' }
# miniprogram/pages/order/index.vm.js:137-141（行视图取 buyerStatus(next)，wxml:80 渲染 item.nextText）
```

对照组——同一事实在详情页与支付页都处理对了：

```
# miniprogram/pages/order-detail/index.vm.js:77,85,292-293,401
const LATE_PAID_NOTE = '我们已收到你的付款，但这张订单已关闭；款项会原路退回，无需重新付款。';
const LATE_PAID_TOP_STATUSES = ['expired', 'cancelled'];
const latePaidTop = o.late_paid === true && LATE_PAID_TOP_STATUSES.includes(status);
# miniprogram/pages/pay/index.vm.js:112-115
if (status === 'expired' || status === 'cancelled') {
  if (latePaid) return `该订单${label}，但我们已收到你的付款，款项会原路退回，无需重新付款`;
```

服务端真值（`server/src/app/mark-paid.ts`：`paidMoment >= expires_at` 或订单已处 CLOSED_UNPAID 终态的到账，一律不落账、不置 paid，只记一条 `order_events 'late_paid'`，自动退款留到售后阶段；`order-query-routes.db.test.ts` 中订单仍为 created 态即置 `late_paid=true`）。迟到窗口没有“宽限例外”：`adapters/orders.ts` 的 `EXPIRE_PAYMENT_GRACE_MS`（5 分钟）只延迟关单与回补库存，窗口内到账仍按迟到处理。

**复现路径**：买家在 Stripe 托管页付款耗时超过 30 分钟（3DS/输错卡号很常见），或回调晚于关单作业 → 订单 expired + `late_paid=true`，钱已扣 → 买家回微信进「订单」tab → 列表该行写着“需要的话可以重新下单” → 买家重新下单并再付一次 → 第一笔走人工退款。点进详情页才会看到正确的“无需重新付款”（`order-detail/index.vm.js:311`）——**同一事实两页两种指引**。

**影响**：唯一一条能把买家引向“付第二笔”的现存路径；不属服务端重复扣款（服务端幂等/迟到拒收都在），但买家资金被双重占用、客服成本与信任损失真实存在。订单列表是买家付完款回到微信的第一落点，暴露面大。

**解决方案**（需契约 + 服务端 + 小程序三方配合）：

1. 契约：`OrderSummary`（或 `OrderListItem`）增 `late_paid: {type: boolean}`（0.6.37 已给详情 Order 加过，属补齐遗漏；描述注明“恒下发或省略”）。
2. 服务端：`order-query-routes.ts` 列表分支补查 `latePaid`（详情分支 `:120` 已有同一查询，复用）；`toOrderListItem` 透出。
3. 小程序：`pages/order/index.vm.js` 行视图——`o.late_paid === true && (status==='expired'||status==='cancelled')` 时，`nextText` 改用 `LATE_PAID_NOTE` 同文案（可从 order-detail vm 下沉到 utils/order-status.js 共用，避免第三份实现）。
4. 测试：`order/index.vm.unit.test.ts` 加一例“expired + late_paid → 行内下一步不含‘重新下单’”；契约侧若有 schema 快照测试同步更新。
5. 反向风险：低。列表行只改一句话，不碰任何写路径；服务端加字段不影响旧客户端（省略即 false）。

**置信度**：已证实（契约 schema、服务端迟到判定、小程序两处指引均实读；无时序例外）。

### 【2】P3 ｜ 交互 ｜ 拒付争议进行中仍给出「确认收货」，点击必被服务端 40902

**证据**：

```
# miniprogram/pages/order-detail/index.vm.js:290
const showConfirmReceipt = status === 'shipped';
# 同文件 :295 —— 争议数据本来就在手里
const dispute = disputeStatus(o.payment_dispute, o.status);
# 同文件 :403 的注释与上面两行自相矛盾：
* 确认收货（P2-13）：只在已发货时给。拒付中的单服务端回 40902（买家视图不含 has_dispute，不在前端猜）。
```

契约：`api-contract.yaml:1265` 买家 `Order` 自 0.6.82 起下发 `payment_dispute`（open/lost）；`:441`（0.6.38）明确 confirm-receipt“其余状态**或有拒付限制** → 409 / 40902”。

**复现路径**：订单 shipped → 买家没认出扣款名目、银行发起拒付（`payment_dispute='open'`）→ 买家打开订单详情 → 底部仍有「确认收货」→ 点击 → `POST /orders/{id}/confirm-receipt` 返回 40902 → 走 `actionFailure`（`order-detail/index.vm.js:97-106`）重取订单并提示“订单状态有更新，已为你刷新到最新状态；如仍无法操作，请联系客服”。

**影响**：一个必然失败的按钮 + 一句归因错误的文案（“状态有更新”其实什么都没变）；无资金风险（服务端正确拒绝），属体验与前后端状态口径不一致。若拒付单量上升可升 P2。

**解决方案**：`showConfirmReceipt = status === 'shipped' && dispute === null`（数据已在手，不新增请求）；订正 `:403` 注释（买家视图**有** `payment_dispute`，是“刻意不在前端预判”还是漏判，写清楚）；`order-detail/index.vm.unit.test.ts:216-236` 那组加“shipped + dispute=open → `canConfirmReceipt=false`”。反向风险：无——服务端仍会拒，前端只是不再给必败入口。

**置信度**：已证实。

### 【4】P3 ｜ 体验 ｜ 「我的」页复制客服联系方式没有失败回调，隐私拒绝时静默无反馈


`setClipboardData` 是隐私接口：用户拒绝隐私弹窗（errno 104）或隐私指引漏声明剪切板（errno 112）时对所有用户失败（`utils/privacy.js` 文件头、`pay/index.vm.js:251-262` 同口径论证）。

**解决方案**：补 `fail: () => this.setData({ supportCopied: '' })` 并加一行“复制失败，请长按联系方式手动复制”（wxml 增加一个 note 位，与 legal 页同文案）；`user/index.shell.unit.test.ts:16` 的 mock 已支持 fail，补一条断言。反向风险：无。

**置信度**：已证实。

## 三、横向规律（同一根因归类）

1. **“同一事实多处实现，靠单测比对兜底”——shared 镜像模式**：`order-status.js`、`order-tabs.js`、`after-sale.js`、`email-shape.js`、`address-form.js`、`us-states.js`、`cart-store.js` 的上限都是 shared 的手写副本，各自有双向比对单测。本轮逐条比对**未发现漂移**（子代理 + 抽查），但“运行时引不了包所以抄一份”是结构性风险源；tab 序号则是第三处同型风险（`app.json` / `custom-tab-bar` / `utils/tabs.js` 三份，有单测守）。**每一次“加字段/改规则”都要记得改两边**——本轮 P1 的根因正是“规则只在详情侧落地、列表侧契约就没跟上”。
2. **错误码恢复策略已收口到一处（做得好）**：`checkout/index.vm.js:311-325` 的 `recoveryFor` 是唯一恢复策略表（40905/40901/40401 → requote；40912/40906 → requote；40011 → reload_terms；40913 → go_orders；40908 → renew_key；42901 → none）。缺口只有 42901（见待确认）。
3. **“关单后才到款”这一状态只被详情/支付页消费，列表页在契约层就拿不到**——即问题【1】，全部出现位置：契约 `OrderSummary:1236`、`OrderListItem:1264`（缺字段）；小程序 `pages/order/index.vm.js` 行视图（缺分支）；已正确处：`pay/index.vm.js:107-115`、`order-detail/index.vm.js:77-85,292-293,401`。
