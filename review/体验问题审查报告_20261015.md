# 体验问题审查报告（后台管理端 × 小程序）

> 审查日期：2026-10-15
> 方式：方式 A（一次性全查）——两端各派一路独立深挖，主线程逐条复核后采纳
> 范围：`miniprogram/pages/`（14 页）、`admin-web/src/`（11 模块 + `ui/` 组件库）
> **本报告只做分析与修改方案，未改动任何代码、未提交任何 commit。**

---

## 0. 先说结论

这套代码的体验基建**明显强于一般水平**——三态、二次确认、禁用说原因、币种口径、表格截断、连点防线，几乎每一项都有人处理过，而且**理由写在注释里**（带日期和实测来源）。所以 UI/文案两个维度基本没有真问题。

但**布局维度有一个结构性缺陷**（弹层没有高度上限），**滑动维度有一个断点失效**（窄屏滚动记忆），这两条是本次最硬的发现：

| 级别 | 条数 | 说明 |
|---|---|---|
| **P1** | 3 | 订单列表回第 1 页；**弹层超高时按钮滚不到、点不到**；窄屏滚动记忆与换页回顶双失效 |
| **P2** | 12 | 集中在"某一列/某一页漏了" |
| P3 | 6 | 文案一致性与输入细节 |

另有一件同样重要的事：**初查报上来的 4 条问题，复核后确认是误报**（详见第三章）。照着去"修"反而会破坏已有的防线。

## 第一章 P1

### P1-1 弹层没有高度上限、没有内部滚动、没有滚动锁——长确认框在矮窗口下按钮落到视口外，且滚不到

- **位置**：`admin-web/src/app.css:1040-1048`（`.modal`）、`app.css:1150-1161`（`.dialog`）；`ui/confirm.tsx:136`、`ui/drawer.tsx`
- **证据**：

  ```css
  /* app.css:1040 —— fixed 铺满，居中，但没有 padding、没有 overflow */
  .modal {
    position: fixed;
    inset: 0;
    display: flex;
    align-items: center;      /* ← 内容超高时上下同时溢出，上半截不可达 */
    justify-content: center;
    z-index: 10;
  }

  /* app.css:1150 —— 只有宽度约束，没有 max-height、没有 overflow */
  .dialog {
    padding: calc(var(--ws-space) * 1.5);
    width: calc(var(--ws-space) * 26);
    max-width: calc(100vw - var(--ws-space) * 2);
    display: flex; flex-direction: column; gap: var(--ws-space);
    …
  }
  ```

  **全站 `app.css` 里 `max-height` 零命中**（grep 结果只有 `min-height: 100vh` 与 `.main` 的 `height: 100vh`）；也没有 `overscroll-behavior`；`src/**/*.tsx` 里除 `ExportBar.tsx:30` 的 `document.body.appendChild` 外没有任何滚动锁代码。

- **触发条件（真实存在，不是理论）**：最长的确认正文是 `customers/view.ts:187-188`：

  ```ts
  export const CUSTOMER_PURGE_CONFIRM_TEXT =
    '只删除该客户在小程序里的浏览、加购、下单、支付等使用记录（隐私政策承诺的"用户要求即删除"）。订单、地址、退款与审计记录不受影响。删除后无法恢复；这次操作与原因会记录下来。';
  ```

  （约 90 字）与 `customers/view.ts:183-184` 的 `CUSTOMER_BLOCK_CONFIRM_TEXT`（约 70 字），`risk/view.ts` 的 `BLOCK_CONFIRM_TEXT` 同量级。按 `--ws-space: 16px` 算 `.dialog` 内容宽 368px、中文约 24 字/行 → 光正文就 4–5 行；再加上标题、上下文行、`mouseOnlyHint` 一行、按钮行、三段 gap 与上下 padding，总高约 400–480px。

  在 **125% / 150% 缩放**（768 物理高 → 614 / 512 CSS px）、1024×600 类矮窗口、或上下分屏时，必然溢出。而危险确认框恰好**都配了 `mouseOnlyHint`**，又要求**只能用鼠标点按钮**（`ui/confirm.tsx:202`）——键盘和滚动都救不回来。

- **影响**：运营点开「确认删除行为记录 / 确认拉黑」后看不到底部按钮，只能刷新重来、重填原因；观感上就是"点了没反应"。而且这是**不可逆操作**的确认框——点不到「取消」和点不到「确认」一样糟。

- **修改方案**（只补版式与滚动，不动业务语义）：

  ```css
  .modal {
    position: fixed; inset: 0;
    display: flex; align-items: center; justify-content: center;
    padding: var(--ws-space);        /* 新增：矮窗口下不贴边 */
    overflow-y: auto;                /* 新增：超高时这一层可滚，按钮永远可达 */
    overscroll-behavior: contain;    /* 新增：滚到头不再带着背景滚 */
    z-index: 10;
  }
  .dialog {
    …
    max-height: calc(100dvh - var(--ws-space) * 2);   /* 新增（dvh 适配移动端地址栏） */
    overflow-y: auto;                                 /* 新增：正文超高时框内滚 */
  }
  ```

  另外补一条全局滚动锁（写在 `ui/confirm.tsx` 与 `ui/drawer.tsx` 的 `useEffect` 里，卸载时恢复）：打开时 `document.body.style.overflow = 'hidden'`，关闭时还原。`.drawer` 已有 `overflow-y: auto`，只需再补 `overscroll-behavior: contain`。

- **验收**：1024×600 窗口（或 150% 缩放）打开「删除行为记录」确认框 → 按钮可见可点；滚轮在遮罩上滚时背景不动。

### P1-2 订单列表：每次进屏都强制回到第 1 页，滚动位置和分页全丢

- **位置**：`miniprogram/pages/order/index.js`
- **现象**：翻到第 3 页 → 点进订单详情 → 返回 → 列表只剩第 1 页 20 条，滚动位置归零。
- **证据**：

  ```js
  // order/index.js:98-111  onShow 无条件全量重取
  onShow() {
    track(app, 'page_view', { page: 'order' });
    const intent = app.globalData.orderTab;
    if (typeof intent === 'string' && intent !== '') { … }
    void this.load();          // ← 每次进屏都重取
    setActiveTab(this, 'order');
    setCartBadge(this, app.globalData.cart);
  },

  // order/index.js:135  load() 硬取第 1 页
  url: `${app.globalData.apiBase}/api/v1/orders${orderListQuery(tab, 1)}`,
  // order/index.js:140
  this.page = 1;
  ```

  触底加载的 `this.page` 本来是有值的（`loadMore()` 第 191 行 `const next = this.page + 1`），但每次 `onShow` 都被 `load()` 打回 1。

- **影响**：
  - 买家查"发货了没"的本能动作就是**回列表**——代码注释 `order/index.js:265` 自己写着"没有推送时，买家查发货了没的本能动作就是下拉"。这条路径每次都被打断。
  - 订单攒多了永远翻不到底：每返回一次就重置。
  - 注意：**页签切换清列表是合理的**（`setTab` 第 118 行），但从详情返回**不算**换筛选条件。
- **跨端反差**：管理端为此专门做了 `ui/scroll-memory.ts`，`App.tsx:122` 注释"后退 / 前进回到记下的位置"。小程序端全库搜 `scrollTop / onPageScroll`，只搜到首页分类栏的 `scroll-into-view`（`home/index.wxml:96`）。**同一件事，一端做了、一端没做。**
- **修改方案**（推荐①）：
  1. **推荐：按"有没有变化"决定重不重取。** `onShow` 不再无条件 `load()`：`onLoad` 取一次；`onShow` 只在这些情况重取——从支付页返回、页内刚执行过取消/确认收货（设 `this.dirty`，取完清掉）、「我的」带一次性页签意图进来（`index.js:101-105` 已有该分支）；其余只更新 tabBar 高亮与购物车角标。下拉刷新（第 268 行）保持无条件重取。
  2. 退一步：保留每次重取，但记住 `this.page` 与滚动偏移，重取后 `wx.pageScrollTo({ scrollTop })` 复原。
  3. 不推荐：只记滚动偏移不记页数——列表变短后偏移被截断，等于没做。
- **验收**：翻到第 3 页 → 进详情 → 返回 → 仍在第 3 页、滚动位置不变；下拉刷新仍然回到第 1 页。

### P1-3 窄屏（≤ 56rem）滚动记忆与"换页回顶"双双失效

- **位置**：`admin-web/src/App.tsx:124-140`（换页滚动）、`App.tsx:377-381`（记住位置）；`app.css:160-183`（`.main` 的滚动条件）、`app.css:226-255`（窄屏顶栏布局）
- **证据**：

  ```tsx
  // App.tsx:124-140 —— 只对 .main 写 scrollTop
  useLayoutEffect(() => {
    const el = mainRef.current;
    if (el === null) return undefined;
    const target = scrollTarget(routeKey, consumePush());
    el.scrollTop = 0;                 // ← 只对 .main 生效
    …
  }, [routeKey]);

  // App.tsx:377-381 —— 只听 .main 的 onScroll
  <main className="main" ref={mainRef}
    onScroll={() => { if (mainRef.current !== null) rememberScroll(routeKey, mainRef.current.scrollTop); }}>
  ```

  而 `.main` 成为滚动容器的前提是 `height: 100vh; overflow-y: auto`，这条**只在 `@media (min-width: 56.0625rem)` 里**（`app.css:177-183`）；≤56rem 时 `app.css:231-238` 把侧栏改成 `position: static` 的顶栏，`.main` 高度随内容展开、**永远不可垂直滚动**，滚动的是 `document`。

- **后果（窄屏下两条承诺同时落空，且落空得无声）**：
  - `el.scrollTop = 0` 写入一个不可滚动的元素 → **换页后不回顶部**。从第 40 单点进订单详情，窗口停在原偏移，详情头部与「发货 / 退款」操作区在视口外，运营第一眼看到的是时间线和技术信息。
  - `.main` 的 `onScroll` 永远不会带非零 `scrollTop` 触发 → `rememberScroll` 记下的全是 0 → **后退/前进不恢复位置**。
- **影响**：这是 CSS 明确支持的断点（顶栏布局），却在这条断点上两个承诺行为都失效；平板/分屏用户会把"打开详情却看不到头部"当成页面坏了。
- **修改方案**：把"取滚动容器"抽成一个函数，按断点二选一：

  ```ts
  export function scrollHost(el: HTMLElement | null): HTMLElement | null {
    return el !== null && el.scrollHeight > el.clientHeight + 1
      ? el
      : (document.scrollingElement as HTMLElement | null);
  }
  ```

  `App.tsx` 里恢复与 `rememberScroll` 都改用 `scrollHost(mainRef.current)`；记忆的调用除了 `.main` 的 `onScroll`，再加一个 `window.addEventListener('scroll', …, { passive: true })`。更省事的做法：恢复时对两个候选都写 `scrollTop = 0`，记忆时取 `Math.max(main.scrollTop, document.scrollingElement.scrollTop)`。
- **验收**：窗口拉到 ~800px 宽 → 订单列表翻下去 → 点进详情 → 详情顶部可见；后退 → 回到原位置。

### 状态 / 反馈

#### P2-3 运营日志页完全没有 loading 态

- **位置**：`opslog/OpsLogPage.tsx:64-82`（`load`）、`:253-273`（分页器）
- **证据**：该文件里 grep `loading` **零命中**。`load()` 只做 `setRows / setTotal`，请求期间表格保持上一次内容、分页器保持「第 1 / 1 页，共 0 条」。
- **影响**：点「下一页 / 查询」后有 0.3–2 秒页面纹丝不动 → 运营连点「下一页」，一次跳过多页（且中途还会被 `seq` 竞态丢弃）。日志页是排查问题用的，误跳页等于漏看记录。
- **修改方案**：加 `const [loading, setLoading] = useState(false)`，`load` 里 `finally` 复位；翻页按钮 `disabled={loading}`；表格上方加 `{loading && <span className="muted">加载中…</span>}`（与 `OrdersPage.tsx:472`、`CustomersPage.tsx:105` 同一写法）；分页器文案在 loading 时隐藏「共 N 条」（照抄 `OrdersPage.tsx:379` 的 `{loading ? '' : …}`）。

#### P2-4 列表取数失败只走 Toast，页内没有"这份数据不是最新的"持久标记

- **位置**：`orders/OrdersPage.tsx:257-262` + `:472-476`；`products/ProductsPage.tsx:120`；`customers/CustomersPage.tsx:80-90`；`opslog/OpsLogPage.tsx:72-77`

  ```tsx
  // OrdersPage.tsx:257-262
  } catch (e) {
    if (seq !== reqSeq.current) return;
    // ⚠️ 失败不清列表（同商品管理）：只报错，列表保留上一次结果
    setFailed(true);
    const { text, traceId } = toastError(e, '订单列表加载失败');
    sink.error(text, { traceId });
  }
  ```

  `failed` 这个 state 唯一的用途是**抑制空态文案**（`:474` 的 `&& !failed`），页面上看不到任何"加载失败"。
- **说明为什么没打成 P1**：`ui/toast.tsx:59-74` 里 `error` 是**恒停留**的（不自动消失），风险被兜住了一半；但 Toast 在右下角、与表格无视觉关联，运营在表格里勾选/发货时未必把两者联系起来。
- **影响**：失败后表格保留上一次结果（可能已是几十分钟前的），运营照着它勾选批量发货 / 导出 CSV，导出的是过期数据。
- **修改方案**：给"失败"一个页内位置（与 `CategoriesPage.tsx:61` 的 `<p className="error">分类列表加载失败，请刷新页面重试</p>` 同口径）：

  ```tsx
  {!loading && failed && (
    <p className="error">列表没能刷新，下面显示的是上一次成功加载的结果（可能已过期）。请点「刷新」重试。</p>
  )}
  ```

  建议顺带把这句抽成 `ui/` 里的 `<ListError>`，四个列表页统一。

### 一致性

#### P2-5 运营日志的分页与其它三个列表页三处不一致

- **位置**：`opslog/OpsLogPage.tsx:37, 253-273` vs `orders/OrdersPage.tsx:711-735`、`products/ProductsPage.tsx:375-397`、`customers/CustomersPage.tsx:206-225`

  ```tsx
  // OpsLogPage.tsx:37 —— 本地 state，不在 URL
  const [page, setPage] = useState(1);
  // OpsLogPage.tsx:253-273 —— row2 + link 文字链，无每页条数
  <div className="row2">
    <button type="button" className="link" disabled={page <= 1} …>上一页</button>
    <span className="muted">第 {page} / {pages} 页，共 {total} 条</span>
    <button type="button" className="link" disabled={page >= pages} …>下一页</button>
  </div>
  ```

  而订单/商品/客户三页统一是 `<footer className="pager">` + `btn btn-secondary` + `<PageSizeSelect>`。
- **影响**：① 页码不在 URL → 刷新/分享/后退全部回第 1 页，与项目"列表状态走 URL"（`OrdersPage.tsx` 头部 @limitation 四）的约定背道而驰；② 无每页条数，审计记录只能按固定 20 条翻；③ 分页用 `link` 而不是 `btn`，同一站点两种分页观感。
- **修改方案**：`page` 收进 `route.query`（照 `readListParams` + `patch` 的写法），容器换 `<footer className="pager">` + `btn btn-secondary`，补 `PageSizeSelect`。若 `AUDIT_PAGE_SIZE` 是服务端硬上限，就换成一句「每页固定 20 条（服务端上限）」的 muted 说明——别让两个列表看起来不一样却说不清为什么。

### 危险操作

#### P2-6 分类「停用」一键生效、无二次确认，后果在**成功之后**才说清

- **位置**：`categories/CategoriesPage.tsx:82-90`、`categories/CategoryRow.tsx:97-99`


#### P2-8 结算页：闸门与按钮的禁用态**不同源**——`loading` 进不了闸门

- **位置**：`miniprogram/pages/checkout/index.wxml:181,193`；`index.js:242-255, 412-433`
- **现象**：原因行只吃 `gate.reason`，而 `gate` 由 `submitGate()` 从**状态**算出（`index.js:413-432` 的参数里**没有** `loading`）：

  ```xml

  <!-- :193 -->
  disabled="{{(!gate.ok && !gate.fix) || submitting || loading}}"
  ```

  刷新开始时会先置 `loading: true` 并**立刻**重算闸门（`index.js:242-255`：`this.setData({ loading: true, … })` → `this.updateGate()`），此刻 `data.quote` 可能还是上一次的旧值 → `gate.ok === true`、`gate.reason === ''`。
  - 现在的表象：按钮因 `loading` 而禁用，**但原因行是空的**——与该文件自己立的铁律冲突（`index.wxml:9`：「提交按钮禁用时**必须显示原因**，禁用不说为什么会被读成"这站坏了"」）。
  - 潜在的更坏结果：哪天有人把 `disabled` 里的 `loading` 去掉，闸门就会**拿着旧合计放行**，提交必然吃 40905（`index.js:635-638` 的注释已经警告过这条）。
- **修改方案**（推荐①）：
  1. **推荐：让闸门自己挡。** `disabled` 改回 `{{(!gate.ok && !gate.fix) || submitting}}`，把"正在重算"作为闸门的一种状态交给 `submitGate`（`refresh()` 开头 `updateGate()` 时若 `refreshing === true`，给出 reason「正在重新计算运费与合计…」）。与 `index.js:635-640`（MP3-05）已有做法同口径。
  2. 兜底：wxml 上补 `{{gate.reason || (loading ? '正在重新计算运费…' : '')}}`。改动最小，但把"为什么禁用"劈成两处，将来容易漂。

#### P2-9 结算页没有手动刷新入口

- **位置**：`miniprogram/pages/checkout/`
- **现象**：全库 grep `onPullDownRefresh / enablePullDownRefresh`，`cart`、`user`、`home`、`order`、`order-detail`、`pay` 六个页面都开了（且都有 shell 单测钉住"json 开了 enablePullDownRefresh"），**唯独 `checkout` 没有**；页面里也没有「刷新」按钮。

#### P2-10 售后页「问题类型」picker：首项可能选不中

- **位置**：`miniprogram/pages/after-sale/index.wxml:38-44`

  ```xml
  <picker mode="selector" range="{{reasonLabels}}"
          value="{{form.reasonIndex < 0 ? 0 : form.reasonIndex}}" bindchange="onReasonPick">
    <view class="input input--picker …"><text>{{view.reasonText || '请选择'}}</text> …
  ```

  `reasonIndex` 初始为 -1（未选）时 `value` 被算成 **0** → picker 打开后游标停在第一项、文案却显示"请选择"。用户打开后不滑动直接点「确定」，`bindchange` 是否派发取决于基础库对"值未变化"的处理——不派发就仍然停在"请选择"。
- **影响**：提交时才发现没选（提交按钮在缺项时是可点的，这是 `index.wxml:5` 的刻意设计），用户会觉得"我明明选了"。
- **修改方案**：方案 A——不用默认值兜底，改成**打开即选中第一项**（`reasonIndex` 初始为 0，文案显示第一项而非"请选择"），问题类型有合理默认的话反而少一步；方案 B——引入"未选"哨兵并同时处理 `bindcancel`。**无论哪个都必须真机验"打开后不滑动直接点确定"**。

## 第五章 横向规律

### 小程序端

13. **`order-detail` 物流卡上移到状态卡之后**，运单号与订单号同一写法（号码 + 右侧「复制」），复制后提示"打开手机浏览器，粘贴到地址栏即可查看物流"——如实说清能力边界。
