### 【1】P2 ｜ ③ 交互 ｜ 地址列表页「设为默认 / 删除」无在途守卫、无加载态

**位置**：`miniprogram/pages/address/index.js:155-199`（`removeAddress` 155-171、`onSetDefault` 178-199）；`miniprogram/pages/address/index.wxml:66-91`

**代码证据**：

```js
// pages/address/index.js:155-171
async removeAddress(id) {
  try {
    await app.globalData.api({
      url: `${app.globalData.apiBase}/api/v1/addresses/${id}`,
      method: 'DELETE',
      traceId: this.traceId,
    });
  } catch (err) { /* ...setData 错误条... */ return; }
  await this.load();
},
// pages/address/index.js:178-199
async onSetDefault(e) {
  /* ...取 id / raw... */
  try {
    await app.globalData.api({
      url: `${app.globalData.apiBase}/api/v1/addresses/${id}`,
      method: 'PUT',
      data: toAddressInput({ ...formModel(raw), is_default: true }),
      traceId: this.traceId,
    });
  } catch (err) { /* ...setData 错误条... */ return; }
  await this.load();
},
```

```html
<!-- pages/address/index.wxml:66-91（操作区：裸 view + catchtap，无 loading / disabled） -->
<view class="addr__act" wx:if="{{!pick}}" data-id="{{item.id}}" hover-class="ws-press" catchtap="onDelete">删除</view>
<view class="addr__act" wx:if="{{!pick && !item.isDefault}}" data-id="{{item.id}}" hover-class="ws-press" catchtap="onSetDefault">设为默认</view>
```

**对照组（全项目其余写操作均有在途守卫，本页是唯一缺口）**：

| 位置 | 守卫 |
|---|---|
| `pages/address-edit/index.js:184` | `if (this.data.saving === true) return;`（注释明写"POST /addresses 没有幂等键，双击会建出两条一样的地址"） |
| `pages/after-sale/index.js:85` | `if (this.data.submitting === true || this.orderId === '') return;` |
| `pages/checkout/index.js:542` | `if (this.data.submitting === true) return;`（注释 W-03：视图层回传有延迟，只靠按钮挡，快速双击的第二下会穿透） |
| `pages/user/index.js:198` | `if (this.retrying) return;`（注释：与结算页 W-03 同一类） |
| `pages/order-detail/index.js` | `cancelling` / `confirmingReceipt` 状态 + wxml 281-306 用 ws-button `loading` 挡连点 |

**问题说明**：三个具体后果——

1. **无加载反馈**：两个动作用裸 `<view>` 而非 ws-button，没有任何 loading / 禁用态，点击后页面纹丝不动直到请求返回，用户不知道是否生效，容易重复点。
2. **并发「设为默认」可能落错值**：对不同行快速连点「设为默认」会发出多个并发 PUT，服务端落库顺序不保证，最终默认地址可能不是用户最后点的那个；而页面 `await this.load()` 显示的是服务端结果，用户对此无感知。若用户随后直接去结算页，会按**错误的默认地址**预选并下单——"按错误地址发货"是电商场景里代价最高的一类错误。
3. **连点删除会显示误导文案**：连点删除时第二次 DELETE 打到已删除的 id，服务端返回 40400，页面显示"删除没有成功，地址还在"（`errorTitle('delete')`），而地址其实已经删掉了——用户会重复操作或误判数据状态。

**触发条件 / 复现步骤**：管理态进入地址列表 → ① 快速连点某行「删除」两次；② 对 A、B 两行先后快速点击「设为默认」，再进结算页查看预选地址。

**影响**：中。无资金损失，但后果 ② 直接导致错价发货级别的客诉；后果 ③ 造成误导与重复操作。

**建议修改（未实施）**：
- 给两个方法加入在途标志（如 `this.busyId`，同 id 在途直接 return），并在 wxml 动作上体现 loading / 禁用态（或改用 ws-button）；
- 针对后果 ②，更稳的做法是「设为默认」串行化（一个 pending 队列依次执行），保证"用户最后点的最后生效"；
- 与 `address-edit` 的 `saving` 命名口径保持一致，便于全项目审查时一眼看出守卫齐全。

**建议修改（未实施）**：统一补 `alive` 标志（onLoad 置 true、onUnload 置 false），三个回调里先判 `alive` 再 setData；写法与 checkout / after-sale 保持一致。

### 【3】P3 ｜ ⑥ 其他（排障 / 可维护性）｜ 「我的」页无页面级 traceId，两个请求链路断裂

**建议修改（未实施）**：在 `onShow`（或 `onLoad`）里 `this.traceId = newTraceId()`，两个请求补 `traceId: this.traceId`，与其它页口径一致。

**位置**：`miniprogram/pages/legal/index.js:23-27`（`@limitation 三`）

**代码证据（注释原文）**：

```
 * @limitation 三：**没有特商法表示（特定商取引法に基づく表示）**。它是日本法对通信販売的硬要求，
 *              但契约的 `/terms` 目前只给条款版本与三语种链接，**没有特商法字段**，
```

**反证（以当前契约与代码验证）**：
- `contracts/api-contract.yaml:739` 的 `/terms` 响应 schema 自 **0.6.33** 起已有 `documents`（四类法务文档 terms / privacy / refund / **tokushoho** 各三语绝对地址）与 `seller`（特商法商家信息，契约注释明写"只含已配置的字段（公司登记前为空对象，不编占位值）"）；

**问题说明**：注释称"契约没有特商法字段、需登记后单独立单元加字段"，而契约早就有字段、页面也已经在渲染。按"注释只能当线索、必须以代码验证"的审查规则，这是注释与事实相反。真实状态是：**字段已就绪，值待日本公司登记后配置**（这与注释后半句"要等登记完才有真值"不矛盾；矛盾在于"契约没有字段、需要立单元加字段"）。后来人若照此注释规划，会做重复开发，或误判特商法合规状态。

**触发条件**：任何人读该文件头做法务合规规划或排期。
