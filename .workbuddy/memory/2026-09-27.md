## 🔴 本轮踩到并记下的教训

### §2 第 46 条：工作区有并发写入时，**提交前必须逐文件核对暂存区**
- 现象：`git add` 显式列了 10 个文件，但 `mount.ts` 里**混入了另一个会话的改动**
  （`import markOrderDisputed` + `disputed` 注册块），typecheck 才把它抓出来
  （`Cannot find module './mark-disputed.js'`）。
- 正解：`git add <显式路径>` 之后、**提交前**跑 `git diff --cached` 逐个看，
  尤其 `mount.ts` / `webhook-results.ts` 这类**多方共享的高频冲突点**。
  "我 add 的是我的文件" ≠ "我 add 的文件里只有我的改动"。

### §2 第 47 条：`git stash` 前后要重新 `git status`——工作区不是私有的
- 本轮为验证 e2e flaky 用了 `git stash push` / `pop`，期间另一个会话往工作区写了
  `mark-disputed.ts`、`mark-disputed.db.test.ts`、`docs/问题清单和整改方案-2026-09-27.md`，
  并改了 `idempotency.ts`（租约续期并发修复）与 `docs/README.md`。
- 处置（用户拍板：**只精确提交我这轮的文件**）：
  ① 用**显式路径** add + commit，绝不 `git add -A`；
  ② 对方不合规的文件（lint 红：F10 `new Date()`、缺 @limitation）**临时移到 /tmp**，
     提交/跑门禁后**立即恢复**（备份在 `/tmp/other-session/`）；
  ③ 不代为修改对方的文件（不替他 prettier、不替他补注释）。

### 🔴 核心发现：结案不清 `has_dispute` = 订单被**永久锁死**
- `shipGuard`（40909）与 `refundGate`（40907）在 `domain/admin-order-actions.ts`，
  deny reason 就叫 `dispute_open`，读的是 `orders.has_dispute`。
  语义是「**有进行中的拒付**」，但 U-F3 从不清它 → 拒付结案后这张单
  **永远不能发货、永远不能退款**，且没有任何一方报错。
  👉 **这不是显示问题，是运营做不了事。**
- ⚠️ 契约 `AdminOrder.has_dispute` 的描述**本来就写着"存在进行中的拒付"**——
  所以 0.6.7 之前是**契约与实现不符**，这一版是**修复漂移，不是改口径**
  （写 AJ / 契约说明时必须点明这一点，否则会被误读成"又改口径了"）。

### 实现要点
- `ports/payment.ts`：`outcome` 增 **`dispute_closed`**（与开案的 `disputed` **分开**）。
  @why 合并就要每个落账器自己分辨开案/结案，漏分辨 = "结案事件把开案又写一遍"
  （已 won 的拒付被重新标成 open）。增可选字段 `disputeStatus`（机构 status 原值，**不映射**）。
- `stripe-checkout.ts`：`charge.dispute.closed` → `dispute_closed`；
  只在 `obj.object === 'dispute'` 时回带 `obj.status`
  （charge/session 的 status 是**支付**状态，不分对象回带会把"支付失败"当成"拒付输了"）。
- `domain/dispute-input.ts`：`parseDisputeResult`（won/lost）。
  未结案状态一律 undefined（把 `needs_response` 认成 lost 后果最严重：拒付还有救却按已输结案）；
  **`charge_refunded` 故意不映射成 lost**（退款已由机构执行，我方不该再退一次）。
- `markDisputeClosed`：定位支付行用 **dispute_id 精确匹配**（不是"最近一条 succeeded"）——
  结案是对**某一条**具体拒付的判决，按"最近一条"会在"旧拒付已结、新拒付刚开"边界上判错对象。
  已结案且结果相同 → 幂等；结果不同 → 40902 `dispute_result_conflict`（不静默改判）。
  结案时刻取**入库时刻**（SQL now()），与开案相反——开案时刻是举证期限起点必须取机构时间，
  结案时刻不是任何期限起点，且 Stripe 对象上根本没有"结案时间"字段。
- 新 reason 三个（`dispute_not_open` / `dispute_result_conflict` / `dispute_result_unknown`）
  **全部进管线 error 级词表**：不进 = warn + 2xx = 机构不再重发、没人看见。

## 📌 缺陷注入的可复用做法（本轮用了 4 次）
写 Python 脚本（**不要用 sed**：BSD sed 的 `-i ''` 在本机会把脚本当文件名，报 No such file）：
```python
ORIG = F.read_text(); F.write_text(ORIG.replace(old, new, 1))
code = subprocess.run([...vitest...], env={**os.environ, "NODE_OPTIONS": ""}).returncode
# 锚点不存在要报 ❌ 而不是静默跳过；最后务必写回 ORIG 并复跑确认绿
```
⚠️ 三条纪律：① 退出码**直接取**，不能走管道（§2 第 43 条）；
② 锚点不存在必须显式报"注入无效"（否则以为守住了）；
③ **注入没变红时先怀疑用例，不只是怀疑实现**（本轮 ⑩ 就是这样补出一条断言的）。
